# The Docker write build — docker-backed vendor executor dispatch (executor-seam follow-up)

## Context

PR-4 of the executor seam (camus C1-1, next-ten #7) shipped the `access:`/`session_sandbox:` knobs **enforce-only**: `access: :write` requires `session_sandbox: :docker` at hydration, and `:docker` is refused at dispatch (`forge_executor.ex:245-255`) — "write can't reach a live session this wave." This plan is the named follow-up: make `session_sandbox: :docker` vendor dispatch real, so a write-capable codex/claude session runs inside an sbx microVM with a direct rw repo mount (the pinned OQ-1(a) materialization), deposits typed output through the scoped MCP endpoint, and its edits land in the real working tree.

**Environment fact that reshapes the design:** the installed sbx (v0.34.0) **rejects `--mount` and `--network`** as unknown flags (probe-verified). Workspaces are now `sbx create [flags] AGENT PATH [PATH...]` positionals (rw default, `:ro` suffix), mounted in-VM **at the same absolute path as the host** (proven by `docker_integration_test.exs:58-62`); network control moved to `sbx policy` (global init + `allow|deny network [--sandbox NAME] RESOURCES`, comma-separated `host[:port]`, `**` wildcard). This means the shipped front-door exec-tier create path (`extra_mounts` → `--mount`, `network: :none` → `--network none`) is **broken against the installed CLI today** — a live break this plan repairs (Unit A), operator-ratified fold-in.

**Operator-ratified decisions (this session):**
1. **Write posture in-VM = the runners' existing `:full` arms** (codex `--dangerously-bypass-approvals-and-sandbox`, claude `--dangerously-skip-permissions`) — the microVM + workspace mount mode is the boundary (camus sketch (d)). `:read_only`+docker keeps the read-only CLI flags AND a `:ro` mount (defense in depth). Executor `access: :write` → runner `access: :full`; `:read_only` → `:read_only`.
2. **sbx 0.34.0 drift remediation folded in** as its own unit (Unit A) — same-path workspace positionals + policy-based network control, front-door producer migrated.
3. **Live smoke: both vendors**, real sandboxes, PR-2 style. I run `sbx policy init balanced` (one-time host-global; approved). Operator clicks the one-time macOS Keychain prompt when it appears.
4. **Shared claude credential source** (Unit C): host `.credentials.json` → legacy `credentials.json` → macOS Keychain (`security find-generic-password -s "Claude Code-credentials" -w`), written in-sandbox to the **dotted** `.credentials.json` (what in-VM Linux claude reads under `CLAUDE_CONFIG_DIR`); fixes the latent macOS `:no_credentials` on the local path too. The blob never lands on host disk.

**Design pillars (verified against source):**
- **Same-path mounting kills path translation**: repo materializes as an extra workspace positional (`project_dir` or `project_dir:ro`) → `cwd`, `--add-dir`, `-C`, and prompt paths are valid verbatim in-VM. After Unit A constrains `extra_mounts` to host==container, the repo mount is expressible through the **existing** `extra_mounts` spec key `{project_dir, project_dir, "rw"|"ro"}` — no new mount key, `RecoveredSpec` already whitelists it.
- **Deposit reachability**: `ScopedEndpoint` keeps its `127.0.0.1` bind; the in-VM consumer gets the URL host rewritten to `host.docker.internal` and a per-sandbox `sbx policy allow network --sandbox <name> "host.docker.internal:<port>,localhost:<port>"` rule (both forms required per `docs/exploration/sandboxes/README.md:318-320` — spike-verified only, so this is the live smoke's **gate**: if the sbx proxy can't reach host loopback, STOP and redesign — never silently bind wider; the consolidator shares `ScopedEndpoint`). Anubis's streamable-HTTP plug validates only `Accept` (no Host/Origin check) — transport-clear.
- **stdin-EOF comes free**: `sbx exec` without `-i` = docker-exec semantics (stdin not attached ⇒ immediate EOF) — replaces HostShell's `</dev/null` wrap for the docker path. Integration-probed + smoke-verified.
- **Auth ports verbatim**: credential files ride the existing exec-based `FileSync` transport (in-VM writes on docker); `CODEX_HOME`/`CLAUDE_CONFIG_DIR` ride `.forge_env` → `--env-file`. API keys stay out of sbx env (default-deny scrub unchanged).

Done means: all units land, both-vendor live smoke green (findings folded back), `mix precommit` passes (exit code + counts verbatim), **nothing committed/staged**. Keep a `## Deviations` section in this file current as implementation reveals corrections.

## Unit A — sbx 0.34.0 remediation (repairs the live exec-tier break)

### A1. `lib/jido_claw/forge/sandbox/docker.ex`
- `build_create_args/4` (:282-299) restructure: mounts become **trailing positionals AFTER `[agent_type, workspace_dir]`** (order matters — sbx treats the first PATH as the primary workspace). Verify `sbx policy deny network --help` mirrors the allow syntax at implementation time. A spec carrying BOTH `network: :none` and a non-empty `allow_network` is **rejected up front** (contradictory intent; no producer needs both).

- `RecoveredSpec.normalize_sandbox_spec` (recovered_spec.ex:161-182): add `"allow_network"`/`:allow_network` to drop_keys + `put_present(:allow_network, ...)` — validated list per the shape rule, fail closed otherwise.

- **E finding 1 — stdin-EOF does NOT come free** (plan assumed "sbx exec without -i = immediate EOF; integration-probed"): the original TTY probe was misleading — under OsCmd the sbx client's stdin is a never-EOF PIPE and the client forwards it into the exec, so `Docker.run(client, "cat")` hung to timeout (integration test caught it red). - **E finding 2 — `sbx exec --env-file` is INERT on 0.34.0**: probed directly — the file's vars never reach the exec'd process while `-e K=V` does; the shipped `--env-file` emission was silently dead (docker_integration inject_env tests caught it red). `-e` was rejected (resolved vault secrets on the HOST argv = ps-visible). - **E finding 4 — harness `terminate/2` was dead code on the stop path (latent product bug, now load-bearing)**: `Manager.stop_session` terminates the harness child with a `:shutdown` exit and the harness never trapped exits — so `terminate/2` (whose body was explicitly written for Manager-driven `:shutdown`: `maybe_finalize_phase` comments name it) NEVER ran there, and `Sandbox.destroy` never fired on graceful stops. Invisible for HostShell (linked sandbox Agents die with the harness; the boot reaper sweeps workspace dirs); a leaked microVM + secret-bearing workspace per session on docker (the smoke's 90s drain caught it — the VM sat "stopped" forever). Fix: `Process.flag(:trap_exit, true)` in `Harness.init`, with the destroys DETACHED under the app TaskSupervisor — a first cut used a 30s child `shutdown:` budget with inline destroys, which blew every `stop_session` caller's 5s GenServer.call deadline and would have serialized wave teardowns through the singleton Manager; the detached-task shape keeps stop latency unchanged and leaves interrupted rms to the boot reaper. Stray `{:EXIT,…}` messages land in the existing `handle_info` catch-all. Pinned red-first by `harness_teardown_test.exs` via a new `StubSandbox.destroy` notify seam (`:stub_sandbox_destroy_notify` — the facade dispatches post-create calls by CLIENT STRUCT, so a delegating recorder module can't observe destroy).
- **E finding 5 — `persist/1` wasn't exit-total**: the harness's best-effort persistence guard only rescued raises; DBConnection faults arrive as EXITS (checkout on a dead pool/owner), and inside `terminate/2` an uncaught exit REPLACES the session's real exit reason (`:normal` → a DB error) for every monitor. - **E finding 3 — deny-all is enforced IN-BAND, not at transport**: the per-sandbox deny rule works (`sbx policy log` records every denial), but the transparent proxy accepts the TCP connect and answers HTTP 403 with a "Blocked by network policy" body (HTTPS included — the sandbox trusts the proxy CA), so the old curl exit-code probe read denials as REACHED.
