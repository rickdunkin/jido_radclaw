# V2-1: Per-Tool-Call Approval Gate with Durable Approval Interrupts

## Context

Per `docs/exploration/jidoka/FEATURES-WORTH-BORROWING-V2.md`, **V2-1 (operation controls with durable approval interrupts)** is the headline remaining borrow — "the single most threat-model-aligned item V2 added", Tier 1, NOT_ADOPTED, nothing blocking it. The V1 doc has zero NOT_ADOPTED entries and both PARTIALs are parked behind triggers that haven't fired; V2-2..V2-7 are explicitly sequenced after/below V2-1. So this is the next work item.

**The gap**: gating exists at the workflow axis (Reactor gate/case family) and the sandbox layer (Forge), but at the conversation axis nothing sits between the LLM's decision to call `git_commit`/`network_share`/`kill_agent`/etc. and the tool executing. The codebase already anticipates this feature: `JidoClaw.Gates.ToolCallGate` (kind `:tool_call`) shipped **declared-but-unproduced** — "the tool-approval producer … is future work; the kind ships now so the vocabulary, `AgentCase.kind` column, and approval surfaces are ready for it." This plan is that producer.

**Design (ticket pattern, per the doc's recommended v1)**: a require-listed tool call is intercepted in the shared `Tools.Action` wrapper → a durable pending `AgentCase` (kind `:tool_call`) is created, keyed by a fingerprint of `{tenant, session, tool, args}` → the tool returns a structured non-retryable `approval_pending` error the LLM relays to the user → operator approves via existing surfaces (REPL `/gates approve <id>`, web `/approvals`) → the LLM retries the identical call, which matches the approved fingerprint and executes, consuming the approval.

**User-confirmed knobs**: ship **enabled** with conservative require list (`network_share, kill_agent, schedule_task, unschedule_task, git_commit, forget, replay_workflow`); approvals are **single-use**; rejections are **deny-once** (identical call later re-pends). Test env ships disabled.

**Plan-review findings folded in (user review)**:
- **Bypass**: `run_command` could route shell equivalents of gated tools (`git commit ...`) ungated → add **param-pattern triggers**: per-tool regex patterns on a designated param that also require approval (minimal phase-2-predicate support). Defaults for `run_command`/`:command`: git-commit equivalence via `~r/\bgit(?:\s+-{1,2}\S+(?:\s+\S+)?)*\s+commit\b/` — matches plain `git commit` **and option-bearing forms** (`git -C repo commit`, `git -c user.name=x commit`, `git --git-dir=.git commit`) while NOT matching bare-token interpositions (`git log && echo commit` stays unmatched — non-option tokens break the chain); plus `~r/\bcrontab\b/` (schedule_task equivalence). Tests must cover each option form and the false-positive-avoidance case. Documented precisely: quoted-args-with-spaces edge cases (`git -C "my dir" commit`) are out of regex reach — operators wanting full shell containment add `run_command` to `require`. False positives just ask for approval — acceptable.
- **Coverage**: the marker sweep must include MCP-published tools (`replay_workflow` is MCP-only and on the require list), plus a test asserting every shipped require-list entry resolves to a real tool name.
- **Per-template `require_approval` dropped** for v1: `ToolContext.child/2` clears `:agent_template` and `spawn_agent`/`send_to_agent` don't restore it, so template policy would silently not apply to spawned agents — an inconsistent enforcement surface. Global config only; per-template returns as a follow-up once child contexts thread the template name.
- **Fingerprint canonicalization**: hash a canonical semantic term (DefinitionFingerprint pattern), not raw params — deep-normalize map keys and atom scalars to strings, maps to sorted pair lists, so atom/string-keyed JSON-equivalent shapes fingerprint identically across MCP/internal paths.
- **`session_id` precision**: `AgentCase.session_id` stores `tool_context.session_uuid` (the `Conversations.Session` UUID FK, ToolOutput pattern); the runtime external session id goes in `details` only.

**Also retired**: the dormant `JidoClaw.Platform.Approval` GenServer (blocking-await scaffolding, zero callers) and its `tool_approval_mode` config key.

## Verified load-bearing facts

- **Wrapper insertion point**: `lib/jido_claw/tools/action.ex` `__before_compile__` wraps every tool's `run/2` as `MCPScope.wrap(name, params, context, fn enriched -> super |> Error.normalize_result |> OutputRedaction |> OutputShaper |> OutputLimit end)`. 38 tools use it; marker-sweep tests (`test/jido_claw/tools/output_redaction_test.exs:71-89`) today sweep only `JidoClaw.Agent.tool_modules()` — Step 4 extends them to MCP-published modules and adds the third (approval) marker.
- **Context seam (verified in deps)**: jido_ai 2.2.0 flat-merges the caller's `tool_context` map into the run/2 context (`deps/jido_ai/.../react/strategy.ex:641,694-702`) — on the live ReAct path scope keys arrive at **top level**, `context[:tool_context]` is absent, and tools/OutputShaper silently run on fallbacks. The gate needs scope on exactly that path, so a scope-lift step is required (Step 1). jido_ai also overrides `:agent_id` with the runtime id — the lift must exclude `:agent_id` to avoid changing swarm parent-scoping (`SwarmScope.scope_from_tool_context`).
- **`{:error, %{code: :approval_pending, ...}}` is non-retryable** in jido_ai (verified: `retryable_type?` whitelist `[:timeout, :transient, :transient_error, :rate_limited]`, deps/jido_ai/lib/jido_ai/error.ex:467). The code/message/details are preserved through the local `Tools.Error.normalize/1` pre-shaped-map clause (error.ex:119-122), then serialized by jido_ai as the normal tool-error envelope and appended as a tool-result message the LLM reads and relays. **Constraint**: `details` must not contain `:reason`/`:retry`/`:retryable` keys (jido_ai's retry-hint digger inspects them). Keep details to `%{case_id: id}`.
- **`Cases.decide` is run-coupled** and both callers crash on a case-shaped return (`run.name` in `approvals_live.ex:184-189` and `cli/commands/approvals.ex:54-58`); `Cases.load/3` unconditionally loads the run. All three need the run-less branch.
- **`AgentCase.details` has no write-time redaction** (caller contract) — the producer must pre-redact (`JidoClaw.Security.Redaction.Transcript.redact/1`) and cap args summaries (`ToolTranscript.summarize_args/2`); `AgentCaseEvent.data` is auto-redacted by its Allocate change.
- **Concurrent identical calls race** (runner executes tool batches via `Task.async_stream`) — pending-case uniqueness needs a **named** partial unique index so `AshErrors.unique_violation?/2` (matches on constraint-name fragment, `core/ash_errors.ex:36-40`) can drive the race-loser re-read.
- `change filter(expr(...))` + `set_attribute` is the house DB-fence idiom (agent_case.ex:95-98); `is_nil/1` works in those exprs. `%GateContext{run: nil}` is legal (`@enforce_keys` requires presence, not non-nil); ToolCallGate's no-op hooks never touch `ctx.run`.
- **`mix jidoclaw.system_prompt.check`** (runs in precommit) checks `priv/defaults/system_prompt.md` only: tool-catalog count heading == `length(JidoClaw.Agent.tool_modules())` and line-start `**snake_case**` tokens ↔ registered tool names. New prose must not start lines with `**snake_case**`. `.jido/system_prompt.md` is gitignored and auto-synced at runtime.
- reach arch rules only constrain web/data layers — `Security.* → Orchestration.*` is legal.
- Tenant rows exist on every session-bearing path (`Workspaces.Resolver.ensure_workspace` → `Tenant.ensure`); tests use `JidoClaw.TenantCase.seed_tenant`.

### Step 3 — Producer: `lib/jido_claw/orchestration/tool_approvals.ex` (new)

`request(scope, tool_name, params) :: {:allowed, case} | {:pending, case} | {:denied, case}`:
- **Actor fallback (load-bearing)**: all `AgentCase` writes go through the base resource policy, which requires an actor whose tenant matches the row (`resource.ex:25`); some valid tool contexts carry `tenant_id` but no `:actor`. Resolve `actor = scope[:actor] || Actor.system(tenant_id)` — the exact `MCPScope.actor_for/1` pattern (mcp_scope.ex:192-206) — so a valid tenant-scoped call can't become `approval_unavailable` because the producer itself was unauthorized.
- `fingerprint/3`: `sha256(:erlang.term_to_binary({:v1, tenant_id, session_uuid || session_id, tool_name, canonical_params(params)}, [:deterministic]))` hex. `canonical_params/1` builds a canonical semantic term first (DefinitionFingerprint discipline): deep-walk — maps become key-sorted pair lists with stringified keys, atom scalars stringified, lists keep order — so JSON-equivalent shapes (atom vs string keys, MCP vs internal path) fingerprint identically.
- Classify `by_fingerprint` rows in order: approved-unconsumed → `Ash.transact([AgentCase, AgentCaseEvent])` { `consume` + `:consumed` timeline via `WorkflowLog.case_event` } → `{:allowed, case}` (stale-record loss → re-classify); any pending → `{:pending, existing}`; rejected-unconsumed → transact { `consume_rejection` + timeline } → `{:denied, case}` (loss → re-classify); else transact { `open_tool_call` + `:opened` timeline } + `RunPubSub.broadcast_gate({:gate_requested, nil, %{tenant_id:, agent_case_id:}})` → `{:pending, new}`; on unique-violation race (`AshErrors.unique_violation?(err, ["agent_cases_pending_fingerprint_index"])`) → re-read pending and return it.
- `details` seeded like GateStep does, via a **new shared helper `JidoClaw.Orchestration.Gate.Presentation.details/1`** (gate_title/description/fields from `Gate.Info`; GateStep's private `dsl_details/1` moves there and GateStep delegates) merged with `%{"tool" => tool_name, "arguments" => args summary, "session_id" => runtime external session id, ...}`. **Argument order is load-bearing: `Transcript.redact/1` on the structured params FIRST, then summarize/cap** — summarizing first destroys key context and lets key-named secrets (`%{api_key: "no-regex-pattern"}`) leak; test exactly that case. Must stay small — CLI `print_case` inspects details raw. `AgentCase.session_id` (the column) gets `scope.session_uuid` — the Conversations.Session UUID, never the runtime external id.
- Lock-order note: run-less transactions touch the case row first and `AgentCaseEvent.Changes.Allocate` re-locks the same row in the same transaction — no deadlock window (verified).
- Tests (`test/jido_claw/orchestration/tool_approvals_test.exs`, TenantCase): full lifecycle, duplicate-pending reuse, single-use consume, deny-once, claim races, unique-race fallback.

### Step 4 — Policy + wrapper gate

- `config/config.exs`: replace `tool_approval_mode: :off` (line ~188) with
  `config :jido_claw, :tool_approval, enabled?: true, require: ~w(network_share kill_agent schedule_task unschedule_task git_commit forget replay_workflow)` (+ rationale comment, DestinationPolicy style). `config/test.exs`: `config :jido_claw, :tool_approval, enabled?: false`.
- `lib/jido_claw/security/tool_approval.ex` (new): in-module defaults + per-call opts override (`opt_or_config` pattern from DestinationPolicy); `gate(tool_name, params, context, opts \\ [])` → `:ok | {:error, %{code: :approval_pending | :approval_denied | :approval_unavailable, message: ..., details: ...}}`. `details: %{case_id: id}` **only when a case exists** (pending/denied); `:approval_unavailable` paths (no tenant scope, DB failure) carry `details: %{}` and a message that is clearly non-approvable ("denied fail-closed: no tenant scope to record an approval request — configuration issue, not an approval request"). Never put `:reason`/`retry*` keys in details (jido_ai retry-hint digger). Scope from `context[:tool_context]` (guaranteed by Step 1). Messages: pending → instruct the LLM to relay the case id + `/gates approve <id>` (or dashboard Approvals) and retry the identical call only after approval; denied → "operator rejected — do not retry automatically; ask the user how to proceed".
- **Requirement check (global config only — no per-template knob in v1)**: `required?` = `tool_name in require` **or** a param-pattern trigger fires. In-module default `@require_patterns %{"run_command" => {:command, [~r/\bgit(?:\s+-{1,2}\S+(?:\s+\S+)?)*\s+commit\b/, ~r/\bcrontab\b/]}}` (shell equivalents of gated `git_commit`/`schedule_task` — the git pattern matches option-bearing forms `git -C repo commit` / `git -c user.name=x commit` / `git --git-dir=.git commit`, must stay identical to the Step-1-findings default), overridable via the `:require_patterns` config key (invalid entries warn-and-skip — defaults stay in-module, so config typos can't disable the shipped patterns). **Param lookup normalizes atom/string keys** (`params[key] || params[to_string(key)]`, same spirit as the fingerprint canonicalization) so a raw/MCP-path `%{"command" => "git commit"}` can't slip past a configured `:command` trigger. Pattern-triggered approvals use the same fingerprint/case machinery; the denial/pending message names the matched pattern.
- `lib/jido_claw/tools/action.ex`: third macro-enforced concern — inside the wrap callback, `case ToolApproval.gate(...)` branches and **both** arms flow through the full `Error.normalize_result → OutputRedaction → OutputShaper → OutputLimit` tail. Third marker `def __jidoclaw_tool_approval_gated__, do: true`.
- **Coverage tests**: third marker sweep over `JidoClaw.Agent.tool_modules()` **plus the MCP-published tool modules** — accessor on `JidoClaw.MCPServer` that **derives from the existing `__publish__/0`** (no duplicated list, so the sweep can't drift; `replay_workflow` is MCP-only and on the require list); extend the existing two sweeps to MCP-published modules too; a config-sanity test asserting every shipped `require` entry and `require_patterns` key resolves to a real wrapped tool name, **and that each `require_patterns` param name exists in that tool's `schema` as a string-ish field** (catches both list typos and a mistake like `{run_command, :cmd}` that would silently never match — read the tool module's `schema/0` and assert the keyed field is `:string`).
- Tests: policy unit tests (env-free via opts — require list, pattern triggers incl. chained `&& git commit` commands, disabled passthrough), fingerprint determinism + canonicalization (atom vs string keys), wrapper integration (inline victim action: pend → approve → pass → consumed → re-pend; reject → denied → re-pend; disabled → pass-through; no-tenant → unavailable). **Consume-before-execution test**: a victim action that approves, then *raises/errors* on execution — assert the approval is already consumed (the identical call re-pends, doesn't re-run) so a post-approval tool failure leaves no reusable approval. Documents the tradeoff: an approval grants **one attempt, not one successful side effect**.

## Verification

1. Per-step: targeted new tests + `mix test` after each step (Postgres required; `mix ecto.migrate` after Step 2).
2. End-to-end (test-level): wrapper integration test drives the full ticket loop — gated tool pends → `Cases.decide` approve → identical call executes once → re-pends; reject → denied once → re-pends; tool-call cases appear in `pending_for_tenant` (the `/gates` + `/approvals` inbox source).
3. Final gate: `mix precommit` passes clean (the task's completion criterion).
4. Optional manual smoke (needs a configured provider): `mix jidoclaw` → ask the agent to `git commit` → expect relayed approval message → `/gates` → `/gates approve <id>` → ask it to retry → commit executes.

## Out of scope (recorded in the doc-status note)

## Post-approval housekeeping

Save feedback memories from the two plan-review rounds: (1) gating specific tools needs a bypass analysis for equivalent capabilities reachable through general-purpose tools (shell — including option-bearing invocation forms like `git -C repo commit`), and coverage sweeps must include every publication surface (MCP-only tools), not just the primary registry; (2) fingerprints/dedupe keys hash a canonicalized semantic term (key/atom normalization), not raw params; (3) extend the existing redact-before-truncate memory: redaction must see the full *structured* original — summarizing/serializing first destroys key context; (4) before citing a repo pattern (e.g. FK `on_delete` behavior), verify it in the generated artifact (migration), not just the resource declaration; (5) project memory: iterate schema work with `mix ash.codegen --dev`, squash to one named codegen before the precommit gate.
