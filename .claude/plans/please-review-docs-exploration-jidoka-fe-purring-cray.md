# Plan: Finish the genuinely-deferred Jidoka-V2 borrows

## Context

`docs/exploration/jidoka/FEATURES-WORTH-BORROWING-V2.md` declares the V2 borrowing program "complete" (Program status, 2026-06-16). A three-agent audit of the doc's claims against the actual code found **no overclaims** — every entry marked ADOPTED/shipped is genuinely present (real migrations, partial indexes, effect emission, tests). So the "stuff that hasn't actually been done" is precisely the **deferred** items.

Of those deferrals, almost all carry an explicit, reasoned "we chose not to" justification (V2-1 input/output-length controls = "not load-bearing for this threat model"; V2-2 per-tool approval overlay = "superseded by per-template reach-allowlist"; V2-5 eval harness / V2-7 Lua DAGs = "don't build ahead of the pain"). **Two are genuine pending work that the "complete" summary quietly glosses over:**

1. **V2-2 reconnect/re-discovery** — the MCP `Consumer` discovers each server's tools **once** at boot and never again. A hard prep crash parks it in `:failed` **permanently** (no timer, no re-spawn; the OS supervisor can't help because the `Consumer` traps the prep `DOWN` and never itself crashes — `consumer.ex:203`). A server that's down at boot, or that later changes its tool set, is never picked up until an app restart.
2. **V2-4 "P1 consumer-attach"** — replay preflight diagnostics are attached for three specific refusal reasons but **not** on the raw-read-error refusal path; an opaque Ash error from the irreversibility check surfaces as a bare `inspect/1` string with no preflight summary.

**Outcome:** the MCP subsystem self-heals from a transient prep crash and keeps live agents' external tool sets in sync with their servers; and a replay refused by an events-read failure surfaces a structured preflight report instead of an opaque error.

**Confirmed scope** (per your answers): MCP **full reconnect/re-discovery** (crash-recovery *plus* periodic re-discovery) **+** the V2-4 replay-diagnostics follow-up. The reasoned non-goals stay deferred.

Greenfield project — no data/path back-compat to preserve. **Not done until `mix precommit` is green.** Nothing committed; leave everything unstaged.

## Phase A2 — MCP periodic re-discovery

Re-run discovery on an interval while `:ready`, diff against the current tool set, and reconcile live agents (register added/changed tools, **unregister** removed ones via `Jido.AI.unregister_tool/3`).

**File: `lib/jido_claw/mcp/consumer.ex`**

- **`attached` becomes `Map<pid, template>`** (was `MapSet<pid>`). Reconciliation needs each attached pid's template to apply the reach-allowlist. Thread the template through the mark flow: `register_and_mark/3` → `…/4` and the `{:mark_attached, pid, generation}` cast → `{:mark_attached, pid, generation, template}` (both call sites — `start_register_task` and `mcp.ex`'s `do_ensure_attached` — already have the template). Update `:already` fast path / fan-out reject / DOWN cleanup to `Map.has_key?`/`Map.put`/`Map.delete`.
- **Endpoint refresh — the "came online after a failed boot init" case (review P1).** Re-running `prepare/1` is **not** enough on its own: `Live.register_endpoint/1` folds `{:endpoint_already_registered, _}` → `:ok` *without* restarting the client (`live.ex:25`), and Anubis `await_ready` only parks until `server_capabilities` exist (`anubis/client.ex:~1088`), so a client that's alive-but-stuck (its server was unreachable during boot init) never re-initializes via re-`register` + re-`await`. The dep provides the cure: **add `refresh_endpoint/1` to the `JidoClaw.MCP.Client` behaviour** + `Live` (delegate `Jido.MCP.refresh_endpoint/1` → `ClientPool.refresh/1`, a real stop+restart, `client_pool.ex:163-176`) + `Stub` (`resolve(:refresh_endpoint, …, :ok)`). Refactor `prepare_server/1` to a `discover/1` (the existing register→await→list `with`) wrapped by **refresh-on-failure-retry**: a healthy endpoint lists fine (never refreshed); a failed one is `refresh_endpoint`ed and retried **once**. Gate it behind a `refresh?` flag threaded through `prepare/1` (final signature `prepare(servers, refresh?)` / `run_prep(parent, servers, refresh?)`) — boot passes `false` (stay fast when a server is simply down); the **crash re-prep (A1 `:reprep`) and re-discovery paths pass `true`**. The single `discover/1` helper keeps the two `with`-blocks from becoming a clone.
  - **Scope boundary to document at the refresh note (review P2):** `refresh_endpoint/1` restarts the endpoint **as stored in `ClientPool`** — it does **not** apply a changed connection *spec* (URL/command/env) for an existing server *name*; that's config hot-reload, explicitly **out of scope** (needs `unregister_endpoint` + re-`register`, a future extension). What re-discovery *does* pick up: **new** server names (registered fresh), **tool-set changes** on existing servers, and a previously-unreachable server **coming online** (via refresh). A server *removed* from config has its tools pruned from agents (it's absent from `new_modules` → in the `removed` diff), though its `ClientPool` endpoint lingers until restart (a documented minor residue, not a tool-exposure leak).
- **Single-owner re-discovery timer (review P2 — one cadence, no overlap).** Arm the timer **once on `{:prepared}`** (entering `:ready`), then **re-arm only when an attempt finishes** — in the `{:rediscovered}` handler and the rediscovery-`DOWN` handler. Do **not** re-arm inside the `:rediscover` handler that *launches* an attempt (that's what caused the duplicate-timer ambiguity). Config `mcp_opt(:rediscovery_interval_ms, 300_000)` (5 min default; **`0` disables** auto-arming — `arm/1` is a no-op at `0`, but a manually-sent `:rediscover` still reconciles, the deterministic test seam). State carries **both `rediscover_ref` and `rediscover_pid`** (review P3 — the pid is needed by the crash test + manual smoke).
- **`handle_info(:rediscover, %{status: :ready, rediscover_ref: nil} = state)`:** `spawn_monitor` an off-process re-discovery prep (`prepare(servers, true)`, re-reads config, tolerates still-unreachable servers → `{[],%{},%{}}`), store `rediscover_ref`/`rediscover_pid`, **do not re-arm** (the attempt's completion/crash owns the next arm). Suppress/lower the per-tick parse/unknown-template warnings on this path. A fallthrough `handle_info(:rediscover, state)` ignores a tick that arrives while not-`:ready` or already in-flight (cadence resumes via `{:prepared}` on recovery, or via the in-flight attempt's re-arm).
- **`handle_info({:rediscovered, ref, new_mods, new_policy, new_templates}, state)`:** **apply only when `ref == state.rediscover_ref`** (drops a superseded/stale result); `Process.demonitor(ref, [:flush])` to drop the trailing normal-exit DOWN; then —
  - **Two independent conditions keep a tick cheap:** bump `generation` + spawn per-pid reconcile tasks **only if** `new_mods`/`new_templates` changed; republish the policy **only if** `policy_changed?(new_policy, approval_policy())`. A true no-op (neither changed) just clears `rediscover_ref`/`rediscover_pid` and re-arms — no tasks, no `:persistent_term.put`.
  - **On an actual tool-set change, mint a fresh `generation` (review P2 — the in-flight-attach race).** A `start_register_task` spawned just before this tick captured the *old* module set and carries the *current* `generation`; without a bump its later `{:mark_attached, pid, gen, template}` would be honored (same incarnation, matching `gen`), falsely marking that pid attached **against stale tools** — and the per-pid reconcile below (iterating `attached`) would already have skipped it (not yet attached). Bumping `generation` makes the existing fence **drop** that stale mark, so the pid stays unmarked; its **mark** self-heals on the next `ensure_attached` (re-register current reach + mark). *(A stale **tool** a late task left is add-only-invisible to `ensure_attached`; it's pruned at the **next rediscovery** — the bounded residual under Known limitations. Review P2: "next rediscovery", not "next ensure".)*
  - Compute the global **`changed`** name set: names present in both old (`state.modules`) and new with a **different module atom** (content-addressed redefinition — `ProxyGenerator` mints a new atom but keeps the `.name()` string; the name-keyed prune can't see an atom swap on its own).
  - For each live attached `{pid, template}` the Consumer **spawns a supervised reconcile task** (`Task.Supervisor.start_child`, mirroring `start_register_task` — **review P2: so a slow/dead agent never blocks the Consumer GenServer**; the GenServer only updates state + schedules, never `Jido.AI`-calls inline). Each task runs `reconcile_pid(pid, reach, changed)` with `reach = modules_for_template(new_mods, new_templates, template)` — **query-based and fully safe-wrapped** (`list_tools`/`unregister`/`register` each `try/rescue/catch :exit` + timeout): list the pid's `mcp_*` names, **unregister** `(current_mcp_names − reach_names) ∪ (changed ∩ current)` (prunes removed tools, narrowed allowlists, the atom-swap for `changed`, and a stale tool a late task left), then **register** `reach` (idempotent). Query-based (not an old/new diff) so it converges to the pid's *actual* tools.
    - **Failure semantics (review P3):** a failed `list_tools` **aborts** this pid's reconcile (return `:skip`, retried next tick) — **never treat current tools as empty**, which would silently skip pruning and falsely claim convergence. A failed `unregister`/`register` yields `:partial` (not `:ok`) and the pid is retried next tick; this is safe because `register`-by-name **skips** an already-present tool, so a failed prune of a `changed` name simply leaves the old module in place (no duplication, no half-update) until the retry. `reconcile_pid/3` returns `:ok` only when list succeeded *and* every unregister/register confirmed.
  - **Republish the policy only if `policy_changed?(new_policy, approval_policy())`** (a `:persistent_term.put` triggers a global GC — don't churn). `policy_changed?/2` is **`@doc false` public** so it's directly unit-testable without a `:persistent_term` seam (review P3).
  - Update `state.modules`/`state.module_templates`, set the bumped `generation`, clear `rediscover_ref`/`rediscover_pid`, **re-arm the timer**.
- **Separate DOWN clause for `rediscover_ref` (`%{rediscover_ref: ref}` match):** a re-discovery prep that hard-crashes must **not** disrupt the healthy `:ready` state — log, clear `rediscover_ref`/`rediscover_pid`, **re-arm the timer** (existing tools keep working).
- **New helpers:** `reconcile_pid/3` (the **supervised-task body** — query-based converge-to-reach, runs off the Consumer) + a safe `list_tools` wrapper + `unregister_names/2` + `safe_unregister/2` (mirror `register_modules`/`safe_register` — `try/rescue/catch :exit` + timeout around `Jido.AI.unregister_tool(pid, name)`); `policy_changed?/2` (**`@doc false` public**, for the direct unit test). Keep the unregister helpers structurally distinct from their register-side twins (clone check).

**Known limitations to document inline:** (1) the per-pid reconcile keys on `module.name()`; a same-name redefinition is handled via the `changed` set (unregister-then-register), and the orphaned old module atom lingers in the code server (BEAM doesn't unload it) — harmless, noted in `ProxyGenerator`'s moduledoc. (2) In the rare window where a fresh attach races a tool-*removing* rediscovery, a just-attaching pid may transiently carry the removed tool until the **next** rediscovery cycle reconciles it (it's now `attached`, so `reconcile_pid`'s query-based prune drops it); meanwhile the **proxy call fails** (the endpoint no longer serves that tool) — the real backstop, true regardless of approval config — and, while global MCP approval is enabled (the default `mcp_require_approval: true`), the tool's absence from the republished policy *also* leaves it **gated/fails-closed** (review); with global approval disabled, the proxy-call failure stands alone. Either way, no un-approved stale-tool *success*. (3) **Eventual consistency (review P2):** reconcile tasks run async, and attached pids stay marked `attached` throughout, so a turn landing in the brief window between a `{:rediscovered}` apply and its reconcile tasks finishing hits the `:already` fast path and uses the *prior* tool set for that one turn (a removed tool fails at the proxy — and is gated when global approval is on; an added tool appears the turn after). Acceptable for this deployment — the whole attach path is already eventually-consistent (fire-and-forget tasks + self-heal). Closing it would mean tracking `reconciling` pids (or transiently unmarking them so `ensure_attached` can't shortcut to `:already`), not worth the bookkeeping for a sub-second window.

**Config:** add `rediscovery_interval_ms` to the `config.exs` `:mcp` doc comment; `config/test.exs` sets it to `0` (drive `:rediscover` manually in tests for determinism).

**Tests:** re-discovery picks up an **added** tool (counter-stub returns `[ping]` then `[ping, pong]`); **removes** a vanished tool (`[ping, pong]` then `[ping]` → `unregister_tool` called, agent loses it); a **changed tool, same local name** (review P2 — stub returns `ping` with schema A then schema B; assert the `changed`-set path **unregisters then re-registers**, so the agent ends with the *new* proxy module, not the stale one `register_modules` would have skipped); a **server unreachable at boot then online** — the stub must make success **depend on** refresh (review P2): `list_tools` keeps returning `{:error, _}` until the stub's `refresh_endpoint` callback flips an Agent/ETS flag, after which it succeeds; assert the tool attaches *only* after `refresh_endpoint` ran (a stub that simply succeeds on the 2nd call would pass without ever proving the refresh path); allowlist reconcile (a tool the template can no longer reach is unregistered); **rediscovery during an in-flight attach** (review P2 — pin a register task mid-flight, apply a rediscovery that removes a tool; assert the stale `{:mark_attached, …, old_gen, …}` is **dropped** because `generation` was bumped (pid not in `attached`), the pid's **mark** self-heals on its next `ensure_attached` (current reach registered + marked), and the removed tool is pruned on the **next rediscovery** — *not* at `ensure_attached`, which is add-only); a **no-op tick** leaves the policy **value equal** (`approval_policy/0` unchanged) and spawns **no** reconcile tasks (assert via value-equality + unchanged tool sets, *not* "no `:persistent_term.put`" which isn't observable without a seam — review P3); plus a direct unit test of the **`@doc false` public** `policy_changed?/2`; a re-discovery prep **crash** — kill `state.rediscover_pid` (the new pid field) mid-attempt, assert the `rediscover_ref` DOWN clause leaves `:ready` + existing tools intact and re-arms; a **stale `{:rediscovered, ref, …}`** with a non-matching ref is ignored. Most drive `send(consumer, :rediscover)` directly (interval `0`); one uses a small interval to verify auto-arming. Update existing tests that assert `MapSet.member?(…attached…)` → `Map.has_key?`.

   - **Backoff re-prep:** note `prep_pid` is **`nil` once `:ready`** (review P3) — to observe the backoff you must catch it during boot `:preparing` (point at an unreachable/slow server so prep blocks), then `Process.exit(state.prep_pid, :kill)` and watch `reprep_attempts` climb and recover. (This staging is exactly what the blocking-stub tests automate, so the manual step is genuinely optional.)
