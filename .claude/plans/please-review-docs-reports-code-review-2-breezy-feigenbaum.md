# Fix M13 (HostShell output cap + opt-in ulimits) + L10 (read_file/edit_file size guard)

## Context

`docs/reports/code-review-2026-06-10.md` has been burned down to 5 open MEDIUMs and ~19 LOWs. The biggest remaining item is **M13** ("No CPU/memory limits on HostShell; unbounded output buffering"): a command run through the default forge backend can balloon BEAM memory with unbounded output — `OsCmd.collect/4` accumulates iodata with no cap, and truncation happens only downstream (10 KB tail at forge persistence, 32 KB head at the tools layer) on an already-materialized binary. Several forge paths (`HostShell.exec/3`, the `:infinity` timeout clause, all three no-timeout Docker branches) still bypass `OsCmd` entirely via raw `System.cmd`, so they get neither cap nor the H15 tree-kill. **L10** is the same unbounded-memory family: the `read_file` tool loads an entire file into the heap before applying `offset`/`limit` (writes are capped at 5 MB; reads are uncapped) — and `edit_file` has the identical shape (`Resolver.read` materializes the whole target before `replace_unique_match`), so it gets the same guard.

User decisions (confirmed): implement the ulimit half as **opt-in config, default off**; batch scope is **M13 + L10 (+ edit_file read guard)**. Greenfield — no compat constraints. Nothing gets committed; all changes stay unstaged. The batch is complete only when `mix precommit` passes.

## Key decisions

- **Cap locus**: `OsCmd.run/3` gains `:max_output_bytes`, **default-on** (H9 philosophy: a caller that forgets the option is safe). Config key `:os_cmd_max_output_bytes`, default `10_000_000` (matches `backend_host.ex`'s streaming cap; far above the 32 KB tool / 10 KB persistence caps so it only catches runaways).
- **`:infinity` is per-call only, never config**: app config accepts **positive integers only** (anything else — including `:infinity`, nil, non-positive — normalizes to the 10 MB default, with the `Allocate.payload_leaf_cap/0` why-comment). `max_output_bytes: :infinity` is honored solely as an explicit call-site option, so global config can never silently disable the safety default.
- **Overflow behavior**: keep the prefix of the overflowing chunk up to exactly the cap (`binary_part`), then `kill_tree` + discard post-kill drain → result is exactly cap-sized. Return `{output, :output_limit}`, mirroring the `:timeout` contract. (backend_host drops the whole overflowing chunk because it *streams*; OsCmd returns a binary, so a cap-sized prefix is the friendlier contract.)
- **Boundary mapping**: `:output_limit` → **exit code 153** (= 128 + SIGXFSZ, "file size limit exceeded"; 124 is taken by timeout) at the HostShell/Docker boundary. The constant lives once — `JidoClaw.Forge.Sandbox.output_limit_exit_status/0` on the facade, with `@spec output_limit_exit_status() :: 153` — no repeated magic numbers; each backend keeps its own one-line mapping clause using it. Verified: Behaviour specs (`exec` → `{String.t(), integer()}`; `exec_argv`/`run` → `{String.t(), integer() | :timeout}`) and every consumer (`claude_code.ex:84-88`, `codex.ex`, `shell.ex:14`, `workflow.ex:38`, `bootstrap.ex:22-24`, `harness.ex:475` opaque pass-through, `resource_provisioner.ex:155`) have `{output, code}` catch-alls — **zero downstream/spec changes needed**. Only `OsCmd.run/3`'s own `@spec` widens.
- **ulimit (opt-in, default off)**: `:forge_ulimit_cpu_seconds` (`ulimit -t`, portable) and `:forge_ulimit_virtual_memory_kb` (`ulimit -v`, enforced on Linux, documented no-op on macOS) — the finding's "CPU/memory limits". Skip `-f` (not in the finding; block-unit differs across shells). HostShell only — Docker's microVM has cgroups. `exec/3` keeps its current contract (`timeout: :infinity`, opts ignored) — **no** `:timeout` support added to it in this batch.
- **L10 cap**: read cap = write cap. Reuse `FilePayloadLimit.max_bytes/0` (5 MB) — no new config key. Two-layer guard in both `read_file` and `edit_file`: a **pre-read `File.stat`** guard for locally-resolvable paths (the actual heap protection — avoids materializing at all), plus an **unconditional post-read `byte_size`** guard on every branch (closes the stat→read race and gives remote/VFS branches uniform behavior; for remote schemes the bytes are materialized before the check — documented residual, bounding the fetch needs backend streaming). Cap errors use the structured `JidoClaw.Error.validation_error/2` idiom `edit_file` already uses, not plain strings.

## Implementation steps

### 1. `lib/jido_claw/core/os_cmd.ex` — output cap

- `@default_max_output_bytes 10_000_000`. **Two distinct normalizers — keep them separate**: (a) **config-level** `configured_max_output_bytes/0` reading `:os_cmd_max_output_bytes` app env, honoring **positive integers only** — rejects `:infinity`/nil/non-positive → hardcoded default (`Allocate`-pattern comment); expose **this one** `@doc false` so the invalid-config fallback (incl. `:infinity`-in-config) is unit-testable without generating >10 MB of output. (b) **option-level** normalize for the per-call `:max_output_bytes` opt, accepting positive int or `:infinity`; anything else → `configured_max_output_bytes()` — stays private, tested through `run/3` behavior. Don't conflate them: config must reject `:infinity`, the option must accept it.
- `run/3`: `max_bytes = normalize_option(Keyword.get(opts, :max_output_bytes, configured_max_output_bytes()))`; thread `bytes_so_far` + `max_bytes` through `collect` (6 args, private). **Handle `:infinity` with an explicit function clause / pattern match in the cap check, not term-order comparisons** (`new_total <= :infinity` would "work" by term ordering but is opaque and dialyzer-unfriendly) — e.g. a `within_cap?(:infinity, _)` head returning true, integer head doing the arithmetic. While here, switch accumulation from the improper `[acc | chunk]` to proper iodata `[acc, chunk]` (in `collect` and `drain_after_kill`) — same semantics, less surprising while adding byte accounting.
- On `{:data, chunk}` over cap: append `binary_part(chunk, 0, max_bytes - bytes_so_far)`, transition to new `output_limit/3` terminal that **mirrors `timeout/3` (os_cmd.ex:144-157) including its nil-`os_pid` safety branch** (`is_integer(os_pid)` → `kill_tree` + drain; else just `close_port` — a missing/closed port pid must not crash the cap path): on the kill branch, new `drain_after_kill_discard/1` consumes-and-drops port messages until `exit_status` or the 1 s cap, **explicitly `close_port`-ing on the timeout branch exactly as `drain_after_kill/2` does** (no port left around if the exit status never arrives; mailbox hygiene without growing `acc` — comment the asymmetry vs the timeout path's accumulating drain), then `flush_port`, return `{IO.iodata_to_binary(acc), :output_limit}`. Deadline check stays first (chunk tripping both → `:timeout` wins).
- Widen `@spec run/3 :: {binary(), integer() | :timeout | :output_limit}`; document the option + overflow semantics + per-call-only `:infinity` in `@doc`/moduledoc.

### 2. `lib/jido_claw/forge/sandbox.ex` — shared constant

- Add `@spec output_limit_exit_status() :: 153` / `def output_limit_exit_status, do: 153` on the `JidoClaw.Forge.Sandbox` facade (with a one-line doc: boundary mapping for `OsCmd`'s `:output_limit`; 128 + SIGXFSZ). Used by both backends and their tests (runtime call from backends to the facade — no compile cycle, both in `forge/` so reach-arch-clean).

### 3. `lib/jido_claw/forge/runner/host_shell.ex` — all paths through OsCmd + 153 mapping + ulimit wrapper

- `exec/3` (line 67-84, **the default consolidator path**): resolve the shell via a `shell_path/0` helper — `System.find_executable("sh") || ("/bin/sh" when executable)` (robust to weird PATH environments; nil → `{"sh: command not found", 127}`) — then `OsCmd.run(sh, ["-c", ulimit_prelude() <> command], cd:, env:, timeout: :infinity)`; map `{output, :output_limit} -> {output, Sandbox.output_limit_exit_status()}`, pass `{output, status}` through. Keep the existing `rescue e -> {Exception.message(e), 1}` (file-level `# reach:disable-for-this-file bare_rescue` covers it). Contract unchanged: always `{String.t(), integer()}`.
- `run_with_timeout/5` (lines 128-144): collapse both clauses into one `OsCmd.run(exec2, args2, cd:, env:, timeout: timeout)` (OsCmd accepts `:infinity`), where `{exec2, args2} = apply_ulimits(executable, args)`. Mappings: `{_partial, :timeout} -> {"", :timeout}` (unchanged), `{output, :output_limit} -> {output, 153-const}` (partial output preserved — deliberate, more debuggable), `{output, status}` pass-through. Keep the rescue.
- Ulimit helpers (default-off):
  - `ulimit_prelude/0`: `""` unless at least one of the two config keys is a positive integer (only validated integers are interpolated); else e.g. `"ulimit -t 600 2>/dev/null || true; ulimit -v 2097152 2>/dev/null || true; "` (best-effort: a rejected limit must not abort the command).
  - `apply_ulimits(executable, args)`: prelude `""` → `{executable, args}` (byte-identical default path). Otherwise `{sh, ["-c", prelude <> ~S(exec "$0" "$@"), executable | args]}` — `$0`/`$@` keeps argv out of the shell string (no escaping); `exec` replaces the sh so rlimits inherit; `kill_tree` walks grandchildren regardless. Shell resolved via the same `shell_path/0` helper; missing → direct exec fallback. Mark `@doc false` if tested directly, else test through `exec_argv` behavior.

### 4. `lib/jido_claw/forge/sandbox/docker.ex` — funnel no-timeout branches + 153 mapping + finder seam

- `exec/3` (~137), `exec_argv/4` (~154), `run/4` (~172): replace `if timeout do exec_with_timeout(...) else System.cmd("sbx", ...) end` with `exec_with_timeout(args, timeout || :infinity)` — removes the three raw `System.cmd` sites; all six paths get the missing-`sbx` → `{"sbx: command not found", 127}` guard (previously the no-timeout branches **raised** `:enoent`), the cap, and tree-kill. stderr merge preserved (OsCmd hardcodes `:stderr_to_stdout`).
- `exec_with_timeout/2` (~313-331): add `{partial, :output_limit} -> {"output limit exceeded after #{byte_size(partial)} bytes", 153-const}` alongside the `124` timeout clause (Docker discards partial output in both sentinel branches — consistent with its existing style).
- **Injectable `sbx` finder seam** (the repo's app-env seam idiom, cf. `:compaction_storage`/`:task_supervisor`): `exec_with_timeout` resolves via `sbx_finder()` → use the `:sbx_finder` app-env value **only `when is_function(fun, 1)`**, else fall back to `&System.find_executable/1` (bad config can't crash the exec path). Lets tests force the missing-`sbx` branch deterministically on machines that have `sbx` installed.
- Do **not** touch `create_sandbox`/`destroy` (bounded admin calls) or `spawn` (raw-port streaming contract).

### 5. `lib/jido_claw/tools/read_file.ex` + `lib/jido_claw/tools/edit_file.ex` — L10 guards

Same two-layer pattern in both tools, before/around their `Resolver.read` call (read_file.ex:53, edit_file.ex `edit_with_context`):
- **Pre-read**: `Resolver.local_path(path, opts, :read)` (verify exact signature/branch coverage at resolver.ex:256-262 during implementation); on `{:ok, local}` → `File.stat(local)`; `size > FilePayloadLimit.max_bytes()` → structured error via `Error.validation_error("path is N bytes, exceeds the M-byte read cap; use run_command (e.g. sed -n 'START,ENDp') for large files", details: %{path:, size:, max_bytes:})` (match edit_file's existing `Error.*` idiom). Stat errors fall through to the normal read (the read surfaces the real error).
- **Post-read (unconditional, all branches)**: after `Resolver.read` returns `{:ok, content}`, guard `byte_size(content) > FilePayloadLimit.max_bytes()` with the same error **before** `String.split`/`count_occurrences` — closes the stat→read race on local files and covers VFS/`github://`/`s3://` uniformly (materialize-before-check residual documented for remote).
- **edit_file only — validate the final `new_content` too**: after `replace_unique_match` builds the replacement, run `FilePayloadLimit.validate(:content, new_content)` before writing — and **wrap its plain-string `{:error, msg}` into `Error.validation_error(msg, details: %{...})`** so the cap errors stay structured end-to-end (or add a structured-returning sibling helper on `FilePayloadLimit`; either way, no bare-string errors from this path). Without it the write-cap invariant leaks: a ≤5 MB file plus a ≤5 MB `new_string` can produce a ~10 MB file (replacements can also multiply via multiple-occurrence semantics — check what `count_occurrences == 1` enforces; the single-occurrence rule bounds it to one insertion, but guard anyway so the invariant holds independent of that rule).
- Extract the shared guard into a small private helper per file or a function on `FilePayloadLimit` (e.g. `validate_read/2` beside `validate/2`) — implementer's pick; prefer the `FilePayloadLimit` home since both tools use it.
