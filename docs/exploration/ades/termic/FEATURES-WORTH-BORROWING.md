## Determination (TL;DR)

**Nothing to adopt as a dependency — the AGPL decides that before the architecture does (and it's a WKWebView desktop binary with no OTP seam anyway). The haul is real but lands somewhere the scan didn't point: half of it is security doctrine for Forge, not cockpit UX for argus.** The scan flagged three donors; they deliver, but with reframes. (1) The turn-completion engine is real and the most engineered of the set — but its load-bearing trick is that **the agent CLIs already broadcast their turn state over public terminal sequences when the host terminal claims capability** (termic spoofs `TERM_PROGRAM=iTerm.app` precisely to unlock Claude Code's OSC 9/9;4/133 emission). That inverts cleanly for us: our REPL knows its own state authoritatively and can *emit* the same protocol for ~a hundred lines, making every cockpit — iTerm badges, tmux, termic itself — track JidoClaw for free (TM1-1, this doc's do-today item). The consume side stays a parked reference: Forge's runners are one-shot print-mode invocations detected by exit + JSON parse, so terminal-signal detection has no consumer here until an interactive harness exists (TM2-1). (2) Spotlight is genuinely novel — the only new worktree UX idea across the whole ades set — and its guardrail set (no-commit detached HEAD, clean-root precondition, crash detection, full restore with an untracked ledger) is the spec for argus's "preview this worktree at the repo root" story (TM1-3). (3) Review-comment batching is convergent with emdash's, contributing the quote-as-anchor idea and serialization details as garnish (TM3-1). The unflagged find: **the sandbox's trust rules** — the login-shell rc-delta withheld from caged spawns, cage-gating config read from outside the agent's write reach, per-agent credential-dir isolation, and a monitor/shadow mode — which map 1:1 onto Forge and onto the tracked crabbox CB1-1 concern (TM1-2, TM2-3). Plus one shipped-decision validation: their Docker-sandbox plan independently investigated and **rejected** OAuth-token brokering in favor of mounted credential dirs — the same conclusion as our Forge OAuth file-sync decision. Headline negative finding, completing the set: **no edit-step-output-and-resume, verified with grep evidence** — argus §5 is now confirmed novel across all three desktop comparables.

## Tier 1 — load-bearing for a named decision

### TM1-1. Emit the work-done protocol from our own CLI surfaces

**Recommendation**: INDEPENDENT — surfaced by this dig, valuable with or without argus; the do-today item (the third across the ades digs, after traycer TR1-2a and emdash EM2-3).

**Where in termic** (as the *consumer* that proves the protocol): the spawn env claims iTerm2 — `TERM=xterm-256color`, `TERM_PROGRAM=iTerm.app`, `TERM_PROGRAM_VERSION=3.5.0` — with an in-code rationale that agent CLIs **gate their "fancy" OSC emission on a known host** (`lib.rs:1011-1024`; the comment names Claude Code's OSC 9 / OSC 9;4 / OSC 133 / OSC 1337 specifically). The consumption ladder (`TerminalPane.tsx:591-620`, handlers `:891-996`): OSC 9 plain = notification text, OSC 9;4 = ConEmu progress (state 1/2/3/4 busy, 0 idle — "reliable busy/idle edge from Claude Code"), OSC 133;C/D = FinalTerm command running/ended, OSC 1337 `RequestAttention`, OSC 0/2 title strings (Claude's `✳` brand glyph = idle; spinner glyph = busy, `:809-837`). Everything below the ladder is heuristic fallback for CLIs that emit nothing.

**What**: The agent CLIs we care about already *broadcast* turn state over vendor-documented terminal sequences — the cockpit ecosystem (termic, iTerm badges, tmux hooks, ConEmu taskbar) is the installed consumer base. A CLI that emits them is trackable by every one of those surfaces with zero integration work on either side.

**Gap in jido_radclaw** (verified 2026-07-03): we emit none of it. Greps for OSC-progress/`9;4`/title emission across `lib/` are clean (seams pass §7); the only ANSI/OSC code we have is `Security.Redaction.Ansi.strip/1`, which *destroys* inbound sequences for redaction reassembly and parses nothing (`security/redaction/ansi.ex:19-21,30-35`). The REPL writes plain text; a long agent turn, a pending tool-approval gate, and an idle prompt all look identical to the terminal hosting it. Meanwhile our attention surfaces are pull-only (dashboard/CLI counts + `/approvals`; seams §6) — an operator in iTerm or tmux has nothing that pings them.

**Why it matters**: This is the single-operator-many-surfaces problem — our exact life — solved at the cheapest possible layer. The REPL knows its own state *authoritatively* (no detection needed; we are the well-behaved CLI termic wishes `agy`/`grok` were), and emitting makes gate-pending and turn-done visible in whatever hosts the terminal: iTerm's tab badge and dock bounce, tmux window flags, a termic-class cockpit if one is ever pointed at us. It also future-proofs the Forge story: if Forge ever hosts *our* CLI as a sub-agent, the harness gets structured turn signals for free. License-safe by construction — the sequences are public protocol (ConEmu's OSC 9;4, FinalTerm's OSC 133, iTerm2's OSC 1337, xterm's OSC 0/2); we implement from the protocol docs, not termic's code.

**Adoption sketch**: a small `JidoClaw.CLI.TerminalSignals` module, called from the REPL turn loop: (a) capability probe once at boot — emit unless `TERM` is dumb/absent; honor a `config :jido_claw, :terminal_signals, false` kill-switch (mirror: termic's per-agent `work_done` toggle); (b) turn start → OSC 9;4 state 3 (indeterminate); turn end → state 0 + an idle-marked title (`OSC 0; ✳ jidoclaw · <session-label>`); error → state 2; (c) the real payoff: **tool-approval gate opened for this session → OSC 9 notification** (`approval needed: <tool>`) + OSC 9;4 state 4 (warning) — wire it where the REPL learns of `approval_pending`, and clear on decision. Keep it REPL-only first (headless/print modes stay silent — they're piped; see OQ-1). Sequences behind one emit function that no-ops when the probe failed, so tests never see escape bytes.

### TM1-2. The cage trust rules: rc-delta withholding, config outside the cage, per-agent credential dirs

**Recommendation**: BORROW-PATTERN (three rules) — Forge/security territory, threat-model center. Read before the next change to Forge spawn env or to how policy config is resolved.

**Where in termic**: (a) **The login-shell env delta is withheld from caged spawns.** `pty_spawn` resolves the user's login-shell env once (`$SHELL -ilc env`, cached), always applies the resolved `PATH`, but injects the *delta* (EDITOR/LANG/tokens/exported secrets from rc files) **only when no sandbox is active** (`lib.rs:966-1024`, the gate at `:989-993`), with the explicit rationale that the rc delta can carry `GITHUB_TOKEN`-class secrets the seatbelt/proxy don't filter; it also deliberately drops `VIRTUAL_ENV`/`CONDA_*` so one startup-time venv doesn't freeze onto every workspace (`shell_env.rs:232-240`). (b) **Config that gates the cage lives outside the cage's write reach**: `.termic.yaml` (which carries sandbox allowlists) is read and written **only at the project's root checkout, never a worktree**, "so a caged agent can't edit the config gating its own sandbox" (`repo_config.rs:8-12`; `lib.rs:814-819`). (c) **Per-agent credential-dir isolation**: each registry agent's `sandbox_allowed_paths` lists only *its own* state dirs, so a claude cage cannot read the codex/gemini OAuth stores (`lib.rs:6445-6459`). One anti-pattern to note alongside: sandbox provisioning failure **fails open** — the spawn proceeds unsandboxed with a warning flag (`lib.rs:950-953`) — the opposite of our fail-closed doctrine; take the rules, not that posture.

**What**: Three crisp allocations of trust for host-executed agent CLIs: the shell-rc environment is a secret channel distinct from PATH resolution; policy config is only as trustworthy as the least-trusted writer of its location; credentials are scoped per-agent, not per-machine.

**Gap in jido_radclaw** (verified 2026-07-03): (a) Our strongest analog is MCP-scoped: `Env.scrubbed_port_env/1` builds default-deny env for MCP stdio subprocesses (AGENTS.md, the stdio trust-boundary patch). But the Forge **HostShell default backend runs claude/codex directly on the host, unsandboxed** (`forge/backends/host_shell.ex:30-34` — "commands run as the current OS user"), and this dig did not audit what env its `OsCmd` ports inherit — that audit is the sketch's first step. (b) `.jido/config.yaml` lives in the workspace the agent operates in; crabbox **CB1-1** already tracks the sharpest instance (an LLM editing config can redirect a host-env credential destination) — termic's rule is the *mitigation shape* CB1-1 lacked: resolve gate-relevant config (tool-approval require-list, `mcp_servers`, future egress lists) from a location the agent's tools can't write, e.g. committed HEAD or a host-side copy. (c) Forge runner config-sync is already per-runner in direction — claude_code syncs `~/.claude`, codex syncs `~/.codex` (`runners/claude_code.ex:222-223`, `runners/codex.ex:331-332`) — but nothing *states* the isolation rule, and the docker backend's mount policy should inherit it explicitly.

**Why it matters**: All three rules sit at the exact center of the house threat model (LLM-misbehavior containment + leakage hygiene). (a) is the subtlest: PATH resolution *requires* running the login shell, which tempts passing the whole resulting env along — termic shows the disciplined split. (b) closes a live tracked concern. (c) costs one sentence of doctrine now and prevents a cross-vendor credential bleed the first time two runners share a sandbox home.

**Adoption sketch**: (a) audit the Forge HostShell/Docker spawn env (`OsCmd`'s `{:env, _}` builders); adopt the rule "resolved PATH yes, rc-delta no" for any host-exec of an agent CLI — likely by routing Forge spawns through the same `Env` scrubbing posture MCP stdio already uses. (b) fold into CB1-1's fix: gate-relevant config keys resolve from committed HEAD (`git show HEAD:.jido/config.yaml`, the traycer TR2-2 preview-at-ref trick) or from a tenant-level store, with the working-tree copy demoted to non-security keys. (c) write the per-runner credential-scope rule into the Forge backend docs and assert it in the docker backend's mount builder when that path next changes. (Connective note, 2026-07-03: the Xantham dig, later the same day, is the live demonstration of what violating rule (b) costs — its approval ledger is a plain file inside the gated agent's own write reach, self-approval is an `echo` one-liner, and its own SECURITY.md names the symlink/TOCTOU consequences; [XA1-1](../Xantham-system-blueprint/FEATURES-WORTH-BORROWING.md).) (Cross-corpus note, 2026-07-05: the pms digs added spawn-boundary riders — on rule (a), multica scrubs nested-session env by **exact name**, deliberately not the whole `CLAUDE_CODE_*` namespace ([MC2-4](../../pms/multica/FEATURES-WORTH-BORROWING.md)), and orca contributes the non-interactive subprocess env baseline (`CI=true`, `GIT_TERMINAL_PROMPT=0`, caller wins) queued as a do-now ([OR3-1](../../pms/orca/FEATURES-WORTH-BORROWING.md), [OR-FIRST-WAVE](../../pms/orca/OR-FIRST-WAVE.md) item 2); on rule (c), myrlin's credential lineage guard is the multi-machine sequel — cross-machine OAuth refresh-token theft found and fixed at the file layer, with rotation write-back and three-state token health ([MY1-1](../../pms/myrlin-workbook/FEATURES-WORTH-BORROWING.md)).)

### TM1-3. Spotlight: the preview-a-worktree-at-the-repo-root pattern

**Recommendation**: BORROW-PATTERN — the scan's hoped-for novel worktree UX, confirmed. Absorb at argus step 1+ (whenever the argus UI grows a "preview/run this worktree locally" story); gated on EM2-3 landing first.

**Where in termic**: `lib.rs:5120-5598` (tests `:7697-7910`). Mechanism: **apply** = capture the worktree's HEAD, `git checkout --detach --force <wt_head>` at the repo root (the branch ref never moves — proven by test assertion "main branch ref must not move", `:7792`), pipe the worktree's `git diff --binary HEAD` into `git apply` at the root (no `--3way` — clean by construction since root HEAD now equals worktree HEAD), then copy untracked files (`git ls-files --others --exclude-standard -z`, honoring .gitignore, each path traversal-guarded, `:5277-5292`) recording every copied path in an **`applied_untracked` ledger**. **Revert** = `git checkout --force <original_ref>` + delete exactly the ledgered untracked files (`:5305-5322`). Change detection is a 1.5s poll comparing a state hash (`rev-parse HEAD` + `status --porcelain`, `:5169-5183`); each change tick reverts then re-applies. The guardrails: per-project opt-in, default off (`lib.rs:106-110`); refuse repo-root and multi-repo workspaces; **one spotlighted workspace per project**; **refuse to start from a detached HEAD** — with a message telling the operator a previous session likely crashed and how to heal (`:5411-5417`); **require a clean root** (`:5419-5423`); stop hooks on archive and on app exit revert *every* active session so no repo is left detached (`:7288-7307`). While spotlighted, the project's run script executes at the repo root and is SIGTERM'd on stop/switch so a stale dev server never serves the old target (`:5664-5675`, `:5328-5334`). Known sharp edges (from the code): a brief per-tick window where the root shows reverted state (revert-then-reapply), `git apply` failures leave the root reverted until the next good tick, and a crash leaves a detached HEAD healed manually. Plus the drift finding: UI copy claims a "checkpoint commit" that doesn't exist (`RepositorySection.tsx:525`).

**What**: A worktree preview that is *safer than committing*: the operator's branch is never touched, everything applied is either git-tracked state (restored by one checkout) or ledgered untracked copies (removed by name), and every precondition failure names its own recovery.

**Gap in jido_radclaw** (verified 2026-07-03): no worktree machinery at all (argus OVERVIEW appendix A.2; seams pass re-confirmed — the only `worktree` token in `lib/` is the `git config --worktree` scope *flag* in the analyzer's bool-opts table, `security/shell_command/git.ex:150-153`, **not** the subcommand). Sharper: the git ops Spotlight runs — `worktree add`, `checkout --detach`, `reset` — currently pass the shell analyzer as **benign** (only `commit`/`push` mint gating effects, `git.ex:211-215`; gating would need new facts in `classify_candidate/6`, new effects beside `commit_effect`/`push_effect` at `shell_command.ex:637-640`, and a fold into `git_gating_effect?/1` at `:479-482`). That is emdash **EM2-3**, still unshipped — it is the prerequisite for any of this.

**Why it matters**: Argus §3 models worktrees but has no preview story — and the first time the operator wants to *run* a worktree's state against their editor/dev-server/browser, the naive answers (merge it, or cd into the pool dir) are respectively destructive and workflow-breaking. Spotlight is the worked answer, and its guardrail set is exactly the part that took 54 releases to harden. Our version is also better-placed: preview is inherently a single-node op (the checkout and the operator's editor share a machine), which the argus `worktree.node` affinity already models.

**Adoption sketch**: a `Worktree.spotlight_start/stop` action pair executing on the owning node, after EM2-3 lands: (1) preconditions as typed refusals — clean root, attached HEAD (with the crash-recovery message), one-per-project (a lock row or the existing lease idiom); (2) apply/revert exactly their plumbing shape, with the untracked ledger persisted (a `ToolOutput` ref or a column on the Worktree row) so revert survives a node restart — their in-memory ledger is the one piece our durability substrate improves; (3) drive re-sync from our own signals where the writer is a JidoClaw agent (tool-execution events on that workspace) with their cheap state-hash poll as the fallback for external edits; (4) surface sync passes on the `worktrees:project:<id>` PubSub topic argus §4.2 already plans (their live per-pass file log is the UX to mirror); (5) app/node shutdown hook reverts all active spotlights (their `:7288-7307`). Skip the run-script handoff initially — our run story belongs to Forge sessions, not a bespoke runner. (Cross-corpus note, 2026-07-05: orca's review-surface pack includes a read-only per-worktree preview server its dig records as the second, smaller reference beside this entry for the preview-worktree story; [OR3-3](../../pms/orca/FEATURES-WORTH-BORROWING.md).)

## Tier 2 — absorb at a specific step, or parked on a named trigger

### TM2-1. The turn-completion detection engine (consume side)

**Recommendation**: BORROW-REFERENCE, parked. **Named trigger**: Forge grows an interactive/PTY harness — i.e. the first runner whose completion cannot be read from exit-plus-structured-output (the dead scaffolding is the slot: `Runner.handle_output/3` optional callback with zero implementors, `forge/runner.ex:28,33`; `Sandbox.spawn/4` delegated but caller-less, `forge/sandbox.ex:20-21`) — or a cockpit feature over CLIs whose events we can't parse. Next-ten #7 PR-4 (`needs_input` → gate-case mapping) is the adjacent queue item; coordinate if both fire.

**Where in termic**: the priority ladder (`TerminalPane.tsx:591-620`): explicit signals (OSC 9 / 777 / 9;4 / 133 / 1337, then per-CLI title classification) outrank heuristics; **when the most recent sender signal says "busy", every timing heuristic is suppressed** (`senderStateRef`, `:142,868` — the single design idea that makes the rest reliable); heuristics fire only below it — byte-quiet 4s, scrollback-stability 3×3s, viewport content-hash 2×3s, a 90s soft and 10-minute absolute ceiling (constants table at `:46-47,654,1644-1734`). False-positive kit: a **pre-submit viewport hash baseline** so "done" can't fire if the agent never actually responded (`:200-207`), one-done-per-submit token (`:207,226-230`), sticky done (agent signals can't un-done; only user input/focus can — `app.ts:1423`), startup-animation gate. The honesty rule worth quoting: for signal-silent CLIs, fallback completion badges as **attention (bell), not done** — "finished and waiting for input cannot be told apart" (`:1664-1669`; CHANGELOG:473). Per-CLI classifier covers only claude (`✳` = idle, other leading glyph = busy) and codex (`Waiting|Action Required` → attention; `Ready` → idle; `Working|Thinking`/Braille frames → busy) (`:809-837`).

**What**: A fusion contract for inferring turn state from a terminal you don't control: signals are authoritative and suppress heuristics; heuristics degrade honestly (unknown ⇒ attention, never silent-done); everything is bounded by ceilings.

**Gap in jido_radclaw** (verified 2026-07-03): deliberately none *today* — the seams pass confirmed Forge detection is exit-code + post-hoc buffered JSON parse (claude: the `{"type":"result"}` object from `claude -p --output-format stream-json`, `runners/claude_code.ex:84-88,115-149`; codex: `turn.completed`/`turn.failed` JSONL from `codex exec --json`, `runners/codex.ex:126-131,176-213`), `:needs_input` is structurally unreachable for both (only the Workflow runner emits it), and no PTY exists anywhere in the tree. Terminal-signal detection currently has **no consumer** — which is why this is parked, not skipped.

**Why it matters / when it fires**: the moment we host a CLI *interactively* (session continuity, TUI-mode agents, or cockpit-ing a third-party CLI), we inherit exactly termic's problem, and this ladder — with the sender-busy gate and the honest-degradation rule — is the best-engineered worked answer in the corpus. Two prerequisites their code teaches: the process must run under a **PTY** and the env must **claim a capable terminal** (`TERM_PROGRAM=iTerm.app`, `lib.rs:1011-1024`), or the rich signals simply never flow — our pipe-based `OsCmd` ports would receive nothing (OQ-2). **AGPL note**: reimplement from the contract described here and the underlying protocol docs; never port their TS. (Connective note, 2026-07-03: when the trigger fires, classify *into* the muxara MX1-1 single-agent contract — dug later the same day — rather than minting a new enum; muxara OQ-2 also refines this doc's fail-toward-attention rule by splitting `unknown` into agent-shaped (alarming) and foreign (boring); [muxara MX1-1](../muxara/FEATURES-WORTH-BORROWING.md).)

### TM2-2. The CLI-native session-resume ladder

**Recommendation**: BORROW-REFERENCE, parked. **Named trigger**: Forge wants CLI-native session continuity (across iterations, restarts, or into a Docker cage) instead of — or alongside — the shipped transcript persist-then-resume pair (agentos borrow).

**Where in termic**: `decideResume` (pure, `src/lib/agents.ts:318-367`) picks per-tab: explicit override → **resume-id** (`--resume {storedUuid}`) → **mint** (`--session-id {freshUuid}`, stored per-(workspace, tab), `lib.rs:264,348-369`) → **cwd-resume** (`--continue` / `codex resume --last`; worktree + primary tab only, so it can't lasso the user's unrelated same-cwd sessions) → fresh. Failure honesty: a resume attempt that exits within 2s is treated as *failed resume* — `has_resumable_history` flips false and the retry starts fresh instead of looping (`TerminalPane.tsx:169`; `lib.rs:256,3415`). For CLIs that mint sessions lazily, a `post_launch_capture` shell probe harvests the id after first exit (opencode: `session list | grep -m1 '^ses_'`, `lib.rs:6648-6670`). **Gap in jido_radclaw** (verified 2026-07-03): Forge runners are deliberately **stateless per iteration** — `claude -p` one-shots and `codex exec --ephemeral` (`runners/claude_code.ex:54-89`, `runners/codex.ex:89-132`); continuity lives in *our* transcript, not the CLI's session store. **Why it matters**: If Forge ever wants warm-context iterations (cheaper than re-priming from transcript) or resumable interactive sessions, this ladder is the complete contract: strategy precedence, per-surface id scoping, rapid-exit failure detection, lazy-mint capture, cage-awareness. ### TM2-3. Monitor mode: shadow-run a containment policy before enforcing it

**Recommendation**: BORROW-PATTERN (small) — Forge/security territory; absorb the next time an egress or destination policy is added or tightened.

**Where in termic**: `SandboxMode` is not a boolean: `Off | Monitor | Enforce | EnforceFs` (`lib.rs:202-213`). **Monitor** allows everything but logs every file op and network request with a computed `would_block` flag (`compute_monitor_policy`, `sandbox.rs:392`; the recent-denies panel reads the same feed), so the operator tightens the allowlist against evidence before flipping to Enforce. `EnforceFs` is the half-step the other direction — full filesystem cage, network open — for setups whose egress is controlled elsewhere (CHANGELOG 0.15.9).

**Gap in jido_radclaw** (verified 2026-07-03): every containment surface we run is binary: tool-approval `enabled?` on/off, the browse_web destination-policy gate, Forge backend egress config, the loop guard. Nothing anywhere evaluates-and-logs without enforcing; tightening a live policy on a personal system means eating the friction immediately or not shipping it.

**Why it matters**: Shadow mode converts "would this break my workflow?" from an incident into a log query — highest-value exactly where our threat model wants new floors (egress allowlists for Forge, future worktree-mutation gating per EM2-3) but the operator is also the only user. It slots into machinery we already have: the `:guardrail` Trace channel (loop guard is its first producer) is the natural sink.

**Adoption sketch**: a `mode: :monitor | :enforce` option on the next policy shipped (candidate: the EM2-3 worktree-mutation gate, or the first Forge egress floor): monitor ⇒ evaluate, emit a `:guardrail` Trace event + counter with `would_block: true`, allow. Flip to enforce after a quiet observation window. One clause per gate, not a framework. (Connective note, 2026-07-03: the same-day Xantham dig added two more first-consumer candidates — the XA2-2 hard-block tier, whose effect-class list wants shadowing before it becomes unappealable, and the XA2-1 approval TTL; [Xantham Tier 2](../Xantham-system-blueprint/FEATURES-WORTH-BORROWING.md).)

### TM2-4. Worktree contract deltas — the third datapoint (FOLD-IN to traycer TR1-3 / emdash EM1-1)

**Recommendation**: FOLD-IN — read alongside the two sibling references when argus step 1 models `Worktree`; termic mostly *confirms* them, with four deltas and two cautionary negatives.

**Where in termic / what it adds**: (a) **Carryover, the third philosophy**: `files_to_copy` defaults to `.env*`, `.venv`, `node_modules` and copies **recursively, wholesale** — including dependency trees, to skip installs entirely (`lib.rs:1284-1288,891-898,4908-4924`; resolution: project override else committed `.termic.yaml`). Contrast emdash's untracked-only + three safety rules (EM1-1). The synthesis for our `.jido/environment.yaml` `preserve:` design: support both classes — env-file carryover keeps emdash's tracked-file-never-forks probe; heavy-dir carryover (their insight — the *time* sink is `node_modules`, not `.env`) is fine without it since those dirs are ignored by definition, but keep the containment checks on both. (b) **`git branch --no-track` at create**, so a later branch delete can't offer to delete a shared *remote* branch (`lib.rs:1978-1986`) — a one-flag foot-gun eliminator neither sibling records. (c) **Import-existing-worktree** as a first-class adopt path (list via `git worktree list --porcelain`, filter, adopt without add/copy/setup — `lib.rs:1757-1900`): third independent convergence on traycer's `origin: :imported`. (d) **git-crypt bridging** (key-dir symlink into the per-worktree gitdir + `--no-checkout` then reset to run the smudge filter, `lib.rs:1987-2066`): a checklist item for repos with secret smudge filters. The negatives, both vindicating sibling entries: **no git-op serialization at all** (the `git()` helper has no lock; concurrent creates or a spotlight tick racing a create are possible — `lib.rs:683-701`) → emdash's serialize-per-repo GenServer advice stands; **archive has no busy/dirty guard** (`git worktree remove --force` + SIGTERM everything behind a confirm dialog, `lib.rs:3459-3630`) → traycer TR2-1's guarded deletion and our EM2-3 gate are the correction, not the exception. One forward-looking crumb from their Docker plan: a worktree's `.git` pointer file carries an **absolute** gitdir path, so container-mounting a worktree requires mounting at the matching path (+ `safe.directory '*'`) — validated in their spike (`docs/plans/docker-sandbox/findings.md:46-57`); load-bearing if Forge ever mounts host worktrees.

**Gap in jido_radclaw** (verified 2026-07-03): unchanged from the sibling digs — no worktree functionality (`git.ex:150` is a config-scope flag, not the subcommand); EM2-3 still unshipped.

### TM3-1. Quote-anchored review comments and their serialization (rider on emdash EM3-1)

**Recommendation**: BORROW-RUBRIC. termic anchors an inline comment by `{file, line-range, verbatim quoted snippet}` — the quote is the deliberate drift-proof anchor ("line numbers drift but the quoted snippet stays greppable", `reviewComments.ts:8-11,15-31`) — where emdash pins `{baseOid, headOid}`. ### TM3-2. Fingerprint-tied "viewed" marks (rider on emdash EM2-1)

**Recommendation**: BORROW-RUBRIC (one idea). "Mark as viewed" stores the file's `mtime:len` fingerprint at tick time; the mark counts only while the stored fingerprint equals the current one, so any edit **auto-un-views** the file — no watcher, no event (`fileViewed.ts:10-16,81-83`; fp at `lib.rs:4167-4180`). For the argus seen-flag (EM2-1's `viewed_at` sketch): bind "seen" to a content version, not a timestamp — for us, naturally, the run's event seq or the case's updated_at: *seen-at-seq N* self-expires when the thing moves. Cheaper and more honest than read/unread booleans.

### TM3-3. Editor-engine datapoint: CodeMirror over Monaco in WebKit (rider on argus §5.3 / emdash EM3-2)

**Recommendation**: BORROW-RUBRIC (a decision input, not a decision). termic's architecture doc pins "do NOT swap to Monaco — verified slower in WKWebView" (CLAUDE.md:7), and its diff surface is CodeMirror 6 `@codemirror/merge` in both side-by-side and unified modes (`DiffPane.tsx:15,259-287`).
