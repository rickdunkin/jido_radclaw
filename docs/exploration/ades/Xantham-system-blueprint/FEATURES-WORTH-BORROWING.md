## Determination (TL;DR)

**The scan's "contrast only" verdict holds architecturally — and the dig still pays.** Every mechanism is a coarser, file-based, single-session, model-trusting version of something we run durably (approvals → `AgentCase`; audit → `Audit.Event`/`WorkflowEvent`; watchdogs → OTP + leases; memory → the Memory subsystem; council → the composer judge panel). Nothing adopts as a dependency; there is no code to lift — the wizard's output isn't even in the repo. What the dig delivers: (1) the named question answers — the Telegram gate is a **negative reference with portable mechanics** for argus's phone-approval story: the model sits *inside* the approval TCB (it phrases the ask, interprets the "yes", and writes the approval), and the approval store sits *inside* the agent's write reach — the two properties a durable gate family exists to avoid, now citable next to CC2-4 in argus §4.4; (2) the notification trigger set is the **third shipping answer to argus §6.2**, contributing the one architectural rule the other two lack — *infrastructure alerts must not ride the agent path* (their watchdog pings are direct `curl`, precisely because the thing that failed may be the LLM/MCP loop); and (3) two of **our own gaps**, surfaced by holding their gate against ours: unconsumed approvals never age out on our side (theirs expire in 30 days; ours never — XA2-1), and we have no hard-block tier (everything dangerous is approvable — XA2-2). Plus one do-today INDEPENDENT the seams pass exposed: `Config.check_provider/1` already classifies `:unauthorized`, and nothing ever schedules it (XA2-3).

**Why not adopt**: (1) it isn't software — it's ~18k lines of instructions to a model plus 2k lines of bash; the system it describes is generated per-install and largely absent from the repo (most scripts the docs reference have no shipped bodies; the shipped Stop chain calls two nonexistent scripts fail-soft). (2) The trust architecture is the inverse of ours: prompt-level discipline enforced by advisory hooks, with the model inside every loop that matters — their own doctrine line concedes the premise (*"a rule in a prompt does NOT bind the model… So every defense is a HOOK or a deterministic script, not prose"*, `xantham-system-v32.md:733` — the same conclusion our pipeline-gate architecture is built on, executed one layer lower). (3) Single-session by construction ("Agents are not separate processes. They are agent voices inside the same session", `v32:3875-3877`) — the opposite of argus's clustered, multi-device, durable-state design on every axis.

## Tier 1 — read before the corresponding argus step starts

### XA1-1. The phone-approval loop: model-in-the-TCB as the named anti-pattern, with the mechanics worth keeping

**Recommendation**: BORROW-REFERENCE (negative reference for argus §4.4/§5, joining CC2-4) + BORROW-RUBRIC (the mechanics below).

**Where in Xantham**: the loop, verbatim from the shipped hook header (`.claude/hooks/safety-gate.sh:9-16`):

```
# 1. Hook blocks a dangerous command
# 2. Claude sees the block reason and asks Zaki on Telegram
# 3. Zaki says "yes" / "approved"
# 4. Claude writes the command to ${CLAUDE_PROJECT_DIR:-$PWD}/data/approved.txt
# 5. Claude retries the command
# 6. Hook sees it's pre-approved, allows it, removes the approval
```

The human's decision passes through the model **twice** — once to phrase the ask, once to interpret the natural-language "yes" and write the exact command string (`epoch|command` lines, `safety-gate.sh:49-54`). There is no phone-side write path, no structured decision token, no parser (`xantham-templates-v32.md` §4: approval-reply parsing is "LLM-mediated, not regex"). The store is a plain file in the project dir — inside the gated agent's own write reach, and `echo`-prefixed commands skip the gate's checks entirely (`safety-gate.sh:201`), so self-approval is a one-liner. Their SECURITY.md names the consequences: symlink races on the approval file, "the gate is one uid away from itself" (`SECURITY.md:120`), and a TOCTOU race that degrades one-shot to "approximately one-shot" under parallel dispatch (`SECURITY.md:121`). Fail posture: fail-closed on a destructive match, **fail-open on unparseable input** (`safety-gate.sh:36-39`).

What holds up and is worth keeping: **(a)** single-use consumption — one matching entry removed per pass, with a dated bugfix comment for the batch-consume race (`safety-gate.sh:88-102`) — independent convergence on our `:consume` semantics; **(b)** TTL-prune of stale approvals on every fire, "so stale approvals from previous sessions can't quietly green-light a destructive op later" (`safety-gate.sh:52-54`) — see XA2-1, where this beats us; **(c)** a hard-block tier approval cannot unlock (`safety-gate.sh:119-162`) — see XA2-2; **(d)** the two-tier trust rule for the *channel* itself: chat-pairing approval (`/telegram:access`) happens only in the terminal, never from a chat message, "since that is the request a prompt injection would make" (`SECURITY.md:138`, `v32:3745`) — the same trust-mutations-off-the-untrusted-channel rule argus §4.4 already carries from CC2-4, arrived at independently.

**Gap in jido_radclaw** (verified 2026-07-03): none to close — this is the design we already avoid. Approvals are durable `AgentCase` rows decided only through operator surfaces (`Cases.decide/4`, `cases.ex:118`; REPL `/gates`, `cli/commands.ex:611-623`; web `/approvals`), fingerprint-keyed with a FOR-UPDATE fence and a partial unique index (`agent_case.ex:31-49`); the agent never holds the store, and the decision never transits the model. Argus's `decideCase` mutation (OVERVIEW §4.1) wraps the same `Cases.decide/4`.

**Why it matters**: argus is about to put an *approve button on a phone*. Xantham is what that feature looks like when the transport is a chat model and the ledger is a file the agent can write: every property a phone approval needs — authenticity, integrity, single-use, non-repudiation — depends on the model behaving. It joins CC2-4 as the second, differently-shaped cautionary citation for §4.4: CCC showed reads and trust mutations left ungated; Xantham shows the *approval loop itself* built on prompt trust. Between them the checklist for argus's phone surface writes itself: decisions enter through authenticated, non-model surfaces only; the decision artifact is a DB row the agent can't mint; the ask may be *delivered* over any channel, but the *grant* never rides one the model mediates.

**Adoption sketch**: nothing to build — cite in argus §4.4 (done this pass) and keep the four kept-mechanics as review criteria when the phone-approve UX lands. The channel-pairing rule maps to argus keeping Web Push subscription registration and API-key issuance off the GraphQL surface entirely (§4.4's existing lean). (Cross-corpus note, 2026-07-05: the pms corpus supplies the rule's field-positive and a second vacuous case — bosun ships the *separation*: its Telegram chat deliberately carries no approve/deny controls (counts only), grants enter solely through the authed Mini App on signed short-lived action tokens ([BO1-3](../../pms/bosun/FEATURES-WORTH-BORROWING.md)) — the ask rides the chat channel, the grant never does — though the dig also flags a Mini App authz gap, so it confirms the shape, not a clean implementation. Chorus satisfies the rule only vacuously: its daemon defaults to yolo and chorus mode auto-denies rather than bridging approvals ([chorus dig](../../pms/chorus/FEATURES-WORTH-BORROWING.md)).)

### XA1-2. The notification trigger taxonomy — and the rule that infra alerts bypass the agent path

**Recommendation**: BORROW-PATTERN, folding into argus §6.2's trigger-set decision (the third shipping answer, joining emdash EM1-3 and CCC CC1-2).

**Where in Xantham**: eight trigger classes ship (as templates + 2 repo hooks): approval requests (model-relayed, §XA1-1); task-complete pings — "reply-first": acknowledge immediately, dispatch background, send a **new** message on completion because "New messages trigger push notifications on Telegram. Edits don't" (`xantham-system-v32.md:4008-4012`); the batched greeting digest (health line, open threads, stale commits — one message, compiled on session start, `v32:4182-4211`); auth-canary degraded (`v32:5429`); Telegram-MCP watchdog degraded/reinit alerts; the loop-detector owner-ping (3 identical commands/300s → one capped ping, never auto-kills, `v32:743`); the **never-silent fallback** — a Stop-time verifier that fires a direct-`curl` ping when a turn *owed* a reply and emitted none (`v32:749`); and on-demand `/mcp-health`. Delivery discipline: the infra alerts (canary, watchdog, never-silent) go through `notify-telegram-direct.sh` / `telegram-signal.sh` — **pure-bash `curl` to the Bot API, no LLM in the loop** (`xantham-templates-v32.md:3631-3714`, `10631-10669`) — because the failing component may *be* the LLM/MCP path. Rate mechanics: hard cap **20 notifications per tag per day** (`templates:10633,10662-10669`); streak alerts fire on `== N`, not `>= N`, so an ongoing outage alerts once per state transition (`templates:10615`). No quiet hours, no time-of-day batching anywhere (grep-verified).

**Gap in jido_radclaw** (verified 2026-07-03): the seams pass confirms **zero proactive operator notification exists** — gate opens broadcast IDs-only on `orchestration:gates` (`reactor_runner.ex:786-788`, `tool_approvals.ex:294-298`) consumed by two LiveViews as pull-refresh (`approvals_live.ex:184-193`) and by the composer; the per-gate `after_approved/after_rejected` hooks fire on *decide*, not open, and are no-op in all four gate modules (`gates.ex:26-29`, `human_gate.ex:36-42`); no Ash notifier on `AgentCase`; Discord's `send_message/3` has exactly one caller, inside `handle_inbound` — reply-only (`discord.ex:55,64-75`); no OS-notification bridge (grep clean for osascript/terminal-notifier/webpush/vapid/apns).

**Why it matters**: argus §6.2 asks *which events warrant a push*. Xantham's list converges with EM1-3 on the two core triggers (finished + waiting-on-you) and adds three the others lack: the never-silent fallback (≈ CCC's `ended_blocked`, arrived at independently — third convergence, this trigger is now settled), infra-degraded alerts (canary/watchdog — the class CC1-2a's slice covers on our side), and the digest-as-batch shape. Its architectural contribution is the delivery rule: **the notifier must not depend on the agent loop being healthy**. Argus satisfies this natively if pushes are sent by the Phoenix/gateway layer subscribed to PubSub — the rule's value is as a constraint stated up front: never implement "notify the operator" as an agent tool or an LLM behavior. The per-tag daily cap + transition-only (`==` not `>=`) firing are the right primitive shapes for the subscription endpoint's server side.

**Adoption sketch**: fold into the §6.2 trigger table when the Web Push endpoint is designed: triggers = gate opened, run failed/converged, agent finished, `ended_blocked`/never-silent, infra-degraded (canary XA2-3, LoopGuard halts, Forge `:needs_input` — the CC1-2a set); per-kind daily caps and transition-dedup as server-side delivery rules; delivery always from the gateway (PubSub subscriber), never from agent context. Cross-ref hermes' parked cron `delivery_targets` entry rather than re-opening it — the channel-dispatch glue is the same seam. (Cross-corpus note, 2026-07-05: the never-ride-the-agent-path rule shipped twice, independently ([pms observation 12](../../pms/README.md)) — bosun's sentinel watchdog is a literally separate process pushing monitor-crash escalations ([BO1-2](../../pms/bosun/FEATURES-WORTH-BORROWING.md), "the only corpus subject that ships XA1-2's rule *as a process*"), and OpenHelm's scheduler heartbeat watchdog escalates via process exit so the supervisor restarts the agent ([OH1-1](../../pms/openhelm/FEATURES-WORTH-BORROWING.md), "XA1-2 as shipped code"). The trigger set itself is settled in argus FLOW §12, which adopted this entry's caps + transition-only rules wholesale — and they remain distinct contributions there: bosun's otherwise-richest delivery shapes lack per-kind caps and quiet hours ("Xantham stays ahead there", per its dig).)

## Tier 2 — concrete our-side changes this dig surfaced

### XA2-1. Age-bound unconsumed approvals (and stale pending cases)

**Recommendation**: BORROW-PATTERN — small, independent of argus.

**Where in Xantham**: `APPROVAL_TTL_DAYS=30` (`safety-gate.sh:44`); every gate fire prunes entries older than the TTL before matching, with the stated rationale that stale approvals from previous sessions must not "quietly green-light a destructive op later" (`safety-gate.sh:49-74`). Their SECURITY.md still flags the residual *within* the window — "approve-once carries forward" (`SECURITY.md:97,118`) — i.e. even 30 days was judged worth admitting as risk.

**Gap in jido_radclaw** (verified 2026-07-03): **an approved-but-unconsumed tool approval never expires.** `ToolApprovals.approved_unconsumed?/1` matches `status: :approved, consumed_at: nil` with no age predicate (`tool_approvals.ex:186`), and the `:consume` action filters only on status + nil `consumed_at` (`agent_case.ex:213-214`). Nothing sweeps run-less cases: the `Deadline` module is a pure read-model ("never an action", `deadline.ex:2-6`), and `GateDisposition`'s deadline-abandon covers composer-parked child *runs*, not `:tool_call` cases (`gate_disposition.ex:55-66`). Scope honestly stated: the fingerprint includes the session (`{tenant, session, tool, args}`, `agent_case.ex:362-367`), so the stale grant only re-arms within the *same* session — narrower than Xantham's cross-session file — but REPL and MCP sessions here are long-lived, and pending (undecided) cases additionally accumulate in the `/gates` inbox forever.

**Why it matters**: threat-model-central. The operator approves something on Tuesday; the agent takes a different path and never consumes it; three weeks later — same long-lived session — the identical fingerprint silently passes. That is precisely the "quietly green-light later" failure Xantham's file-based gate already defends against. Ours being a durable DB makes the fix trivial and the current absence less defensible.

**Adoption sketch**: add an age predicate to the two unconsumed checks (`approved_unconsumed?`/`rejected_unconsumed?` and the `:consume`/`:consume_rejection` action filters) — `decided_at` older than a configured `approval_ttl` (default order-of-days, config under `:tool_approval`) means the row no longer satisfies the gate and the call re-pends. Same predicate excludes expired rows from the pending/approved lookups; optionally a sweep that transitions long-pending cases to `:abandoned` with a decision-comment, reusing the `GateDisposition` broadcast shape so `/gates` and `/approvals` stay coherent. A `:guardrail`-style Trace event on expiry keeps it observable. Test: approve → age past TTL → identical call re-pends rather than consuming. (Cross-corpus note, 2026-07-05: now a **three-subject convergence** — bosun ships the reference implementation, expiry timeouts + reconcilers that synthesize expiry for orphans ([BO2-5](../../pms/bosun/FEATURES-WORTH-BORROWING.md), an explicit FOLD-IN to this entry), with two anti-patterns to invert: `onTimeout:"proceed"` (timeout = auto-approve; a gate timeout only ever fails closed) and a scope-keyed requestId that became an accidental session-wide standing grant; OpenHelm ships the same never-expire gap, and its dig re-confirmed ours still open ([OH OQ-2](../../pms/openhelm/FEATURES-WORTH-BORROWING.md)). Expiry is now a named axis of the §5.4 acceptance-criteria list ([pms observation 9](../../pms/README.md)).)

### XA2-2. A hard-block tier: the class approval cannot unlock

**Recommendation**: BORROW-PATTERN — the tool-approval gate's missing third verdict.

**Where in Xantham**: Category 1 of the gate — `hard_block()` exits 2 with no approval path at all (`safety-gate.sh:119-162`): `rm -rf /|~|$HOME`, disk-format (`mkfs`/`dd if=`/`diskutil erase`), history rewrite (`filter-branch`/`filter-repo`/`reflog expire`/`gc --prune=now`), and force-push to protected branches. README: hard-blocks "are not configurable on purpose" (`README.md:119`).

**Gap in jido_radclaw** (verified 2026-07-03): **every dangerous command is approvable.** `ShellCommand.analyze/1`'s fail-closed floor is `:opaque` → routes to approval (`shell_command.ex:46-55`); `ToolApproval.requirement` resolves to gated-or-not — no deny verdict exists anywhere in the gate path (grep clean). The catastrophic class (history rewrite, force-push to a protected branch, `rm -rf $HOME`, disk ops) opens an `AgentCase` like anything else, and a phone-fatigued operator tapping approve is the whole failure mode.

**Why it matters**: approval fatigue is a *designed-in* pressure of the argus phone surface — the point is to make approving easy. A hard tier removes the never-worth-it class from the approvable surface entirely, so the worst outcome of a fat-fingered tap is bounded. It also gives the LLM a typed, non-retryable "this is not a permission problem, do not ask" signal instead of an approval loop it might try to socially engineer (their block message literally instructs the model to go ask the human — ours shouldn't, for this class).

**Adoption sketch**: a third outcome in `ToolApproval.gate/4` — `{:error, %{code: :hard_blocked, details: %{retry: false, class: …}}}` (non-retryable at both retry layers, the LoopGuard/doom-loop envelope precedent) — driven by a small effect-class list resolved from the existing `ShellCommand.analyze/1` effects, not new regexes (the analyzer already classifies git force/history operations for the param-pattern trigger). Start with Xantham's four classes minus what can't occur here; keep the list in code, deliberately not operator-configurable (their "not configurable on purpose" is the right call for this project's LLM-misbehavior model). No `AgentCase` is opened — a Trace `:guardrail` event records the refusal. Roll it out monitor-first per termic [TM2-3](../termic/FEATURES-WORTH-BORROWING.md) — evaluate and `:guardrail`-log with `would_block: true` through an observation window before enforcing — so the effect-class list is tuned on evidence rather than incident; a hard tier that misfires on legitimate ops teaches the operator to disable it. (Cross-corpus note, 2026-07-05: OpenHelm answers the classes-vs-scores question in advance — its per-tool numeric risk-1–5 gate is dead code, while the gate that survived is an action-**class** taxonomy (`reversible_tuning | auto_with_undo | destructive_availability`) with unknown→destructive fail-closed ([OH1-2](../../pms/openhelm/FEATURES-WORTH-BORROWING.md)); `destructive_availability` is this entry's hard tier under another name. Argus FLOW §12 adopted the hard-block list as designed-in — never-grantable kinds ask every time, always.)

### XA2-3. The credential canary — schedule the probe we already have

**Recommendation**: INDEPENDENT (surfaced here; worth doing regardless) — joins CC1-2a's do-today slice.

**Where in Xantham**: B14 (`xantham-system-v32.md:5363-5503`): `check-auth-status.sh` probes `/v1/messages` every 5 minutes (launchd), counts consecutive failures in a state file, and at 3 writes `auth-degraded.flag` + fires a direct-curl Telegram alert; recovery is manual. Companion `auth-fallback.sh` flips OAuth ↔ API key by hand (`templates:9687-9708`).

**Gap in jido_radclaw** (verified 2026-07-03): the probe **exists and is never scheduled**. `Config.check_provider/1` already classifies `:ok | {:error, :unauthorized} | {:error, :unreachable}` (`config.ex:240-285`) — its only callers are REPL boot (`repl.ex:161`) and the setup wizard (`setup.ex:264`). Meanwhile the system-cron seam is proven (the memory-consolidator tick, `scheduler.ex:363-386`), and a dead credential today fails silently: an auth error just fails the turn (no failover module exists — grep clean), and a failing *cron-triggered* run ends at a log line + in-memory `last_result` + silent auto-disable after 3 (`worker.ex:238-252`), which is itself one of the invisible-signal classes CC1-2 named.

**Why it matters**: this codebase increasingly runs unattended (cron jobs, clustered nodes, soon argus-driven background work). An expired key or suspended OAuth currently manifests as every scheduled thing quietly failing until the operator next opens a REPL. A 5-minute canary that flips a state row and emits on the transition is the cheapest possible fix and becomes a first-class push trigger the moment XA1-2's notifier exists.

**Adoption sketch**: register a `:system_job` beside the consolidator tick calling `check_provider(Config.provider())`; keep consecutive-failure state (a row or `:persistent_term`), act on **transitions only** (healthy→degraded, degraded→healthy), emit telemetry + a Trace event, and surface the degraded state in the attention feed when CC1-2's module lands (until then: a REPL banner + dashboard badge). Failover stays out (OQ-2). Their `==`-not-`>=` streak rule and manual-recovery lean both port as-is.
