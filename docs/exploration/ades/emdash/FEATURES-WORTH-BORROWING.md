## Determination (TL;DR)

**Nothing to adopt as a dependency; the haul is concentrated exactly where the scan predicted — worktree provisioning practice — plus two shipped answers to questions argus left open.** emdash is the argus-inverse architecturally (local-first, single-machine SQLite, Electron; no durable events, no transcript persistence, no cluster), which is by design: it's the best-*exercised* worktree-per-task UX in the set, and its provisioning mechanics (preserve-patterns file carryover, idempotent compiled setup steps, disk-truth-with-repair) are practice-hardened where traycer's are schema-complete — the two digs compose rather than compete. The shipped answers: a deliberately narrow **two-trigger OS-notification taxonomy** (argus §6.2's open question, answered by a product with real users) and an **attention status fold + seen-flag** for the agent list. The scan's ACP question is now concretely costable: the **minimal ACP agent-server surface is four methods plus two callback families**, and it maps almost 1:1 onto machinery we already run (EM1-4). Headline negative finding, now verified across both of the scan's "closest comparables": **emdash has no edit-step-output-and-resume** — batched diff comments become a *new* prompt (and don't even reach ACP conversations), Monaco hand-edits touch *files* not step output, and the documented Plan Mode turns out to be deleted code. Argus §5 stays novel in the entire ades set, with the last candidate checked.

## Tier 1 — read before the corresponding argus step starts

### EM1-1. Worktree creation-contract cribs: preserve-patterns carryover, naming, pool layout, serialized git ops

**Recommendation**: BORROW-PATTERN — the practice-hardened half of the worktree reference (traycer TR1-3 is the schema half). Targets argus step 1 (§3.1).

**Where in emdash**: `apps/emdash-desktop/src/main/core/projects/worktrees/worktree-service.ts` (525 lines) + the shareable settings schema. The unique piece traycer lacks — **preservePatterns**, untracked-file carryover into fresh worktrees (`src/shared/core/project-settings/project-settings.ts:11-45`):

```ts
export const DEFAULT_PRESERVE_PATTERNS = [
  '.env', '.env.keys', '.env.local', '.env.*.local',
  '.envrc', 'docker-compose.override.yml',
] as const;
```

Applied with three safety rules (`worktree-service.ts:458-510`, `preserve-pattern-safety.ts:3-8`): patterns rejected if absolute or containing `..`; **only files *untracked* by git copy** (`git ls-files --error-unmatch` probe per match — a tracked file never silently forks from its committed state); destination verified contained inside the new worktree (`isRealPathContained`). Failures are logged warnings, never fatal. Declared in committable `<repo>/.emdash.json` alongside `scripts.{setup,run,teardown}` and `shellSetup`, merged with DB-backed project settings (`effective-task-settings.ts` — precedence `defaults < committed file < local DB`, i.e. the operator's local layer wins). Branch naming: `${branchPrefix}/${name}-${5-char-random}` — prefix default `emdash`, suffix toggleable, name sanitized `[a-z0-9-]` max 64 (`resolveTaskBranchName.ts:12-31`, `settings-registry.ts:18-19`); issue-linked tasks bypass both and use the tracker-supplied branch name. Pool layout: `<worktreeDirectory>/<projectSegment>/<branchName>` with `worktreeDirectory` defaulting to `~/emdash/worktrees` (`worktree-defaults.ts`), `.emdash/` added to git exclude so an in-repo pool stays out of `git status` (`create-project-provider.ts:247`). Collision handling: branch already checked out anywhere → adopt that path (`findBranchAnywhere`, `:271-275`); branch ref exists → reuse; target dir exists but invalid → remove-for-reuse (fs remove **guarded to pool containment**, `:91-112`) + prune + recreate. All worktree mutations serialize through a promise queue (`enqueueGitOp`, `:54-58`); `git worktree prune` runs at construction and after every add/remove.

**What**: The parts of worktree creation that only surface after real use: the new checkout can't *run* without its untracked env files; generated branch names need a namespace and a collision suffix; the pool needs a home that git ignores; and concurrent creates corrupt each other unless git ops serialize.

**Gap in jido_radclaw** (verified 2026-07-03): no worktree functionality — `worktree` greps to exactly one hit, the `--worktree` config-scope flag in the shell analyzer (`lib/jido_claw/security/shell_command/git.ex:150`); `preserve_patterns` greps clean. The argus §3.1 sketch has `branch`/`status`/`node` and says "orchestrate via a tool/action" but specifies nothing about carryover, naming, layout, or concurrency.

**Why it matters**: The `.env` problem is the first papercut every worktree feature hits, and their solution is threat-model-compatible with our house rule (never *read* `.env` — this is a mechanical FS copy; no content enters model context). The untracked-only rule is the important subtlety — it makes carryover deterministic (nothing ever diverges from a committed state), and the containment checks matter for us because the pattern list arrives from a repo-committed file, i.e. repo-controlled input.

**Adoption sketch**: Fold into the `.jido/environment.yaml` file TR2-2 already plans: a `preserve:` list defaulting to their six patterns; enforce the same three rules (pattern safety, untracked-only via `git ls-files`, destination containment) in the Worktree create action. Branch contract: `{prefix}/{name}-{suffix}` with prefix a project setting (default `jido`), suffix on by default; adopt-existing-checkout and reuse-existing-branch as non-error paths (they compose with TR1-3's `origin: :imported`). Pool: default under the project workspace with a git-exclude entry, path recorded on the `Workspace` row per argus §3.3. Serialize mutations per-repo — one `Worktree.GitOps` GenServer per project (their promise queue done our way) rather than trusting call-site discipline. (Cross-corpus note, 2026-07-05: naming/collision datapoints from the pms digs — symphony templates `symphony/<sanitized-issue-id>` with **no collision counter**, `worktree add --force -B` resetting instead ([SY2-1](../../pms/symphony/FEATURES-WORTH-BORROWING.md)); myrlin records the reconcile-don't-fail posture — reuse the existing worktree on collision — as the contrast to a `-{n}` counter ([MY2-3](../../pms/myrlin-workbook/FEATURES-WORTH-BORROWING.md)); and multica's repocache mechanics are the git-plumbing reference the pool layout composes with ([MC2-3](../../pms/multica/FEATURES-WORTH-BORROWING.md)).)

### EM1-2. Worktree provisioning compiled to idempotent steps

**Recommendation**: BUILD-ON — the enabling precedent for argus §3.1's "orchestrate via a tool/action, not pretend they're free"; our Reactor substrate is the natural executor.

**Where in emdash**: `compileSetupSpec` (`src/shared/core/workspaces/workspace-setup-spec.ts`) compiles a declarative git intent (`create-branch` | `use-branch` | `pr-branch` | `none`, `:49-148`) into an ordered list of **atomic, individually idempotent steps**, executed by `LocalWorkspaceSetupExecutor`. The step vocabulary (`src/main/core/workspaces/setup-steps/`): `git-fetch` → `create-local-branch` (pre-checks `rev-parse --verify`; "already exists" is success) → `set-branch-base` (records the base ref as git config `branch.<b>.base` — idempotent) → `set-branch-tracking` / `ensure-remote` (fork support) → `add-worktree` → `copy-preserved-files` → `push-branch` (`-u`, **failures non-fatal, warn only**). Disk-truth on re-entry: bootstrap never trusts the persisted path — it re-resolves through `serveBranchWorktree`, which validates the `.git` marker + `rev-parse --is-inside-work-tree` and repairs/prunes stale state (`workspace-bootstrap-service.ts:44-48,102-122`).

**What**: Worktree provisioning decomposed so each step can be retried, skipped-if-done, or fail with a precise error — and re-running the whole sequence against a half-provisioned checkout converges instead of erroring. The three intent kinds map cleanly onto an `origin` concept (created / imported / PR-review).

**Gap in jido_radclaw** (verified 2026-07-03): `Skills.Compiler` compiles YAML → `%Reactor{}` and `ReactorRunner` executes inside the durable envelope (argus appendix A.4) — the *machinery* exists and is strictly stronger (durable events, replay, compensation); what doesn't exist is any worktree step vocabulary, and our only multi-step shell-work precedent is `git_commit`'s reduce-while over `git add` (`lib/jido_claw/tools/git_commit.ex:43-54`, no retries).

**Why it matters**: Independent convergence with traycer (six-state setup machine) on "provisioning is the hard part, model it as steps" — and emdash's contribution is the *idempotency-per-step* property, which is exactly what makes a Reactor-executed provision safe to re-run after a node dies mid-create (our lease-reclaim story will hit this on day one of multi-node worktrees). The non-fatal push and the disk-truth re-resolution are both judgment calls we'd otherwise learn by incident.

**Adoption sketch**: Model `Worktree.create` as a small compiled Reactor (or a plain multi-step action first — the compilation seam can come when a second consumer wants it) with their step list translated: fetch → ensure-branch (idempotent) → record-base → add-worktree → preserve-copy (EM1-1) → optional publish (non-fatal). Each step pre-checks its postcondition before acting. Setup *scripts* (TR2-2) run as the last step with output to a `ToolOutput` ref feeding `setup_status`/`setup_exit_code` (TR1-3a). Re-entry = re-run the sequence; the disk-truth re-resolution rule becomes the `verify_on_disk` action TR1-3d already sketches. (Cross-corpus note, 2026-07-05: the pms wave made this reference three-deep — orca ships the same decomposition with a lockfile-keyed toolchain-detection table, hard-stop/retry/recorded-skip per-step semantics, and the init-status split ([OR1-4](../../pms/orca/FEATURES-WORTH-BORROWING.md)); myrlin is the third init-hooks precedent ([MY2-3](../../pms/myrlin-workbook/FEATURES-WORTH-BORROWING.md)); bosun adds shared-path symlink install-avoidance with signature idempotency ([BO2-1](../../pms/bosun/FEATURES-WORTH-BORROWING.md)); and OpenHelm is the anti-reference — no isolated workdirs, so its collision fix was a global concurrency cap of 1.)

### EM1-3. The two-trigger notification taxonomy and its delivery rules

**Recommendation**: BORROW-PATTERN — a shipped answer to argus §6.2 (push-trigger taxonomy), the OVERVIEW's open question 2. Targets argus step 8.

**Where in emdash**: one code path, `src/main/core/agent-hooks/notification.ts` (`maybeShowNotification`, `:54`; body selection `:32-42`). Exactly **two** events produce an OS notification: agent **stop** → "Your agent has finished working", and an **attention notification** → "Your agent is waiting for input" — where attention is the explicit subset `permission_prompt | idle_prompt | elicitation_dialog` of the notification types, with `auth_success` deliberately excluded (`src/shared/core/agents/agentEvents.ts:7-21`). Everything else — agent **errors**, PR/CI updates, automation results, SSH drops, app updates — produces **no OS notification** (errors surface as an in-app red dot + unseen flag only). Delivery rules: suppressed entirely when the app is focused (`isAppFocused`, `:92-95`); fired only on an actual status *transition* (`agent-hook-service.ts:205`); `silent: true` with sound handled by a separate system carrying its own focus mode (`always | unfocused`); title = `provider — task`; click focuses the window and deep-links to the exact task/conversation (`notification:focus-task`, `:78-83`). Settings: `{enabled, sound, customSoundPath, osNotifications, soundFocusMode}` (`settings/schema.ts:27-33`).

**What**: A product with real users decided which of its dozens of event types warrant interrupting a human: *the agent finished* and *the agent is blocked on you* — nothing else. Plus the four delivery rules that make even two triggers tolerable: unfocused-only, transition-deduped, sound decoupled, click-deep-linked.

**Gap in jido_radclaw** (verified 2026-07-03): no OS/web-push machinery anywhere (`web_push`/`push_subscription`/desktop-notification greps clean); attention surfaces are pull-based — the dashboard stat card (`web/live/dashboard_live.ex:38`), CLI `status` line (`cli/commands.ex:101`), `/approvals` — fed by `AgentCase.pending_for_tenant` and the id-only `orchestration:gates` pokes (`orchestration/tool_approvals.ex:294-298`). Argus §6.2 lists candidate triggers but explicitly defers the decision.

**Why it matters**: Argus's Web Push step needs a trigger set before the subscription endpoint is worth wiring, and the failure mode is notifying too much (the phone goes to Do-Not-Disturb and the control plane loses its channel). Their two triggers translate directly: **gate opened** (an `AgentCase` awaiting decision — their "waiting for input") and **run reached terminal** (their "finished"). Their error-exclusion is the one place our context differs — see OQ-3.

**Adoption sketch**: At argus step 8: Web Push fires on (a) `AgentCase` opened (any kind — tool_call/plan/review), (b) `WorkflowRun` terminal transition; both keyed to the run/case id with a deep link into the SPA (`/worktree/<id>/run/<id>` style). Dedupe on the durable transition itself (we get this free — both are single events in the log). Suppress when the operator has an active socket on any device (our analog of "app focused" — presence via Phoenix.Presence on the UserSocket). Keep the payload id-only (matches §4.2 discipline; the service worker fetches the summary). Sound/badge stay client-side concerns. Decide OQ-3 (failures) explicitly rather than inheriting their exclusion. (Second datapoint from the termic dig, 2026-07-03: independent convergence on the same two triggers, active-surface suppression, transition-edge dedupe, and default-off — plus three delivery deltas folded there: sound only on *done*, per-key debounce, fail-toward-attention for ambiguous states; [termic TM2-5](../termic/FEATURES-WORTH-BORROWING.md).) (Cross-corpus note, 2026-07-05: the strongest confirmation yet — myrlin declares **five** per-event push preferences and exactly **two** fire, and the live pair is precisely this entry's set (finished + waiting-on-your-review), independently re-derived ([MY2-4](../../pms/myrlin-workbook/FEATURES-WORTH-BORROWING.md)); the cautionary rider is that the trigger myrlin *named* — `fileConflicts` — is dead code, so every trigger argus declares needs a named, tested producer. myrlin also contributes three storm-tested delivery rules the EM/TM/XA stack lacked: replay suppression during reconnect catch-up, focus-acknowledgement consumes pending state, minimum-signal re-arm floor ([MY1-3](../../pms/myrlin-workbook/FEATURES-WORTH-BORROWING.md)).)

### EM1-4. ACP: the minimal agent-server surface, enumerated — the "speak ACP" decision brief

**Recommendation**: TRACK with the trigger the scan already named (the argus §4 API-surface design pass) — but the dig converts the question from speculative to costable, and the mapping is BORROW-REFERENCE material when the trigger fires.

**Where in emdash**: the client side of `@agentclientprotocol/sdk@1.1` (npm, not Zed's package), stdio JSON-RPC. What emdash-as-client requires of an agent server (`packages/core/src/agents/plugins/capabilities/acp.ts:50-65`; `acp-agent-connection.ts:84-96`; `acp-session-runtime.ts:677-859`): **four agent methods** — `initialize` (protocolVersion 1 + capability exchange), `newSession`, `prompt` (text/image blocks → `stopReason`), `cancel` — plus honoring **two client callback families**: `session/update` (message/thought/tool_call/tool_update/plan chunks; unknown kinds safely ignored) and `fs/read_text_file`+`fs/write_text_file`. Everything else is optional and degrades gracefully: `loadSession` (resume), `setSessionMode`/`setSessionConfigOption` (modes/model/effort as `category: model|mode|thought_level` select options), `session/request_permission` (only if the agent enforces permissions), terminal methods, `closeSession`, usage updates. Notable contract details: emdash always sends `mcpServers: []`; permission requests carry **title and kind only — the raw tool input never reaches the approving user** (`acp-session-runtime.ts:769-780`); the option vocabulary is `allow_once | allow_always | reject_once | reject_always` (open-ended), and emdash persists **no** grant memory — an `allow_always` choice is forwarded to the agent, which owns it (`permissions.ts:8-30`).

**What**: The concrete price of making JidoClaw drivable by every ACP cockpit (emdash, Zed, whatever ships next): a stdio endpoint speaking four methods and streaming session updates. And a worked example of the permission-flow shape — including its informed-consent weakness.

**Gap in jido_radclaw** (verified 2026-07-03): `ACP`/`agent_client_protocol` grep clean. But the mapping is almost embarrassing: `prompt` ≈ `JidoClaw.chat/4` through the FrontDoor; `session/update` ≈ the `SignalBus` `ai.*` stream the Recorder already consumes (`conversations/recorder.ex:247-258`); `session/request_permission` ≈ the ToolApproval gate — an `approval_pending` case maps to a permission request and `Cases.decide/4` to `resolvePermission`; `loadSession` ≈ the shipped CLI session resume (osa OS1-5); the MCP stdio server (`core/mcp_server.ex`) is the transport-precedent. Where we'd be *better* than the reference: our permission surface would carry the redacted, summarized args (`tool_approvals.ex:266-277`), not a bare title.

**Why it matters**: The scan's cross-cutting question 4 ("should JidoClaw eventually speak ACP?") stays a real strategic option — it makes third-party cockpits free front-ends while argus remains the richer first-party surface. What the dig adds: the surface is small, our internals already produce every signal it needs, and the permission bridge is the only part with design risk (single-use consume semantics vs. ACP's `allow_always` vocabulary — OQ-1).

**Adoption sketch** (when the trigger fires): a `JidoClaw.ACP.Server` sibling to `MCPServer` — stdio, sessions keyed to `Conversations.Session`, `session/update` fed by a SignalBus subscriber, permissions bridged to run-less `AgentCase` rows so the ACP client's allow/reject lands in the same durable decision path as `/approvals`. Skip terminals and fs callbacks initially (advertise `fs: false`, `terminal: false` — capability-gated exactly for this). Decide `allow_always` handling per OQ-1 rather than silently dropping it. (Connective note, 2026-07-03: the same-day CCC dig supplies the agent-side datapoint — CCC implements the server role in 616 experimental lines (initialize/newSession/prompt/cancel over stdio), confirming this entry's small-surface costing, and punts the permission bridge entirely (`--dangerously-skip-permissions`; permission types imported, never used) — reinforcing that the bridge is the one design-risk piece; [CC S-7](../claude-command-center/FEATURES-WORTH-BORROWING.md).) (Second cross-corpus datapoint, 2026-07-05: multica — the fastest-moving tracker in the pms corpus — attaches its newest backend drivers via ACP ([multica dig](../../pms/multica/FEATURES-WORTH-BORROWING.md)), the first adoption signal from the tracker side; the TRACK trigger and this costing stand.)

## Tier 2 — adopt while building the corresponding argus step

### EM2-1. Agent-attention rubric: status fold + seen-flag

**Recommendation**: BORROW-RUBRIC (argus step 2's worktree/agent list UI).

**Where in emdash**: `AgentStatus = idle | working | awaiting-input | error | completed` derived from hook events (`agent-hook-service.ts:31-41`), persisted with a **seen flag** — `seen=1` for idle/working, `seen=0` (needs eyes) for awaiting-input/error/completed (`:179`). Task-level rollup is a pure fold, derived at read time, precedence: **unseen awaiting-input > working > unseen error > unseen completed > nothing** (`conversation-manager.ts:159-173`). A stuck `working` is force-reset to `idle` on process exit because terminal hooks may never fire (`:212-245`). Notably **no attention-sorting**: the sidebar orders by timestamp only; attention is badge + sound + notification, never reordering (`sidebar-store.ts:247-254`).

**What**: The agent-list UX distilled to two primitives — a five-state status with a *have-I-looked* bit, and a deterministic fold from N agents to one badge — plus the finding that a shipped product chose *stable ordering with badges* over attention-sorting (the scan's muxara-derived assumption; the termic dig made it two-for-two, and contributed the fingerprint-tied seen-mark idea — [termic TM3-2](../termic/FEATURES-WORTH-BORROWING.md)). The muxara dig (same day) closed the loop from the other side: the assumption's source really does ship attention-sorting — and exhibits the churn defect in code (its positional selection ring silently drifts across reorders), turning the assumption into the counterexample — [muxara MX2-1](../muxara/FEATURES-WORTH-BORROWING.md); muxara's per-agent enum is also the single-agent contract this fold composes over ([MX1-1](../muxara/FEATURES-WORTH-BORROWING.md)).

**Gap in jido_radclaw** (verified 2026-07-03): the *signals* all exist — `AgentTracker` live status, `AgentCase.pending_for_session` probes (`agent_case.ex:260-264`, used by `agent_view.ex:561`), run statuses from projections — but there is no seen/unseen concept and no defined fold from a worktree's N runs/sessions to one attention state.

**Why it matters**: Argus's project → worktree drill-down needs exactly this rollup, and ours can be *derived entirely from durable data* (pending cases + run statuses + last decision-viewed marker) where theirs needs hook plumbing. The seen-flag is the phone primitive: "what needs me *that I haven't already seen*" is the whole utility of a control plane at breakfast.

**Adoption sketch**: A read-model fold (in the GraphQL resolver or a small view module): worktree attention = pending `AgentCase` (unseen) > any `:running` run > failed run (unseen) > recently-converged (unseen) > idle. "Seen" as a lightweight per-operator ack — a `viewed_at` on the case/run surfaced via the SPA, or purely client-side to start (single operator). Keep timestamp ordering + badges; do not attention-sort. (Cross-corpus note, 2026-07-05: two pms design inputs for the seen-flag — Chorus's wake ≠ read rule: delivery to a machine consumer must never consume the operator-facing unread state ([CH2-3](../../pms/chorus/FEATURES-WORTH-BORROWING.md)); and myrlin's storm-tested focus-acknowledgement-consumes-pending ([MY1-3](../../pms/myrlin-workbook/FEATURES-WORTH-BORROWING.md)) — together: the ack must consume, and only the *operator's* ack counts.)

### EM2-2. Byte-offset + ring-buffer reset replay for non-durable output streams

**Recommendation**: BORROW-PATTERN (argus step 3 — the `forge:session:<id>` channel proxy).

**Where in emdash**: the PTY output stream contract (`packages/core/src/workspace-server/pty-agent/schemas.ts:25-43`): subscribers pass a byte `offset`; frames are `chunk{data, offset}` (monotonic), `reset{data, offset}` (full ring-buffer contents when the requested offset has been evicted), `exit{exitCode, signal}`. Backed by a per-terminal ring buffer capped at 4 MB with a `truncated` flag (`managed-agent-terminal.ts:6`; snapshot shape `terminals.ts:9-27`).

**What**: The cheap, honest answer to "reconnect to a live output stream that has no durable log": resume from your offset if the buffer still has it, otherwise get an explicit full-buffer reset — never a silent gap.

**Gap in jido_radclaw** (verified 2026-07-03): Forge output broadcasts `{:output, %{chunk, seq}}` on `forge:session:<id>` (`forge/harness.ex:666-677`) with no catch-up story — argus §4.2's reconnect design covers *workflow* topics via the durable `workflowEvents(afterSeq:)` feed, but forge session output is PubSub-only and a reconnecting channel client just misses whatever it missed. (Shell `SessionManager` streams reach only the local `Display`; there is no PTY anywhere in the tree — `pty` greps clean.)

**Why it matters**: The forge session view is the one argus screen backed by ephemeral data. This pattern gives it the same "nothing lost while offline" feel as the workflow screens for the price of a capped buffer — and the `reset` frame keeps it honest when the buffer overflows, which is our OutputShaper head+tail philosophy applied to a live stream.

**Adoption sketch**: A capped ring (reuse the 4 MB default) held by the Forge session process (or the channel-side proxy); channel join accepts `offset`; the proxy replays from offset or sends a `reset` payload built from the ring + `truncated` flag. Bonus: the full transcript is already durably captured post-hoc via the Forge transcript pair (agentos borrow) — the ring only bridges the *live* window.

### EM2-3. Gate the worktree mutations — an our-side gap the dig exposed

**Recommendation**: INDEPENDENT — surfaced by this dig's seams pass; doable today, before any worktree feature exists.

**Where in emdash**: n/a (their deletion guards are TR2-1's comparison material — and their dirty-tree warning is defeated by a shipped bug, `getDeletePreflight.ts:64-67`, where a `too-many-files` check unconditionally clobbers the computed flag; evidence that soft guards rot silently).

**What / Gap in jido_radclaw** (verified 2026-07-03): `git worktree remove --force` deletes a checkout directory — with any uncommitted work in it — yet our shell analyzer classifies every `git worktree` invocation as a benign git run: it is neither a commit/push/config effect nor opaque (`security/shell_command/git.ex` produces no effect for it; the only `worktree` token is the `--worktree` config-scope flag at `:150`), and nothing worktree-shaped is in the approval require-list (`security/tool_approval.ex:125`). So today an LLM can run `git worktree remove` through `run_command` un-gated, and the future argus Worktree tool would ship un-gated by default.

**Why it matters**: Straight threat-model center: LLM-misbehavior containment. Worktree removal is destructive in exactly the way `git commit`/`git push` (already pattern-gated) are not — it destroys *uncommitted* work. The gap is cheap to close now and expensive to discover post-incident.

**Adoption sketch**: Add a `:worktree_mutation` effect to the git analyzer (`worktree remove|move|prune` at minimum; `add` is arguably benign) and a corresponding `@require_patterns` entry — the same fail-closed floor the commit/push patterns use. When the argus Worktree tool ships, require-list its destroy/archive actions and let TR2-1's busy/dirty guards be the workflow-side complement. Their preflight bug is the design lesson: make the dirty-check a *typed refusal requiring an explicit flag*, not a UI warning. (Connective note, 2026-07-03: three later same-day digs validated the thesis independently — CCC's teardown is a prompt asking the agent to delete its own worktree, the exact delegate-to-agent pattern this gate exists to catch ([CC2-3](../claude-command-center/FEATURES-WORTH-BORROWING.md)); termic's archive runs `git worktree remove --force` behind a bare confirm with no busy/dirty guard, and its TM1-3/TM2-4 entries are explicitly gated on this entry landing ([termic](../termic/FEATURES-WORTH-BORROWING.md)); Xantham's bash gate approval-gates `worktree remove --force` from inside the same threat model ([XA3-2](../Xantham-system-blueprint/FEATURES-WORTH-BORROWING.md)). Re-confirmed unshipped by every subsequent dig.)

### EM2-4. Versioned JSON columns for mixed-version readers

**Recommendation**: BORROW-PATTERN (small), FOLD-IN to the argus rolling-upgrade doctrine that TR1-1 starts (wire skew) — this is the data-at-rest half.

**Where in emdash**: `agents/conventions/versioned-schemas.md` + `src/shared/lib/versioned-schema/versioned-schema.ts` + `src/main/db/versioned-column.ts`. **Live in production, 10 columns migrated** (contrast traycer's S-1 framework: dormant, zero callers). Mechanics: version field read before parse; sequential upgrade chains applied on read (`v0 → v2` with derivations); `needs-context` when an upgrade requires data the blob lacks; **`future-version` as a first-class parse result** so an older app degrades gracefully instead of corrupting; writes always at latest; Zod validation dev-only. Their stated rationale: "multiple app versions will coexist and share the same database."

**What**: Schema evolution for JSON blobs, designed for the topology where readers and writers run different app versions against one database — which is argus §2.2's cluster verbatim (N nodes, one Postgres, rolling `git pull` upgrades).

**Gap in jido_radclaw** (verified 2026-07-03): narrower than it first looks. Our encrypted envelopes already **fail closed with audit on unknown versions** — `{version, module, inner}` resume checkpoints check `@checkpoint_version` and error typed (`orchestration/gate_resume.ex:79,250-251`), composer artifacts carry `@artifact_version` (`composer_artifact/envelope.ex:17`). What we lack: upgrade chains (no read-time migration exists anywhere), and *coverage* — plain jsonb maps (`Session.metadata` compaction snapshots, `AgentCase.details`, workspace policies) carry no version at all. Ash migrations cover *column* shape, not blob shape, and a migration can't run "between" two live node versions.

**Why it matters**: The first mixed-version window where a v-next node writes a reshaped `metadata["compactions"]` entry and a v-prev node reads it is a silent-corruption candidate. Fail-closed-on-unknown (our existing posture) is the right floor; the emdash datapoint says decide the doctrine *before* the second node exists, and shows the affordable shape if any blob ever needs an upgrade chain.

**Adoption sketch**: Doctrine first, machinery on demand: (a) at argus step 1, write the rule into the Worktree/Workspace design — any structured jsonb written by versioned code carries a `"v"` field, readers treat unknown-higher as refuse-gracefully (our checkpoint posture generalized); (b) retrofit `"v"` onto the compaction snapshot map at its next touch; (c) build an upgrade-chain helper only when the first real v1→v2 blob migration is wanted — a 50-line module then, not a framework now. (Third datapoint from the same-day termic dig — the no-doctrine pole: plain `fs::write`, a `version: u32` written but never read, a corrupt store silently becoming an empty list; [termic S-4](../termic/FEATURES-WORTH-BORROWING.md).)

### EM2-5. The remote-workspace capability checklist (workspace-server contract)

**Recommendation**: BORROW-REFERENCE — diff argus §4.1's surface against it once, at design time (argus step 2). Adopt nothing wholesale.

**Where in emdash**: `packages/core/src/workspace-server/contract.ts` + per-namespace contracts; served by `apps/workspace-server` (oRPC over plain node HTTP at `/rpc`, port env-configured). **130 typed procedures; exactly 2 implemented** (`health`, `initialize`) — the other 128 throw `NOT_IMPLEMENTED` (`router.ts:14-17`); four more namespaces (`workspaces` lifecycle, `terminals`, `activity`, `file-search`) are TODO comments. **No auth, no TLS, no discovery; binds all interfaces** (`index.ts:5,16`) — the CCC cautionary posture again. No desktop client exists yet (the future `WorkspaceServerAcpSessionRuntime` is a doc comment, `runtime.ts:104-107`); today's shipped remote path is the separate SSH/SFTP "byoi" runtime. Version negotiation: single protocol version, same-major compatible, `agreedMinor = min(client, server)` gates features, `PROTOCOL_INCOMPATIBLE` carries `upgrade-client|upgrade-server` (`versions/index.ts:27-58`). Streaming: a uniform **live-model trio** (snapshot + subscribe→Immer-patch deltas with `generation/sequence` gap-detected resync + unsubscribe) plus plain event-iterators for append streams.

**What**: A 126-contributor team's typed inventory of everything a desktop cockpit thinks a remote workspace API needs. The value is the *checklist*, not the code: what they include that argus §4 doesn't mention — deep git plumbing (76 procedures incl. hunk-level staging, merge/rebase lifecycles, blame, conflict-version extraction), dependency probe/install, filesystem CRUD + per-session file-tree live models, per-file diff staleness streams, PTY attach with the EM2-2 replay contract, mid-session model/mode switching — and what they lack that argus has: **no runs/steps/gates, no cluster/nodes, no skills, no durable conversation store** (their `acp.getHistory` is in-memory turn history).

**Gap in jido_radclaw** (verified 2026-07-03): argus §4.1 is a sketch; nothing exists. The reverse deltas re-confirm argus's differentiators survive contact (scan observation 5, second data point).

**Why it matters**: The include-list is mostly *conscious-SKIP fodder* — argus is a control plane, not a remote IDE; the operator has an editor and a terminal. But each omission should be a decision, not an accident: e.g. "no file CRUD" is right; "no way to read a file at a ref" might bite the code_diff editor (§5.3) the first time it needs surrounding context. The `agreedMinor` handshake is also the simpler counter-datapoint to traycer's per-method versioning — it feeds traycer OQ-1/OQ-3 directly (one version for the socket, minor-gated features, no bridging).

**Adoption sketch**: At argus step 2, walk their namespace list once and mark each: covered-by-GraphQL / conscious-skip / gap. Expected gaps worth stealing the shape of: `readBlobAtRef` (the §5 code_diff editor's context fetch), `getConflictVersions` (if merge assistance ever ships), the deep-probe `initialize` idea folded into TR2-4's authenticated probe. For the Channels contract, weigh `agreedMinor` vs traycer's per-topic majors when the second topic family ships (traycer OQ-3, now with both datapoints).
