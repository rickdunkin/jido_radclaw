Exploration notes — not a plan, not a commitment. Initial inventory **2026-07-03**, a scoped dig (three subsystems, per the [ades scan](../README.md)'s next-steps) rather than a whole-repo sweep. Source: `~/workspace/research/ades/traycer` (traycerai/traycer). Self-description: *"an open-source AI orchestration app for advanced agent orchestration — bring your existing provider subscriptions and run multiple agents in parallel without losing context."* Subject @ `b09cf8d` (unmoved since the ades scan), jido_radclaw @ `994cd54f`. Cites are firsthand reads of both trees, accurate to within a few lines.

Shape and maturity: Bun/Nx TypeScript monorepo, ~440k LOC TS (`protocol/` 183 files / ~39k lines; `clients/` ~2.2k files / ~402k lines). 113 commits but PR numbers reach #187 — history squashed at open-sourcing; 8 contributors with a heavy tail (top three hold ~90%); active the week of this review; CHANGELOG holds only `[Unreleased]` (releases are signed binaries published cross-repo from Traycer's internal repo); v0.x. Apache-2.0 with NOTICE; `@traycer/protocol` is a *published npm package* (0.1.0) — the contract layer is a deliberate public artifact.

**The epistemic frame for every entry below**: this repo is the open-source **clients + CLI + protocol only**. The Traycer Host — the process that actually runs `git worktree add`, writes checkpoints, and orchestrates agents — is a closed-source signed binary (AGENTS.md:10-13), and the cloud backend is likewise external. So all host *behavior* claims are "per contract/schema" — this codebase's Zod schema doc-comments are unusually load-bearing (they document host semantics) and are treated throughout as claims, not verified behavior. What IS firsthand-verified: the schemas, the framework code, and the client/GUI code that drives the contract. That constraint turns out to be a feature: the open layer is *exactly* the layer argus needs references for — the versioned wire contract and the persistence schemas — and it is complete and battle-tested in the open.

Companion docs: [ades scan README](../README.md) (umbrella; this dig answers its traycer questions and corrects two of its claims), [argus OVERVIEW](../../argus/OVERVIEW.md) (the consumer — §3.1–3.3 Worktree domain, §5 review editors, §6.3 skew; this dig feeds all three and corrects its `expectedSeq` premise), [camus](../../camus/FEATURES-WORTH-BORROWING.md) (C1-4's `review_stall` gate kind — queued as next-ten #6 — touches the same `Gate.Kinds` list argus §5's `:review` kind will extend; coordinate, don't collide), [squidie](../../squidie/FEATURES-WORTH-BORROWING.md) (origin of the gate/event-log machinery every argus-side gap cites). Threat model (personal, tailnet-only): LLM-misbehavior containment and leakage hygiene over external-attacker hardening — traycer's multi-user/collab machinery is weighted accordingly (mostly SKIP).

## Determination (TL;DR)

**Nothing to adopt as a dependency; the protocol layer is the richest single-subject pattern haul since camus.** Traycer-as-product is the inverse of argus on every architectural axis that matters (closed host binary, cloud CRDT sync, desktop-first) — but its open repo is a complete, incident-hardened worked example of the two problems argus has not yet solved: **client⇄server schema skew under independent shipping** (per-method versioned contracts, a pure compatibility oracle, a CI-frozen released surface — born from two real production incidents) and **worktree-as-a-modeled-resource** (setup state machine, device binding, lifecycle scripts, guarded deletion). The scan's standing question is answered definitively: **traycer has no edit-step-output-and-resume** — plans are approve/reject/dismiss only, and its "Epic" is a CRDT container document, not an execution DAG. Argus §5 stays novel across the entire ades set, now with the last slot verified. That same finding demotes traycer from the scan's "closest architectural comparable" to "closest *contract-layer* comparable": its orchestration model (chat-shaped, CRDT-synced, no dependency graph) is not a reference for ours at all.

| Part of traycer | As a dependency | What to take |
| --- | --- | --- |
| `protocol/src/framework/` (versioned RPC/stream/record + compat oracle + fingerprint diff) | No — TS/Zod, and argus chose GraphQL | The **model**: per-method `{major,minor}` manifests at connect, "newer side owns transforms", additive-minor invariant enforced at load, major-must-break rule, structured skew verdicts (TR1-1); the CI release discipline (TR1-2) |
| Worktree schemas + lifecycle contract (`protocol/src/host/worktree-schemas.ts`, delete stream) | No — host executor is closed anyway | Schema cribs for the argus `Worktree` resource: setup state machine, owner model, disk-truth fields (TR1-3); guarded phased delete (TR2-1); committable env scripts (TR2-2) |
| Device binding / cross-device model (`hostId`-for-life, clone-not-migrate, host-local SQLite projection) | No | The **affinity doctrine** for argus §3.3's `node` columns (TR1-4) — plus a deliberate divergence on path privacy |
| Epic mode + checkpoint manifests | No | Verified-empty for argus §5 (the headline negative finding); garnishes: restore audit-pair honesty (TR3-1), plan supersession vocabulary (TR3-2) |
| GUI client (React/TanStack/yjs) | No — argus chose Apollo | One discipline: per-host cache keying + mutation-time host capture (TR3-3) |
| Electron shell, minisign host provisioning, Tiptap Cloud collab | No | Nothing — different product problems (S-2, S-5) |

**Why not adopt as a dependency**: (1) the part that runs things — the host — isn't in the repo to adopt; (2) the open parts are TS/Zod/Electron artifacts with no seam into an OTP/Ash system; (3) the orchestration model (CRDT chat container, no DAG, no event log) is strictly weaker than the composer + `WorkflowEvent` substrate we already run — on that axis *they* lack what *we* have, not the reverse.

## Tier 1 — read before the corresponding argus step starts

### TR1-1. Per-method versioned contracts + a pure compatibility oracle for the live layer

**Recommendation**: BORROW-PATTERN — the strongest item in this doc. Targets argus steps 2–3 (GraphQL + Channels).

**Where in traycer**: `protocol/src/framework/versioned-rpc-types.ts:42-50` (`RpcContract` = method + `{major, minor}` + request/response Zod schemas; versions are literal ints, explicitly not semver — `versioned-rpc.ts:1-5`), `:166-192` (registry: per-method major lines, minor chains with `upgradeFromPreviousVersion`, direct `downgradePathsFromLatest`). Handshake: each side advertises a canonical manifest (one `{major,minor}` per method) in the `open`/`openAck` frames (`ws-protocol.ts:26,77-122`; `compat-helpers.ts:35-56`). The oracle: `check(myRegistry, myManifest, theirManifest, selfRole)` — pure, stateless, role-parameterized (`compatibility-checker.ts:38-101`), producing structured `IncompatibleMethodDetails` (`client-missing-method | host-missing-method | no-bridge`) + `upgradeGuidance{clientShouldUpgrade, hostShouldUpgrade}` (`ws-protocol.ts:36-71`). The load-bearing asymmetry (`compatibility-checker.ts:109-148`): **the older side never transforms — the newer side owns all bridging** (older-major peer sends its canonical untouched; newer side downgrades requests via authored direct bridges that may honestly *fail* — `DowngradeResult` `versioned-rpc-types.ts:117-136`, e.g. `agent.listHarnessModels` v2→v1 returns `DOWNGRADE_UNSUPPORTED` when required newer context is absent, `host/agent/contracts.ts:120-140`). Registry-load-time enforcement (`versioned-rpc.ts:285-352`): within a major, minors must be purely **additive** (structural JSON-schema diff via `json-schema-fingerprint.ts:238-301` — a normalized shape, not a hash); a major bump **must** contain ≥1 breaking change or the registry refuses to load ("could have shipped as a minor", `:345-349`). Streams deliberately get less machinery (`versioned-stream-rpc.ts:19-22`, `stream-compat.ts:131-158`): additive minors within a major, **reconnect on major skew** (no frame bridging exists at all), per-method isolation (skew on `chat.subscribe` doesn't block `epic.subscribe`), plus additive capability negotiation — `openAck.capabilities: string[]` defaulting `[]` for older hosts (`stream-ws-protocol.ts:89-99,130-137`).

**What**: A complete answer to "client and server ship independently and *will* skew": declare versions per-method (not per-surface), exchange manifests once at connect, verify with a pure oracle both sides can run, put every transform on the newer side, force honesty at authoring time (additive minors; majors must break), and give long-lived streams the cheap rule (reconnect) instead of the clever one (bridging).

**Gap in jido_radclaw** (verified 2026-07-03): zero protocol versioning on any client-facing surface. The WS channel joins with `%{status: "connected"}` — no version field (`lib/jido_claw/web/channels/rpc_channel.ex:6-8`); `UserSocket.connect/3` has no version handshake; `/health` is the *only* surface reporting app version (`web/controllers/health_controller.ex:23-31`); nothing compares versions across cluster nodes (leader election is lowest-node-name-wins, `core/cluster/leader.ex:164-180`); MCP protocol-version negotiation exists but is entirely dep-owned (`anubis_mcp`), uncustomized. Argus §6.3 flagged codegen tooling as the open question — the scan correctly reframed skew handling as the harder half, and it is greenfield here.

**Why it matters**: Argus's client is a PWA — a **service-worker-cached app shell keeps running old JS after the cluster upgrades**, so client-newer *and* client-older skew both occur in normal operation, exactly traycer's topology (their host is "always-latest", their clients lag — ours inverts per-deploy but the math is identical). GraphQL natively covers the additive-evolution half for the query surface (add fields + `@deprecated` ≈ additive minors); what GraphQL does *not* cover is the Channels layer (hand-shaped payloads, no introspection) and the "who should upgrade" verdict. Traycer's stream rules are almost embarrassingly cheap to adopt and match our reconnect-and-refetch design (OVERVIEW §4.2 already specifies catch-up via `workflowEvents(afterSeq:)`).

**Adoption sketch**: (a) A `JidoClaw.Web.Contract` module: per-topic (not per-method) `{major, minor}` for each Channel topic family (`workflows:run:*`, `gates:user:*`, …), declared next to the payload-shaping code. (b) Client sends its manifest in `UserSocket` connect params; the reply carries the server manifest + `capabilities: []`; a pure `Compat.check/3` (their oracle translated — trivially portable, it's ~100 lines of pure logic) returns ok or a structured verdict with `upgrade_guidance`. (c) Adopt the stream rule wholesale: additive minors only; major bump ⇒ client is told to refresh (service-worker `skipWaiting` + reload — the PWA "update available" flow); never bridge live frames. (d) On the GraphQL side, skip per-method versioning entirely (OQ-1) — the golden-SDL guard (TR1-2) plus additive discipline covers it. (e) Reuse the verdict surface for node-vs-node skew during rolling upgrades: `/health` already reports version; the `cluster` GraphQL field (OVERVIEW §4.3) should carry per-node `version` and the UI can flag a mixed-version cluster. Deliberately not borrowed: request/response bridging chains and downgrade paths — a one-operator tailnet can always refresh the client; authored bridges are enterprise-grade machinery we don't need (TRACK inside OQ-1 if a native mobile client ever ships with slow release cycles).

### TR1-2. Released-surface golden test + "new capabilities ride existing names"

**Recommendation**: BORROW-PATTERN — has a do-today slice (MCP) independent of argus.

**Where in traycer**: `protocol/src/host/__tests__/released-surface-compat.test.ts:31-34` — CI asserts `Object.keys(hostRpcRegistry).sort()` equals a committed golden (`__fixtures__/released-method-names.ts`, auto-generated, 115 names, "do not edit by hand"); regeneration is a deliberate act whose diff "is the reviewable record of that decision" (`:26-29`). It does **not** freeze schemas — those evolve under the registry-load additivity validators (TR1-1); it freezes the *name set*, because their handshake fails closed on set inequality. Born from two real incidents (`:12-18`; `versioned-stream-rpc.test.ts:300-349`): `1.0.1-rc.1` added a *new method name* (`worktree.readScriptsAtRef`), which made every RPC against shipped `host-v1.0.0` peers fail; and `chat.subscribe` was major-bumped, breaking all shipped hosts — fixed as an additive 1.1 minor. The distilled rule (`registry.ts:295-306`): **new capabilities ride a new `{major,minor}` of an existing method, never a new method name** — the worktree scripts-preview shipped as `listByWorkspacePaths@1.1` for exactly this reason.

**What**: The deployed contract surface is pinned by a trivial golden test; changing it is possible but *loud* — the diff of an auto-generated fixture is the review artifact. Schema evolution and surface evolution are governed by different mechanisms, each matched to what actually breaks peers.

**Gap in jido_radclaw** (verified 2026-07-03): no contract-freeze test of any kind. Our nearest precedent is runtime, not CI: the replay definition-fingerprint (`orchestration/definition_fingerprint.ex:77-106` — sha256 over a deterministic `:erlang.term_to_binary` of an *allowlisted* canonical term, with `description` and `deadline` explicitly excluded and a `:v1` collision tag; drift blocks replay at `replay.ex:205-221`). That module is our house fingerprint idiom and the right style to extend — but nothing guards the MCP tool list (26 tools, hand-enumerated in `core/mcp_server.ex`), the channel payload shapes, or (future) the GraphQL SDL.

**Why it matters**: Argus multiplies deployed-contract surfaces: GraphQL schema, Channels payloads, MCP tools/resources, all consumed by clients we don't redeploy in lockstep (the PWA, editor MCP clients). Every one of them can be broken by an innocent rename. The golden-test discipline costs ~an hour per surface and converts "we broke the phone client" into a failing CI diff. The incident pedigree is the evidence: even a team whose *whole product* is the protocol shipped a name-set break within their first release candidate.

**Adoption sketch**: (a) **Today, no argus dependency**: a test asserting the MCP served-tool name list + resource URIs against a committed golden (the server module is static; the test is ten lines) — plus the same for the `jido://workflows/catalog` stage-name set, which editor clients already consume. (b) At argus step 2: `mix` task dumps the Absinthe SDL to a committed golden; a test diffs current-vs-golden with an additive-only checker (field/type removals or type changes fail; additions pass) — graphql-inspector semantics re-implemented over the SDL AST, or run via the JS tool in CI if we'd rather not write the differ. (c) At argus step 3: the Channels payload registry from TR1-1(a) gets the same name-set golden. (d) Adopt the naming rule as doctrine in the contract module docs: extend an existing topic/tool with a version, don't mint sibling names for variants.

### TR1-3. Worktree schema and lifecycle cribs for the argus `Worktree` resource

**Recommendation**: BORROW-REFERENCE — study before argus step 1 (§3.1–3.3) models the resource. This is the reference the scan hoped for, and it holds up.

**Where in traycer**: `protocol/src/host/worktree-schemas.ts`. The persisted per-worktree record (`:51-70`, trimmed):

```ts
worktreeBindingEntrySchema = {
  workspacePath, mode: "local" | "worktree", repoIdentifier: {owner, repo} | null,
  worktreePath: string | null, branch: string | null,
  isPrimary: boolean, isImported: boolean,
  setupState: "not_required"|"pending"|"running"|"succeeded"|"failed"|"cancelled",
  setupTerminalSessionId: string | null, setupExitCode: number | null,
  setupFailedAt: number | null, createdAt: number,
}
```

A binding is `{entries: [...]}` — multi-repo workspaces are first-class, one entry per folder, modes mixable (`:6-11,30-35`). Setup runs in a real terminal session whose id/exit-code/failure-time are *recorded on the entry* (`:59-63`); retry returns a fresh terminal session (`:490-501`). Branch selection (`:115-131`): `{type:"new", name, source, carryUncommittedChanges}` (fork from source branch, optionally carrying tracked+untracked work — the "carry-stash" path) or `{type:"existing", name}` ("`git worktree add` without `-b`"); no enforced branch prefixes. Attach-to-existing-checkout is an *intent kind* (`import`, `:160-186`) that materializes as `mode:"worktree"` + `isImported:true`, not a third mode. `missingWorktreePaths` (`:577-585`) is "computed, ephemeral disk-truth… never persisted" — recomputed each read on the owning host, and it gates agent launch. Ownership: every mutation is scoped by an owner triad `{epicId, ownerId, ownerKind: chat|terminal-agent}` (`:329-333`); the epic-level view (`:590-652`) dedups rows by `(hostId, runningDir)` and carries `sources: [{ownerKind, ownerId, …}]` — **N owners sharing one checkout is a modeled state, not an error**.

**What**: A worktree record that separates four concerns our sketch currently blurs: (1) *what kind of dir this is* (mode + isImported), (2) *is it ready* (the six-state setup machine with real telemetry), (3) *does it still exist on disk* (computed at read, never trusted from storage), (4) *who is using it* (owner refs aggregated per checkout).

**Gap in jido_radclaw** (verified 2026-07-03): no worktree functionality — grep of `lib/` + `test/` finds exactly one hit, the `--worktree` git-config flag token in the shell-command analyzer (`security/shell_command/git.ex:150`). The argus sketch (OVERVIEW §3.1) has `branch`/`status: :active|:idle|:archived`/`node`/`last_activity_at` — a *lifecycle* status only. Nothing models setup, disk-truth, import-vs-created, or multi-attachment; `Projects.Project` has no worktree relationship and no active/archived concept (`projects/project.ex:22-56,72-102`).

**Why it matters**: Setup is where worktree UX lives or dies — `git worktree add` is fast, but dependency install/env prep (TR2-2) is slow and fallible, and a worktree that "exists" but failed setup is a trap for the next run dispatched to it. Traycer records enough to answer "why is this worktree unusable" from the record alone (state + exit code + failure time + the terminal session to replay). And the disk-truth discipline matters doubly for argus: our DB is *shared across nodes* while checkouts are per-machine, so a stored "exists" bit would be wrong the moment a laptop reformats — OVERVIEW §3.3 already gestures at this ("without relying on path-existence checks at query time"); traycer shows the working shape: persist nothing, compute on the owning node at read, gate dispatch on it.

**Adoption sketch**: Extend the argus §3.1 resource sketch before building: (a) keep `status` for *lifecycle* (`:active|:archived`) but add a separate `setup_status` (their six states map cleanly; `not_required` covers imported/attach cases) plus `setup_exit_code`, `setup_failed_at`, and — our idiom — the `out_…` ref of the captured setup output (`Conversations.ToolOutput`, which is exactly their setupTerminalSessionId shape done our way). (b) Add `origin: :created | :imported` (their `isImported`) — an imported checkout must never be auto-deleted by cleanup (TR2-1). (c) Branch creation contract: `{branch, source_branch, carry_uncommitted?}` — the carry option is real workflow value (start a worktree from your dirty tree) and costs one flag. (d) Do **not** persist path-exists; expose a `verify_on_disk` action that runs on `worktree.node` (via the same node-affinity RPC the runs use) and gates run placement, mirroring `missingWorktreePaths`. (e) Skip the owner triad as a column — our equivalent is the `has_many :workflow_runs / :forge_sessions` relationships argus already sketches; the borrowable bit is the *UI aggregation* (worktree list rows show attached-consumer badges, deduped per checkout).

### TR1-4. Node affinity: identity-stamped-at-mint, clone-not-migrate

**Recommendation**: BUILD-ON — argus §3.3 owns the design; traycer supplies the doctrine and one design decision argus hasn't made yet.

**Where in traycer**: chats and TUI-agent records carry `hostId` = "device the session was minted on… bound to that host for life… **cross-device continuation is clone-not-migrate**" (`persistence/epic/chat.ts:22-37`, `tui-agents.ts:22-24,50`); `hostId` is an opaque device id (not a hostname — `os.hostname()` is only a human label, `traycer-cli/src/auth/login-flow.ts:46`). The binding record physically exists only in the owning host's SQLite and is projected into snapshots at subscribe time — "cloud collaborators must not see another collaborator's local paths" (`worktree-schemas.ts:1-6`; `host/agent/gui/subscribe.ts:329-332`); other devices see foreign worktrees only as `(hostId, runningDir)`-tagged selector rows (`worktree-schemas.ts:619-652`). Per-host RPC routing: mutations capture the target host id at mutation time (`use-worktree-retry-setup-mutation.ts:36-73`).

**What**: Three commitments that together make multi-device worktrees coherent: (1) node identity is stamped once, at mint, on the owning artifact; (2) work never silently migrates — continuing on another machine is an explicit clone that mints a *new* artifact there; (3) everything path-shaped is readable only through the owning node.

**Gap in jido_radclaw** (verified 2026-07-03): the conventions exist but the doctrine is undeclared. Node identity: `WorkflowLease.node_identity/0` is `to_string(Cluster.local_node())` (`orchestration/workflow_lease.ex:107-109` — note the `Cluster` wrapper, **not** raw `Node.self()` as OVERVIEW §3.3 says; use the wrapper, it's the testable seam), already stored in `WorkflowRun.claimed_by` (`workflow_run.ex:403-406`). No `node` column exists on Workspace or anywhere else yet. Two seams-pass findings sharpen the §3.3 plan: **(i)** Workspace's partial-unique identities are `(tenant_id, user_id, path)` / `(tenant_id, path)` (`workspaces/resources/workspace.ex:245-251`) — the same path on two machines (a repo cloned at `~/workspace/foo` on both) would *collide*, so `node` must join the identity keys and the `identity_wheres_to_sql` SQL (`:28-31`) plus `Resolver.do_register`'s upsert attrs (`resolver.ex:36-58`), not just the attribute list — "mostly additive" in the OVERVIEW undersells this one edit. **(ii)** `Workspace.path` is read at runtime only for two display strings (`cli/repl.ex:375`, `cli/run_command.ex:316`); real filesystem access takes call-time `project_dir` — so the shared-DB-path risk is cosmetic today, and stays manageable after argus as long as run placement (not path reads) carries the affinity.

**Why it matters**: Argus's §3.4 delta 4 (claim runs on `worktree.node`) covers *placement*; what it doesn't yet answer is the operator story "this branch's work should move to my desktop." Without a stated rule, that becomes an ad-hoc migration feature — checkout state, sandbox metadata, and lease history all pretend to teleport. Traycer's answer is the cheap and honest one: **clone** — create a sibling worktree on the target node from the same branch; the old one archives. Same shape as our lease reclaim philosophy (a new claim, not a moved claim).

**Adoption sketch**: (a) Write clone-not-migrate into the Worktree domain doc as an invariant: `Worktree.node` is immutable after create; "move" = `clone_to(node)` action (new Workspace + Worktree on the target, `source_branch` = same branch) + archive of the original. (b) Use `WorkflowLease.node_identity/0` for both new `node` columns (OVERVIEW §3.3 already says this; keep the `Cluster.local_node()` correction). (c) Fold finding (i) into the §3.1 migration plan (identity keys + partial-index SQL + resolver upsert). (d) **Deliberate divergence, record it**: traycer hides foreign paths as a privacy boundary (multi-user cloud); argus *shares* paths in Postgres by design (single operator, tailnet, and the UI wants to show them — OVERVIEW §2.6 surfaces node ownership everywhere). We take the affinity doctrine, not the privacy projection.

## Tier 2 — adopt while building the corresponding argus step

### TR2-1. Worktree deletion as a phased, guarded, observable operation

**Recommendation**: BORROW-PATTERN (argus step 1, the `archive`/destroy actions).

**Where in traycer**: `protocol/src/host/worktree-delete-stream.ts` — delete is a *stream* because it's a pipeline with live output (`:1-34`): busy-check → teardown script (stdout/stderr streamed) → `git worktree remove --force` + prune. Server frames `started{hasTeardown} | phase{teardown|remove} | output{channel,chunk} | complete{deleted} | failed{reason}` (`:55-89`). Guards: **in-use is a hard host block** (bound to an active chat/agent or an active run's cwd — `worktree-schemas.ts:537-540`), **dirty tree is a client warning only** ("Discard N uncommitted change(s)?", `worktrees-settings-panel.tsx:1175-1206`) then `--force`; `gitRemovable: false` (orphaned dir, main repo unresolvable) falls back to `fs.rm` (`:544-546`). `worktree.listAllForHost` is a disk walk of `~/.traycer/worktrees/` surfacing orphans whose owning epic died (`:523-529`). Client caps parallel deletes at 2 (`use-worktree-delete-run.ts:49`).

**What**: Deletion respects that a worktree is live infrastructure: refuse while in use, warn on data loss, run teardown observably, and treat "the DB forgot about this checkout" (orphans) as a first-class discoverable state rather than leaked disk.

**Gap in jido_radclaw** (verified 2026-07-03): no worktree ops exist; the argus sketch has an `archiveWorktree` mutation and notes "`git worktree add/remove` are real shell ops; orchestrate via a tool/action" (§3.1) — no busy-check, no teardown, no orphan story yet.

**Why it matters**: We have better primitives for every guard than traycer does — leases + `AgentTracker` answer "in use" authoritatively where they scrape; `Forge.PubSub`/`RunPubSub` already carry progress; cron + leader election host the orphan sweep. The pattern is worth taking precisely because it lands on machinery we already run.

**Adoption sketch**: `Worktree.destroy` as a small workflow (or a supervised action) on the owning node: (1) busy-check = any non-terminal `WorkflowRun` on this worktree (DB) + live `AgentTracker`/Forge session check (in-memory, local to the owning node); hard-refuse with the holder named. (2) Teardown script (TR2-2) with output captured to a `ToolOutput` ref and progress on `worktrees:project:<id>` PubSub (the topic argus §4.2 already plans). (3) `git worktree remove` + prune; `fs.rm` fallback for orphans. (4) Orphan audit: a leader-owned cron comparing each node's worktree root against Worktree rows — surfacing, never auto-deleting (our reaper-ownership lesson from crabbox CB1-2 applies). Dirty-tree: warn in UI, require an explicit flag on the mutation. (Connective note, 2026-07-03: the later same-day digs completed the teardown spectrum around this entry — weakest to strongest: CCC delegates deletion to the agent via prompt, the anti-pattern ([CC2-3](../claude-command-center/FEATURES-WORTH-BORROWING.md)); termic runs `remove --force` behind a bare confirm, no busy/dirty guard ([TM2-4](../termic/FEATURES-WORTH-BORROWING.md)); muxara hard-blocks teardown on uncommitted changes ([MX2-2](../muxara/FEATURES-WORTH-BORROWING.md)); this phased delete is the strong end — and Xantham independently approval-gates `worktree remove --force` in its own bash gate ([XA3-2](../Xantham-system-blueprint/FEATURES-WORTH-BORROWING.md)), the emdash EM2-3 thesis from outside.)

### TR2-2. Committable per-repo environment scripts with per-worktree override

**Recommendation**: BORROW-PATTERN (argus step 1; also feeds Forge sandbox provisioning).

**Where in traycer**: `worktree-schemas.ts:79-100` — `workspaceScripts = {setup, teardown, updatedAt}` where each is an `OsScript {default, macos|windows|linux: string|null}`; persisted in **committable** `<repoRoot>/.traycer/environment.json` (deliberately moved *out* of host-local SQLite so it's shareable/reviewable, `:87-93`). A create-time intent may carry a per-worktree override that the host writes into the *new* worktree's `environment.json` "without ever writing the source checkout" (`:133-145`). `listByWorkspacePaths@1.1` previews committed scripts at a ref via `git show <ref>:.traycer/environment.json` — read without a checkout (`:241-265`).

**What**: Environment setup/teardown as repo-owned, version-controlled data (not per-machine config), with a clean override path for experiments and a no-checkout preview.

**Gap in jido_radclaw** (verified 2026-07-03): nothing per-repo drives workspace/worktree provisioning. `.jido/` is committed config (agents/skills/strategies), so the house pattern exists; the argus sketch mentions worktree shell ops but no setup content at all. (Answered by the emdash dig, 2026-07-03 — [emdash EM1-1/EM1-2](../emdash/FEATURES-WORTH-BORROWING.md): traycer's committable + override-at-create + preview-at-ref trio confirmed the richer *scripts* contract — emdash persists no setup state and its local DB layer overrides the committed file; emdash contributes what traycer lacks: preserve-patterns untracked-file carryover and idempotent step decomposition.)

**Why it matters**: Every parallel-worktree product converged on lifecycle scripts because a bare checkout isn't runnable (deps, env files, generated code). For argus specifically: setup is what `setup_status` (TR1-3) tracks, teardown is what deletion (TR2-1) runs, and the *committable* choice means all cluster nodes see the same script through the repo itself — no config distribution problem, which matters more for us than for them (they have cloud sync; we have N nodes + one repo).

**Adoption sketch**: `.jido/environment.yaml` (house format) with `setup:`/`teardown:` command lists; read by the Worktree create/destroy actions; output captured to `ToolOutput` refs and reflected in `setup_status`/`setup_exit_code`. Skip per-OS resolution until a real need (single operator, two darwin/linux nodes — YAGNI; note it as the extension point). Keep the override-at-create trick (write the override into the new worktree only). Preview-at-ref is free with `git show` when a UI wants it. Security note ours not theirs: these scripts execute on worktree create — they're repo-controlled code execution, same trust class as the `bash deploy.sh` residual in the tool-approval doctrine; run them through the Forge shell runner / `run_command` pipeline (approval-gated, output-shaped), never a bare `System.cmd`.

### TR2-3. `expectedSeq` revision CAS — the corrected mechanism for argus §5

**Recommendation**: INDEPENDENT (surfaced by this dig's seams pass, worth doing regardless of traycer; traycer itself has no equivalent — convergent-shape credit goes to CCC's mtime-409, per the scan).

**Where in traycer**: n/a — this entry corrects the *argus* sketch using what the seams pass found while mapping the edit-and-resume gap.

**What / Gap in jido_radclaw** (verified 2026-07-03): argus OVERVIEW §4.1/§5.4 sketches `reviseStepOutput(stepId, output, expectedSeq)` with "optimistic locking via the append CAS" / "the event append is the CAS." **No such CAS exists.** The event append is *pessimistic*: `Changes.Allocate` takes `FOR UPDATE` on the parent run row, computes `seq = max+1` under that lock, and the unique `(workflow_run_id, seq)` index is only a backstop (`orchestration/workflow_event/changes/allocate.ex:171-195`, `workflow_event.ex:13-16,43-46`); `seq` is never caller-supplied (`:70`). The only CAS in the append path is the WS1 *lease-token* fence (`claim_fenced?`, `allocate.ex:107-117,160-169`) — ownership, not sequencing.

**Why it matters**: The design intent (reject a revision written against a stale read) is right and cheap — but it's **net-new machinery**, not a wrapper over something that exists, and pretending otherwise would surface as a confusing implementation ticket mid-argus-step-4. The fix is small precisely because the pessimistic lock exists: check *inside* it.

**Adoption sketch**: The revision-append action accepts `expected_seq`; `Allocate` (or a sibling change on the revision event kind) compares it to the current max seq *after* acquiring the existing `FOR UPDATE` lock — mismatch returns a typed `stale_revision` error carrying the current seq, and the client refetches + re-edits (the CCC 409 flow). Two lines of check inside the lock; the GraphQL field error is the bigger half. A dated correction has been added to the argus OVERVIEW (§5.4) pointing here. **CCC dig sharpening (2026-07-03)**: the parenthetical above credited "the CCC 409 flow" — the dig verified the *server* half (typed 409 carrying the fresh mtime; real convergence) and found the *client* half was never built (conflicts dead-end; the only recovery loses the operator's edits). So carry the head revision ref in the `stale_revision` error (one-round-trip refetch) and keep the operator's buffer authoritative across it — acceptance criteria in [CCC CC1-3](../claude-command-center/FEATURES-WORTH-BORROWING.md).

### TR2-4. Skew recovery: probe deep, verdict → routed action, block don't degrade

**Recommendation**: BORROW-PATTERN (argus steps 2–3+, the operator-facing half of TR1-1).

**Where in traycer**: `clients/traycer-cli/src/doctor/engine.ts:545-615` — the doctor probes with a real *authenticated* RPC ("TCP-open ≠ usable"), then routes: `routeIncompatibleRecovery` maps the structured verdict to exactly one action per install vector (`compat-recovery.ts:73-106` — host-stale → "traycer host update"; client-stale → the right upgrade hint for desktop/npm/homebrew/apt; `DOWNGRADE_UNSUPPORTED` with no guidance *synthesizes* host-stale, `:63-71`, so a restart loop can't happen). The GUI **blocks** on terminal incompatibility — full-screen "Host update required" card with one action, not a banner over a half-working app (`compatibility-state.ts:89-93`; `local-host-gate.tsx:450-566`) — with `/settings` exempt as the escape hatch (`:38-50`). Success is cached `staleTime: Infinity` keyed by host id (re-probe only on real host swap, `:43-87`).

**What**: Skew handling as operator UX: detect with a probe that exercises the real path, classify to a structured verdict, present exactly one correct action, and refuse to run degraded.

**Gap in jido_radclaw** (verified 2026-07-03): no probe surface beyond unauth `/health` (version + node only); no verdict vocabulary; nothing blocks a stale client today because nothing versions it (TR1-1's gap).

**Why it matters**: The PWA's stale-shell case (TR1-1) needs precisely this UX: on connect-time major mismatch, a full-screen "update available — refresh" that triggers `skipWaiting`, not a subtly broken dashboard. And mixed-version *clusters* during rolling upgrades deserve the same honesty in the `cluster` view: name the stale node, say what to do.

**Adoption sketch**: Rides TR1-1's oracle. Client: terminal-incompat verdict → full-screen refresh gate in the SPA (settings/diagnostics route exempt). Probe: keep `/health` unauth for liveness, add the authenticated `cluster` GraphQL field as the deep probe (it exercises auth + GraphQL + fan-out in one call). Cluster view: per-node `version`, leader-flagged, mixed-version banner naming the lagging node. Skip install-vector routing — our "vectors" are one PWA and `git pull` on nodes.

### TR3-1. Restore audit-pair: capture manifest + per-file honest results

**Recommendation**: BORROW-PATTERN (small), targeted at argus §5's revision/resume events.

**Where in traycer**: `protocol/src/persistence/epic/checkpoint-manifests.ts` — capture manifest (`:94-103`: `schemaVersion` literal, `capturingUserId`, `capturingHostId`, `allowedRoots`, `workingDirectory`, entries with `beforeHash`/`afterHash`/`undoable`/`reason`) paired with `restoreStartedManifest` + `restoreResultManifest` whose per-file results are `restored | skipped | failed` with reasons (`binary`, `storage_full`, `capture_failed`, `denied`, `not_intercepted`) (`:108-130`; dialog `restore-checkpoint-dialog.tsx:430-443`). **What / why it matters here**: The undo *itself* leaves an audit trail that never rounds up — a restore that skipped three binary files says so, per file, forever. That's camus's honest-terminal-status doctrine applied to a rollback, and argus §5's resume should inherit it: when `GateResume` promotes a head revision, the resume event should record *which* revision (ref + version) it promoted and what the original was; when a revision is rejected server-side (malformed diff, §5.5), that's a recorded outcome, not a silent 400.

**Gap in jido_radclaw** (verified 2026-07-03): resume today seeds only the decision atom (`gate_resume.ex:160-167`); there is no revision machinery yet (that's the argus delta itself) — this entry is a design constraint for it, not a gap fix. **Adoption sketch**: fold into the argus step-4 revision-event design: `step_output_revised` events carry `{art_ref, version, edited_by}`; the resume event carries `promoted_revision` (or `original`); rejected revisions append a `revision_rejected` event with the validation reason.
