# Features Worth Borrowing from osa-claude-code

Exploration notes — not a plan, not a commitment. **Inventory: 2026-07-02**, against osa-claude-code @ `0999c62` (2026-04-02, the entire history: 4 commits over 8 minutes, one code drop + three README rewrites) and jido_radclaw @ `ff39bbc9` (main). Cites are firsthand reads of both trees, accurate to within a few lines.

Source: `~/workspace/research/osa-claude-code` — [Miosa-osa/osa-claude-code](https://github.com/Miosa-osa/osa-claude-code), **License: TBD** (the README's own last line; there is no LICENSE file). Self-description: *"An open-source AI coding agent for your terminal, built in Elixir… an Elixir-native port of Claude Code CLI."* That is exactly what it is: a **machine-scale transliteration of Anthropic's Claude Code**, reverse-engineered from the product's ~1,902-file TypeScript bundle into ~689 `.ex` files / ~187k LOC under `lib/`, down to a pure-Elixir reimplementation of Claude Code's reverse-engineered `cch=` billing-header signing (`utils/cch.ex`, credited to a third party's RE writeup). Shape: Elixir 1.17+/OTP 26, SQLite + ETS + `persistent_term`, `term_ui` TUI, hand-rolled multi-provider clients over Req, a built-in "privacy gateway" Plug. **Tests: 2 files, 9 lines total** (`claude_code_test.exs` = 8, `test_helper.exs` = 1). No behavioral coverage of anything.

**Is it using OSA?** No — the user's open question, answered firsthand. They are **GitHub-org siblings with zero code relationship in either direction**: osa-claude-code neither depends on nor references OSA (grep clean across `lib`, `mix.exs`, `config`), and OSA's only "claude code" mentions are archived design docs *studying* Claude Code's flows plus a git-tool prompt — never this repo. Different lineage entirely: **OSA is an original "Signal Theory" agent; osa-claude-code is a transliteration of Anthropic's product.** Treat them as unrelated subjects that happen to share an org.

**Honesty calibration, before anything else.** This is the opposite failure mode from OSA. OSA's problem was *polished orphaned code* — you had to distrust the moduledocs and read call-sites to find the dead subsystems. osa-claude-code's problem is that **it does not run at all**, and the break is at the spine: the only reachable CLI path (`cli.ex` REPL / `-p` one-shot → `session.ex`) builds a tool-less, hardcoded-stub system prompt and then calls **`ClaudeCode.Query.run/2`, a module that does not exist** (only `ClaudeCode.Query.Query/.Engine/.ToolRunner/.ContextBuilder` do) — so the first user message raises `UndefinedFunctionError` before any inference. The real agentic loop is reachable *only* through the library facade `ClaudeCode.query/2`, which nothing in the shipped CLI calls and which defaults `tools: []`. Below that first break sit more: the skills registry, the background-task manager, and the swarm coordinator are **GenServers never placed in the supervision tree and started nowhere** (their `init/1` ETS tables never exist → every lookup raises); the subagent path calls a nonexistent `ToolRegistry.tool_definitions_for_agent/0`; the permission engine, hook system, settings cascade, sandbox, and `/permissions` command are each either uncalled or wired against their own nonexistent APIs. A clean `mix compile` emits **918 warnings, 436 of them calls to undefined modules/functions** (`State.Store.get/0` at 11 sites, `ClaudeCode.Auth`, `Utils.Settings`, `Utils.Model`, an invented `File.real_path/1`). Of ~88 feature flags, ~76 are read nowhere. Every subsystem the five readers examined came back **DEAD or runtime-broken** — nothing in the repo is both novel and wired.

So the value proposition is unlike any prior subject. There is **no working Elixir worth lifting**: it doesn't run, and on quality grounds — 918 compile warnings, uniformly dead wiring — we wouldn't copy it even if it did. What remains is that, precisely *because* it is a faithful transliteration of the real Claude Code, a handful of its **contract shapes and prompts are reference-grade for what Claude Code itself does** — and those are worth reading, though for most of them we already have an equal-or-better source (our own other exploration docs). The right way to use them is the way copyright already points: take the *idea* — a prompt's section structure, a field list, an event catalog — and re-derive it in our own idioms rather than pasting expression. That keeps us on the unprotected side of the line regardless of the repo's bare "License: TBD" (a minor consideration for internal-only, never-distributed use anyway) and regardless of the fact that some artifacts — the compaction prompt above all — are Anthropic product text, not this repo's to give. Net: read for the shapes, write our own.

Companion docs: **osa** (`osa/FEATURES-WORTH-BORROWING.md`) is the primary cross-reference — OS1-1 (compaction resilience), OS1-3 (deferred tools), OS2-3 (skill disclosure), OS2-4 (hooks), OS2-6 (effort), and OQ-1/OQ-5 all have counterparts here, and every entry below refines or *confirms* one of them rather than opening new ground. **hermes** (T1-2 compaction, T1-4 error taxonomy, T1-6 progressive disclosure, T3-4 shell hooks). **alp-river** (AR-2 composer, AR-9 tiering seam — the real home of effort/model routing).

## Determination (TL;DR)

**SKIP as a codebase — nothing here is wired, nothing here is worth copying on quality grounds, and almost everything it attempts we already do (durably, tested, and better).** Its only use is as a *reference for Claude Code's own contract shapes*, and for most of those our OSA and hermes docs are already the plan. The net-new is small and entirely reference-grade: the canonical Claude Code compaction prompt (richer than the OSA one OS1-1 already queues), a concrete "what if the summarizer itself overflows" degrade step, a negative confirmation of our deferred-tools seam design (OQ-1), the complete SKILL.md field taxonomy + the frozen-snapshot-compatible skill-invocation lane (the user's stated interest — skill handling), and the authoritative Claude Code hook-event catalog for our OS2-4 sketch.

## Why not adopt osa-claude-code (as a dependency *or* as a source of code)

1. **It does not run.** The shipped CLI cannot complete one turn (`session.ex:219` → nonexistent `ClaudeCode.Query`); three central subsystem GenServers are never started; multiple cross-module calls target nonexistent functions; 436 undefined-call compile warnings; 2 test files / 9 lines. There is no "wired part" to depend on — the distinction the OSA doc could draw (dead subsystems around a good wired core) does not exist here.
2. **We'd take ideas, not code — which sidesteps the licensing question.** For internal-only, never-distributed use the repo's bare "License: TBD" is a minor consideration (copyleft would trigger on distribution, and copyright doesn't reach the ideas/interfaces we'd actually borrow). What we take from any entry below is a *shape* — a prompt's section structure, a frontmatter field list, an event catalog — re-derived in our own idioms, never a paste of their Elixir. So unlike the Apache-2.0 OSA doc there is no "Lift: verbatim with an attribution line" affordance here — and on quality grounds we wouldn't want one. (Genuinely separate from licensing, and best left alone regardless: the `cch=` billing signature is reverse-engineered to interoperate with Anthropic's paid API — we ignore it entirely.)
3. **It's an application-shaped transliteration, not a library.** Like OSA, there is no library seam — `privacy/`, `bridge/`, `upstreamproxy/`, `remote/`, the 100+ commands, and the term_ui TUI are all product surface. But unlike OSA it is also a transliteration of *another* product, so the shape is doubly wrong for us.
4. **Substrate mismatch at every layer** (identical to the OSA verdict): hand-rolled GenServer ReAct vs `Jido.AI.Agent`; SQLite + ETS + `persistent_term` vs Ash/Postgres; `settings.json` cascade vs `.jido/config.yaml` + Ash resources; hand-rolled provider clients vs ReqLLM. Anything stateful is a rewrite at every seam.

## How to read this document

- **Recommendation** axis: `BORROW-REFERENCE` (transcribe the contract/prompt shape, write fresh in our idioms) / `ALREADY-COVERED` / `SKIP`. **Nothing rates `ADOPT-AS-DEP` or a code lift** — see reason 2 above.
- **Lift** axis: **design-only** for every entry. There is no verbatim/reshape code lift here — it doesn't run, and we take ideas, not expression. Where an artifact *is* the deliverable (a prompt, a field list, an event catalog), the instruction is "re-derive an equivalent from the documented shape," not "copy the bytes."
- **Tiers**: Tier 1 = a reference artifact that materially sharpens an already-queued borrow. Tier 2 = a reference spec worth keeping for a future design decision. Tier 3 = a small pointer. IDs are `CC<tier>-<seq>`. First inventory — no Status lines.
- Per-entry fields: **Recommendation**, **Lift**, **Where in osa-claude-code** (with wired-in verdict), **What**, **Gap in jido_radclaw** (verified 2026-07-02), **Why it matters**, **Adoption sketch**.

## Tier 1 — Reference artifacts that sharpen an already-queued borrow

### CC1-1. The canonical Claude Code compaction prompt (9 sections) + injection wrappers

**Recommendation**: BORROW-REFERENCE (refines OSA OS1-1c). **Lift**: design-only — the prompt is Anthropic product text; re-derive our own structured variant from its documented shape.

**Where in osa-claude-code** (DEAD — reference only): `services/compact/prompt.ex:76-159`. The strings here are consumed only by `Services.Compact` (`compact.ex`), which has zero callers and itself calls a nonexistent `API.Client.messages/1` — so nothing exercises them. But the prompt *text* is a faithful transcription of Claude Code's own summarizer. It is a **9-section** structure (the OSA doc's OS1-1 pulled OSA's *8*-section variant — this is the richer, canonical original the OSA one imitates): 1. Primary Request and Intent · 2. Key Technical Concepts · 3. Files and Code Sections (with full snippets + why-it-matters) · 4. Errors and fixes (with user-feedback callouts) · 5. Problem Solving · 6. All user messages (non-tool) · 7. Pending Tasks · 8. Current Work · 9. Optional Next Step (with *verbatim quotes* of where work left off, to prevent drift). It ships three supporting pieces worth knowing: a **no-tools preamble + trailer** ("Respond with TEXT ONLY… tool calls will be REJECTED") wrapping every request; two **partial-compaction variants** (`_from` = summarize the recent tail; `_up_to` = summarize a prefix that will be *prepended* to a continuing session, where §8-9 become "Work Completed"/"Context for Continuing Work"); and the **injection wrapper** `get_compact_user_summary_message/3` — prefix "This session is being continued from a previous conversation that ran out of context…", an optional "read the full transcript at {path}" hint, and (on auto-compact) a "Continue… without asking the user any further questions. Resume directly — do not acknowledge the summary" trailer. `format_compact_summary/1` strips the `<analysis>` scratchpad and rewrites `<summary>` → `Summary:`.

**What**: the reference structure for a *structured* summarizer prompt, plus the continuation-injection framing.

**Gap in jido_radclaw** (verified): our `Reasoning.Compactor.Prompt.default_text/0` is a single dense-prose continuation prompt with a 5-item priority list (goal → committed decisions → tool results → open items → explicit-remember) and a "drop greetings/tool-noise/deliberation" list — good, and correctly built for the continuation audience, but *not* the sectioned format, and with no partial-vs-full variants and no auto-compact "resume directly" trailer. `build/3` already folds a prior summary in (continuity) and enforces a char budget. So we have the *plumbing* (prior-summary fold, budget, delimited injection via `RequestTransformer`) and lack only the richer prompt *shape*.

**Why it matters**: this is the single highest-value read in the repo, and it's precisely the "structured summary fields" residual hermes T1-2 and OSA OS1-1c both flagged. Adopting a sectioned prompt is a low-risk swap behind our existing Summarizer seam (the backend already takes a pre-built prompt string), and the partial/`_up_to` variant is directly useful if we ever summarize a prefix rather than a tail.

**Adoption sketch**: add a `Compactor.Prompt.structured_text/0` alternative (selectable via `compaction:` opts) that re-derives the 9-section shape in our voice, keeping our continuation framing; port the auto-compact "resume directly, don't acknowledge the summary" trailer into our injected block (we already inject a delimited user-role message — this is one sentence added). Keep it a *derivation* in our own voice — the borrowable thing is the section structure, not Anthropic's prompt text. Pair with CC1-2 for the overflow case. Do **not** replicate their dead wiring or the nonexistent `API.Client.messages/1` call.

### CC1-2. Degrade when the summarizer *itself* overflows (prompt-too-long retry)

**Recommendation**: BORROW-REFERENCE (feeds OSA OS1-1a degrade ladder / OQ-3). **Lift**: design-only.

**Where in osa-claude-code** (DEAD — reference only): `services/compact/compact.ex`. `@max_ptl_retries 3`; `do_compact_with_ptl_retry` retries the summarize call, and on a `:prompt_too_long` error calls `truncate_head_for_ptl_retry`, which `group_messages_by_api_round` (user→assistant/tool chunks) then **drops the oldest `max(1, floor(#groups * 0.2))` groups** (or a computed count to close a token gap), prepending a `"[earlier conversation truncated for compaction retry]"` marker if the head becomes assistant-first. Separately, `strip_images_from_messages` replaces image/document blocks (including inside tool_results) with `[image]`/`[document]` *before* summarizing. Constants worth noting: `@compact_max_output_tokens 20_000` ("p99.99 observed = 17,387"), a `@max_consecutive_failures 3` circuit breaker.

**What**: a concrete answer to the failure mode OSA's ladder didn't cover — *the summarize request is itself too large to send*. Drop oldest whole API-rounds and strip media, then retry, bounded.

**Gap in jido_radclaw** (verified): our Summarizer retries transient failures (timeout/exit/backend) up to `summarizer_max_retries`, but a genuine context-overflow *on the summarize call* is a deterministic error that retrying unchanged won't fix — we have no "shrink the summarizer input and retry" step, and no image/document stripping before summarizing. This is the tail of OSA OS1-1a: the degrade ladder handles the *conversation* overflowing; this handles the *summary request* overflowing.

**Why it matters**: on long tool-heavy sessions (exactly where compaction fires), the transcript handed to the summarizer can itself exceed the window — today that turns a best-effort compaction into a no-op and the oversized turn still fails. A bounded head-drop + media-strip keeps compaction making forward progress.

**Adoption sketch**: in `Compactor.Summarizer`, classify a context-overflow backend error (via the hermes T1-4 typed taxonomy, **not** substring matching) distinctly from transient errors; on it, shrink the transcript by dropping oldest turn-groups (we already have `Compactor.TurnGrouping`) and stripping media, then retry within the existing retry budget. Emit a `:compaction` Trace breadcrumb noting the degrade. Note the OSA-doc cross-ref: OSA's *conversation*-overflow recovery (OS1-1b) and this *summarizer*-overflow recovery are two different seams that both want the same typed classifier (OQ-3).

### CC1-3. The Claude Code skill model — frontmatter taxonomy + the frozen-snapshot invocation lane

**Recommendation**: BORROW-REFERENCE (refines OSA OS2-3 and answers OQ-5's lane question). **Lift**: design-only. **This is the user's stated interest ("skill handling").**

**Where in osa-claude-code** (DEAD — reference only): `skills/loader.ex` + `tools/skill.ex`. The `Skills.Registry` GenServer is never started (absent from `application.ex`, no `start_link` caller), so every lookup raises on a missing ETS table; and bundled skills carry a `:prompt_fn` closure while the Skill tool reads `:content`, so even a started registry would expand the 11 bundled skills (verify, debug, remember, simplify, batch, stuck, skillify, update-config, loop, lorem-ipsum, keybindings-help) to empty. But the *contract* is the real Claude Code design, and it is clean:
- **Frontmatter taxonomy** (`loader.ex:59-81, 131-180`): `name` (display), `description` (falls back to first non-heading paragraph), `allowed-tools`, `argument-hint`, `arguments` (named placeholders), `when_to_use` (auto-invocation guidance for the model), `user-invocable` (default true), `disable-model-invocation`, `context: fork` (run in a subagent), `agent` (named agent to dispatch to), `version`, `model` (`"inherit"` → nil), `effort` (low|medium|high|int), and `paths` (glob triggers — the OSA OS2-3 trigger-match analog). Discovery: `~/.claude/skills/<name>/SKILL.md` (user) then `<project>/.claude/skills/<name>/SKILL.md` (project), deduped by realpath.
- **Invocation lane** (`tools/skill.ex:107-200`, moduledoc `:16-40`): the model calls a `Skill(name, argument)` tool; the runtime expands the SKILL.md body — substituting `$ARG`/`$1`/`{{arg}}`/named `$<argname>` and `${CLAUDE_SKILL_DIR}`/`${CLAUDE_SESSION_ID}` — and **returns the expanded body as the tool result, which the loop then injects as the next user message**. That is: the catalog (name + description) is designed to live in the system prompt, while the *full instruction body arrives per-invocation via a tool-result → user-turn*, never mutating the system prompt.

**What**: two things — a complete, concrete field list for "what a first-class instruction-pack skill declares," and a delivery mechanism for full instruction text that does **not** thaw a frozen system-prompt snapshot.

**Gap in jido_radclaw** (verified): our skills are YAML-DAG *workflows* run by `run_skill` — the instruction-pack model doesn't exist; the closest injectable-instruction surface is the static per-template doctrine/persona (AR-5). Our system prompt lists a name+description catalog of loaded skills but there is no on-demand full-body injection, and our prompt is a **frozen snapshot by design** (cache warmth), so any per-turn instruction injection *must* ride a turn-scoped user-message lane. OQ-5 asks exactly where that lane is; OSA OS2-3 sketches trigger-matched injection but leaves the lane open.

**Why it matters**: this is the design the user intuited was worth borrowing, and it is the real Claude Code shape (not a MIOSA invention). The invocation lane is a direct, minimal answer to OQ-5 — "return the instruction pack as a tool result and let it become the next user turn" is inherently frozen-snapshot-safe. The taxonomy is the concrete schema for a skill/doctrine catalog if we ever add instruction-pack skills alongside our workflow skills. **The cautionary detail worth carrying**: here `allowed-tools` is *advisory metadata* with **no enforcement point built** (the tool stuffs it into result metadata; nothing consumes it) — so if we want a skill's tool allowlist to bite, the enforcement must be a named, tested consumer, not a field. (Also don't copy the hand-rolled frontmatter YAML parser — it silently drops multi-line lists; use a real YAML lib as we already do.)

**Adoption sketch**: if/when we add instruction-pack skills: (a) adopt the frontmatter field set as our catalog schema (mapping `when_to_use`/`paths` to a trigger match, `context: fork`/`agent` to our subagent dispatch, `effort`/`model` to the AR-9 tier seam — one vocabulary, not two); (b) implement the invocation lane as "a `run_skill`-style tool returns the expanded pack body, injected as a turn-scoped user preamble" — the same lane compaction summaries already use, which resolves OQ-5 for both this and OS3-1 `@`-refs; (c) if `allowed-tools` should constrain the spawned executor, wire enforcement through the per-template reach path (`Consumer.modules_for_template`-style), tested. This is a design north star, gated on the prompt-cache-lane decision — not a now build.

### CC1-4. Deferred tool loading — the negative result that confirms our OQ-1 seam

**Recommendation**: BORROW-REFERENCE (confirms OSA OS1-3 / answers OQ-1). **Lift**: design-only.

**Where in osa-claude-code** (DEAD — cautionary): the per-tool `should_defer?/0` flag exists (~24 tools set it) and a `ToolSearch` tool exists (`tool_search.ex`) — but `should_defer?` is **read in exactly one place** (ToolSearch's own body); **no request-assembly path filters by it** (`tool_registry.ex tool_definitions/1`, `tools.ex get_tools/1` all return the full enabled set), so deferred tools are still advertised. The companion `always_load?/0` is overridden by zero tools. The tool-search **beta headers are never attached** to any request (`advanced-tool-use-2025-11-20` for 1p, `tool-search-tool-2025-10-19` for 3p — defined in `constants/betas.ex`, accessors uncalled). `ToolSearch` returns tool **names as plain text**, not schemas. And the famous `deferred_tools_delta` (see CC2-2) is only *preserved* on session save, never *emitted*. Dispatch resolves any registered name regardless of the flag.

**What**: a fully-built-out *decorative* version of deferred loading — which is exactly why it's useful: it isolates the one missing piece.

**Gap in jido_radclaw** (verified): all 33 native tools ship full schemas every request (`Jido.AI.ToolAdapter.from_actions/2` maps the whole list); MCP proxies attach on top. No defer/search mechanism. OQ-1 asks *where* the advertise-subset seam goes in our jido_ai stack.

**Why it matters**: this repo proves the seam decomposition OS1-3 hypothesized. **Advertise-subset** is a filter that belongs at tool-definition assembly (their `tool_definitions/1` — the one line they never wrote); **dispatch-any** already works via name lookup over the full registry (theirs does, unconditionally). And it demonstrates the trap: a **names-only ToolSearch is insufficient** — without either the server-side tool-search beta loading schemas or explicit next-turn schema injection, the model that "finds" a deferred tool still can't call it correctly. So our version must inject the discovered tool's schema (not just its name) into the next request, or ride the API beta.

**Adoption sketch**: unchanged from OS1-3's — a `defer?: true` marker; partition at agent build into advertised vs registered-only; a `JidoClaw.Tools.ToolSearch` action over the full registry that returns **name + description + input schema** (the correction this repo supplies). The open jido_ai question (OQ-1) stands: jido_ai derives both advertised schemas and dispatch from `config.tools`, so withhold-but-accept needs either an upstream advertised-subset option or a ToolAdapter-level render filter with all modules still registered. Approval-gating is unaffected (keys on name at execution). The real Claude API beta names above are a useful pointer if we ever prefer the server-side mechanism.

## Tier 2 — Reference specs worth keeping for a future design decision

### CC2-1. The Claude Code hook event catalog + matcher/exit-code contract

**Recommendation**: BORROW-REFERENCE (the authoritative spec for OSA OS2-4). **Lift**: design-only.

**Where in osa-claude-code** (DEAD — no executor exists): `utils/hooks/hooks_config_manager.ex:220-431` + `types/hooks.ex:16-342`. No hook fires from any live loop (the only loop-side runner is in the uncalled `services/tool_execution.ex`, reading a `context[:hooks]` nothing populates), and **there is no command-type hook executor anywhere** — no `System.cmd`/`Port` runs a hook's `command` with JSON on stdin (grep clean). So the "spawn shell command, feed JSON, exit-code-2 blocks" contract is *documented in metadata only*. But that metadata is the genuine, complete Claude Code hook spec: ~30 events (PreToolUse, PostToolUse, PostToolUseFailure, UserPromptSubmit, SessionStart/End, SubagentStart/Stop, Stop/StopFailure, Setup, PermissionRequest/Denied, Notification, Elicitation/ElicitationResult, CwdChanged, FileChanged, WorktreeCreate/Remove, PreCompact/PostCompact, ConfigChange, InstructionsLoaded, TaskCreated/Completed, TeammateIdle), each with `matcher_metadata` (a `field_to_match` — usually `tool_name` — matched by exact name, pipe-separated alternation `"Edit|Write"`, or empty = all); the `settings.json` shape (`{ "PostToolUse": [ { "matcher": "...", "hooks": [ { "type": "command", "command": "..." } ] } ] }`); and the decision contract (JSON stdout with `permission_decision: approve|block`, `updated_input`, `additional_context`, `continue`/`suppress_output`, plus an `{async: true, async_timeout}` mode, default 15000ms).

**What**: the reference event surface and decision contract for an operator hook system — far broader than PreToolUse/PostToolUse.

**Gap in jido_radclaw** (verified): no operator hook surface at all — `.jido/config.yaml` has no `hooks:` key; Trace + `Jido.Signal` topics are rich but reachable only from Elixir. This is exactly the OSA OS2-4 sketch.

**Why it matters**: if we build the OS2-4 observe-only sink surface, this catalog is the authoritative list of *what to let operators subscribe to* (lifecycle, permission, config/file, compaction, task, subagent), and it **validates our narrower posture**: Claude Code's real hooks can block/mutate/inject-context, which is more powerful and more dangerous than observe-only — so our deliberate "observe-only, argv-exec-no-shell, redacted payload, in-process gates keep veto" choice is a defensible divergence, not a gap. This repo is *not* a reference implementation (nothing executes), only a spec.

**Adoption sketch**: unchanged from OS2-4 — `hooks:` in `.jido/config.yaml` mapping signal patterns to `webhook`/`command` sinks; use this event catalog to seed the explicit allowlist of subscribable events (start with tool-complete, gate lifecycle, cron outcomes, compaction). Keep observe-only in v1.

### CC2-2. The `deferred_tools_delta` cache-fix on session resume

**Recommendation**: BORROW-REFERENCE, gated on OSA OS1-5 (CLI resume). **Lift**: design-only.

**Where in osa-claude-code** (WIRED — the one genuinely-wired, non-obvious thing in the whole repo): `utils/session_storage.ex:224-228, 752-757`. On the live save path (`Session.terminate` → `save_session` → `write_transcript`), `should_save_message?` **preserves exactly** `["deferred_tools_delta", "mcp_instructions_delta", "hook_additional_context"]` while dropping other attachments and all progress messages. The comment (ported from a community `cc-cache-fix`, ref issue anthropics/claude-code#2638) explains why: upstream once stripped `deferred_tools_delta` on save, so on resume the tool announcements re-emitted, **shifting the cached prompt prefix and burning `cache_creation` tokens**.

**What**: a specific, real gotcha — persisting/resuming a session against a cached prompt prefix requires preserving the exact attachment types that constitute that prefix, or you pay a cache-creation regression on every resume.

**Gap in jido_radclaw** (verified): we don't resume the REPL session today (`repl.ex` mints a fresh `SessionId` per boot — the OSA OS1-5 gap), so the bug can't bite yet. But the durable layer already hydrates `state.messages` from Postgres when rows exist, so the moment OS1-5 (resume) lands, this becomes live-relevant.

**Why it matters**: it's a non-obvious, money-costing detail that only shows up once resume exists — cheap to get right up front, annoying to diagnose later (a silent token-cost regression, not a failure).

**Adoption sketch**: when implementing OS1-5 resume, ensure whatever constitutes our cached prefix (tool schemas / MCP instructions / any per-turn deltas) is reconstructed *identically* on resume — either by persisting and replaying those specific message parts or by regenerating them deterministically. Add a test that resumes a session and asserts the reconstructed prefix is byte-identical to the pre-save one. Tie the work item to OS1-5, not now.

### CC2-3. Permission rule grammar + settings cascade + mode vocabulary

**Recommendation**: BORROW-REFERENCE, only if we ever add a rule-based permission surface. **Lift**: design-only.

**Where in osa-claude-code** (DEAD / partially-broken — reference only): `permissions/rules.ex` + `utils/permissions/{permission_rule_parser,shell_rule_matching,permission_mode,permission_update}.ex`. The engine is never consulted from the live tool loop (dispatch calls only `validate_input` + `execute`; `check_permissions/2` has zero invocations; the sophisticated `shell_rule_matching` has zero callers; the *wired* engine variant silently ignores content-scoped rules). But the *grammar* is the genuine Claude Code contract: rule strings `Tool` or `Tool(content)` (parens escaped `\(`/`\)`); three content pattern types checked **prefix → wildcard → exact** (legacy `git:*` prefix, `npm run *` glob compiled to anchored regex, exact equality); behavior precedence **deny > ask > allow > mode-fallback**; a settings cascade `policy/MDM > flag > user > project > local` (later overrides earlier, MDM highest) with a `{add_rules|replace_rules|set_mode|add_directories, ..., destination}` grant shape persisted per-layer; and a mode vocabulary `default | plan | accept_edits | bypass_permissions | dont_ask` (plus Anthropic-internal `auto`/`bubble`).

**What**: the reference grammar, precedence, cascade, and mode set for a standing-rule permission model.

**Gap in jido_radclaw** (verified): our model is deliberately different — a durable, single-use, fingerprinted `AgentCase` approval gate (ephemeral one-shot), plus a fail-closed shell analyzer. We have no path-scoped edit rules, no settings-cascade rule grammar, no permission modes.

**Why it matters**: our gate is a *different and, for our threat model, stronger* shape (fail-closed, durable, tenant-scoped) than standing allow/ask/deny rules. This entry exists so that *if* a "standing rule" surface is ever requested (e.g. an operator wants "always allow `Bash(git status:*)`"), the CC grammar/precedence/cascade is the known-good vocabulary to mirror — with the caveat that this repo's *matcher* is not a reference (the wired one ignores content rules; plan-mode "read-only" is decorative, not enforced). Take the grammar spec, not the implementation.

**Adoption sketch**: none now — our approval gate covers the need. If a standing-rule request arrives, adopt the `Tool(content)` grammar + deny>ask>allow precedence + the `{rules, behavior, destination}` grant shape, layered *above* (not replacing) the fail-closed gate, with a real tested matcher.

### CC3-1. Bash command prefix canonicalization (wrapper-unwrap + compound LCP)

**Recommendation**: BORROW-REFERENCE, trigger-gated (only if we ever want bash permission rules richer than tool fingerprints). **Lift**: design-only. **Where in osa-claude-code** (DEAD island — high-fidelity port, zero callers): `utils/bash/prefix.ex` (+ `parser.ex`/`bash_parser.ex` building a real AST with a `:parse_aborted` fail-closed sentinel). A genuine transliteration of Claude Code's tree-sitter-bash prefix machinery: `get_command_prefix_static/3` unwraps command wrappers (sudo/nice/timeout, via an `isCommand`-arg position spec) with recursion/wrapper-count caps, and `get_compound_command_prefixes_static/2` splits `&&`/`;` compounds and collapses them via a word-aligned longest-common-prefix — turning `sudo git commit -m x && npm run build` into a canonical set of rule prefixes. Consumed only by `utils/shell/`, which has zero external callers. **Gap**: our `Security.ShellCommand.analyze` gates by runner/interpreter *reach* with a fail-closed opaque floor — stronger for *gating*, but it doesn't *canonicalize* a command into rule prefixes (we fingerprint the whole call, we don't derive `git commit:*`-shaped keys). **Why it's only a pointer**: we have no rule surface to feed canonical prefixes into (see CC2-3), and our gate doesn't need them. If CC2-3 ever lands, this algorithm is the non-trivial piece worth reading (wrapper-unwrapping + compound LCP is easy to get subtly wrong). Until then, zero carrying cost — this entry just names the algorithm.

## Bottom line

osa-claude-code is the first exploration subject that **does not run** — a machine-scale, unlicensed transliteration of Anthropic's Claude Code whose spine calls a module that isn't there, whose central subsystems are GenServers no supervisor starts, and whose 918 compile warnings include 436 calls into the void. As a system it is not a cautionary tale about missing structure (the way OSA was); it is a *map* of a product we wouldn't lift from anyway — it doesn't run, and on quality grounds there is nothing here we'd copy. There is no wired part to depend on. Its worth is narrow and entirely reference-grade: because it faithfully transcribes the real Claude Code, a few of its *contract shapes* are the canonical ones — most usefully the 9-section compaction prompt (richer than the OSA variant OS1-1 already queues), the "what if the summarizer itself overflows" degrade step, the SKILL.md taxonomy and the frozen-snapshot-safe skill-invocation lane (the skill handling the user hoped to find — and the real Claude Code design, not a MIOSA one), and the authoritative hook-event catalog for our OS2-4 sink surface. Every one of those is a *refinement of something already in the OSA or hermes docs*, to be re-derived in our idioms rather than copied. Net: read it once for those shapes, fold them into the borrows already planned, and otherwise skip it — we already do, durably and tested, everything real it was reaching for.
