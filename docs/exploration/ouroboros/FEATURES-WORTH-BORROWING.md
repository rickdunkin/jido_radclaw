## Determination (TL;DR)

**Nothing to adopt as a dependency (Python, app-shaped, and a loop-owner — same structural reasons as gepa), but a real borrow list concentrated at the two ends where our composer is verifiably weakest: the front door (nothing sharpens an ambiguous ask before composing — triage's `ambiguous` signal is published and consumed by nothing *(true as inventoried; closed 2026-07-07 by OB1-1's adoption — Status below)*) and the verification floor (verify stages trust worker self-reports; premises carry no acceptance criteria).** Ouroboros's genuinely-wired mechanisms land on exactly those slots: a quantified ambiguity gate with anti-gaming floors, a structured spec artifact whose acceptance criteria flow into both prompts and verification, a transcript-grounded anti-fabrication verifier with a shell-output-masking analyzer, and a validated project-gate-command detector. Its failures are as instructive as its features: the dead PAL router is a mirror warning for our own wired-but-undeclared tiering seam, and its degenerate drift measurement validates our self-reported `scope-shift` choice.

## Why not adopt ouroboros as a dependency

1. **It's an application with a different product thesis.** Ouroboros *wraps* coding CLIs (it would happily drive us); jido_radclaw *is* the runtime. Its orchestrator, runtime adapters, TUI, and plugin marketplace are product surface for "sit between the user and their CLI" — no library seam exists for the parts we want.
2. **Loop-owner inversion, same as gepa.** The interview pipeline, auto state machine, and evolutionary loop all own state, budget, and scheduling in Python. Putting those loops outside OTP supervision, Ash durability, and the gate family inverts the platform.
3. **Persistence mismatch.** SQLite event store + file checkpoints + in-payload event versioning vs. Ash/Postgres event-sourced composer with typed projections. Their resume story is genuinely good (journaled `seed_json`, phase-level resume — `evolution/loop.py:651-806`) and *ours already works the same way, more durably*.
4. **The valuable parts are small and mostly data.** Weights, floors, regex banks (vague terms, secret flags, shell-masking checks), prompt skeletons, and a handful of pure decision functions. MIT + cross-language means the *tables and prompts* transcribe nearly verbatim with an attribution line (`Q00/ouroboros @ e905a41c, MIT`); the code is a rewrite at every seam regardless.

### OB1-3. Transcript-grounded evidence verification — the anti-fabrication floor

**Recommendation**: BORROW-PATTERN.

**Where in ouroboros** (real, tested — 89 test files — but **opt-in off by default** after #1202): default AC success upstream is trivial (`success = not message.is_error` + a `[TASK_COMPLETE]` prose marker, `orchestrator/parallel_executor.py:5749`). `fat_harness` mode replaces it: the agent must emit a **typed evidence record** (`commands_run`, `files_touched`, `tests_passed`) validated against a per-task-type profile schema (`:5972`), and `_verify_atomic_evidence_against_runtime_messages` (`:6098-6200`) cross-checks every claim against the actual tool-call transcript — **deliberately excluding the agent's final self-report message** so evidence can't support itself (`:6108-6110`). Unsupported claim ⇒ `FABRICATION_SUSPECTED`; supported-but-malformed ⇒ `EVIDENCE_FORM_MISMATCH` (`:6184-6191`) — the latter backed by a serious shell-analysis library (`:994-1412`): test-command detection, **pipefail/output-plumbing detection** (a test command piped through a filter that would mask a failing exit code), gradle/maven skip-flag detection, env-prefix stripping, alias normalization. The separate `verification/` package (612 LOC, wired in the evolution evaluator) applies the same philosophy more cheaply: LLM-extract tiered assertions from ACs once (cached by seed), grep-verify the constant/structural tiers, and **only ever flip a claimed pass to fail on a positive discrepancy** — "can't verify ⇒ trust the agent" (`verification/verifier.py:122-126`).

**What**: a deterministic floor under agent self-reports — claims must be backed by transcript facts the agent cannot forge, with output-masking treated as a first-class evidence defect.

**Gap in jido_radclaw** (verified): worker stages self-report through typed Envelope `signals` and prose, and nothing cross-checks claims against what tools actually ran. The substrate is unusually ready: every tool call already lands durably (`Conversations.ToolOutput`, full capture up to 512KB under refs; Trace events), `OutputShaper` deliberately keeps failure blocks verbatim ("compress the green, never the red"), and `Security.ShellCommand` already does deep command resolution (env prefixes, `-C`, `sudo`, `sh -c`, multiline, aliases) for the approval gate. The instinct even exists as a *human* rule — the repo's own working agreement forbids piping gates through `tail`/`head`/`grep` because "pipes mask exit codes and have shipped a false green before." Ouroboros codified our memory rule as an analyzer.

**Why it matters**: camus doctrine says verify deterministically where possible; this is the missing enforcement half for the composer's code path. A fixer that says "tests green" without a test invocation in its transcript, or with the invocation piped through a filter, is precisely the false-green the review loop exists to catch — and catching it is a pure fold over data we already store. Heed the upstream rollback (#1202): as a hard executor gate it broke layered scaffolds; as a *verify-stage input* it's all upside.

**Adoption sketch**: (a) A pure `JidoClaw.Verify.Evidence` module: given a stage's claims and the wave's tool-call records (Trace + `ToolOutput` refs, already tenant/session-scoped), classify each claim `supported | unsupported | form_mismatch`. (b) Producer side: the coder/fixer Envelope schema gains an optional `evidence` block (commands_run/files_touched/tests_passed — string lists, per the Zoi/Envelope round-trip rule), requested via a doctrine slice (AR-5 seam; pairs with the existing `confidence_tagging` slice). Absent block ⇒ posture unchanged. (c) Consumer side: the review wave (or a cheap pre-review check) receives the classification — `FABRICATION_SUSPECTED` findings route into the existing AR-4 fix loop rather than hard-failing the run. (d) Port the masking checks into `ShellCommand` (it already parses this deeply for gating; this adds a read-side "would this invocation's exit code survive its plumbing" fact — transcribe the check table with attribution). (e) The `verification/` variant — extract-assertions-then-grep with flip-only-on-positive-discrepancy — is the natural second slice once OB1-2's ACs exist, and its conservative override rule ("only downgrade a claimed pass") should govern both slices.

### OB2-1. The mechanical command detector — discover a repo's own gate commands, safely

**Recommendation**: BORROW-PATTERN, **trigger-gated**: adopt when composed verify waves (or the queue-item-5 eval harness) need to run project gates on repos beyond this one.

**Where in ouroboros** (wired via evaluation stage 1 + `verification_artifacts.py`): `.ouroboros/mechanical.toml` holds per-project build/test/lint commands (their own dogfood file is 3 lines). When missing, `evaluation/detector.py` (2,362 LOC) makes **one** LLM call over manifest excerpts (40+ manifest types; "propose only commands that this project can actually execute right now… shell operators are forbidden," `:355-362`), then **validates every proposal against disk before writing**: ~90-tool executable allowlist (`languages.py:38-130`), shell-operator and absolute-path/`..`-escape rejection, argument-path containment, ~40 per-tool entry-point-exists validators (package.json script exists, Makefile target declared, cargo manifest path, gradle task, …, `detector.py:607-805`), and destructive-target refusal (`deploy`/`publish`/`install`). Anything unverifiable degrades to "skipped" — "Stage 1 must never produce a phantom failure." Honesty: this is also why their "$0 stage" is vacuous on unconfigured repos — detection costs one call, and no-commands ⇒ no gate.

**Gap in jido_radclaw**: gate commands live in prose (AGENTS.md's `mix precommit`) and in whatever the LLM decides to type into `run_command`. Nothing discovers, validates, or pins a foreign project's gate; the eval harness plan (queue item 5) will need exactly this for command-shaped cases, and Forge/system-path runs on arbitrary repos currently trust the model's guess.

**Why it matters**: it converts "the agent knows how to test this repo" from a prompt hope into a validated per-project artifact — and the validation recipe (allowlist + on-disk entry-point proof + destructive refusal) composes naturally with our approval gate: a command that was disk-validated at detection time is a much better candidate for a standing approval fingerprint than a free-typed one.

**Adoption sketch (when triggered)**: `.jido/gates.yaml` (or a `config.yaml` key) mirroring mechanical.toml; a `GateDetector` module following the `Triage.LLM` pattern for the single proposal call; port the validator table + allowlist as data (attribution line); wire as the command source for verify-stage `run_command`s and harness cases. The detection write is a config mutation — route it through the gate family (same posture as gepa OQ-1's deploy gate).

### OB2-2. Progress-aware loop stops — oscillation and regression detection for the fix loop

**Recommendation**: BORROW-PATTERN, **trigger-gated**: adopt on evidence of non-progressing reruns (the fix loop re-running to its cap with unchanged findings).

**Where in ouroboros** (wired — these are the *live* stagnation mechanisms; the marketed 4-pattern detector is dead, see §Skip): Ralph's terminal heuristics (`ralph_loop.py:418-437`) — **findings-hash oscillation stop** (SHA-256 over the QA verdict's `differences`+`suggestions`; 3 consecutive identical hashes ⇒ stop) and **grade-regression stop** (letter grades mapped to floats, 2 strictly-decreasing ⇒ stop); and the convergence evaluator's **withholding gates** (`evolution/convergence.py:83-181`) — refuse to declare success if the artifact never actually changed (`_count_evolved_generations == 0`), if any AC regressed vs. an earlier generation, plus a true period-2 oscillation check (`sim(N,N-2) ∧ sim(N-1,N-3)`, `:323-346`) and a repeated-question overlap check (≥70% across 3 rounds, `:348-369`).

**Gap in jido_radclaw** (verified): the composer's review→fix→re-review loop is bounded by count and budget only — `@default_rerun_cap 2` is explicitly "the bound on a non-progressing re-plan loop" (`route_composer.ex:209-212`), `loop.ex` classifies only converged/not-converged/deadlock, and nothing compares round N's findings to round N−1's. (OSA OS1-2 covers the *tool-call* layer; this is the *workflow-loop* layer above it.)

**Why it matters**: a count cap burns its full budget on a loop that stopped progressing after round one, and — the subtler failure the withholding gates target — a loop can "converge" because the fixer produced a no-op diff, not because findings were addressed. Findings are already structured (`findings:<lens>` artifacts), so a fingerprint comparison is a pure function over data the projection already holds.

**Adoption sketch (when triggered)**: a pure `RouteComposer.Progress` check consulted where the rerun edge fires: canonical-fingerprint the round's findings set (memory rule: hash the canonicalized semantic term, not rendered text — dedupe by lens+file+summary), stop-with-reason on identical consecutive fingerprints; optionally compare confirmed-findings counts as the grade analog. Emitting a distinct terminal (`route_stalled`) keeps it observable; the existing budget/cap machinery stays the outer bound.
